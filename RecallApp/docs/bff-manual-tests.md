# Ручные проверки BFF: вход и обновление токенов

Документ описывает сценарии, которыми мы вручную проверяем аутентификацию BFF и обновление токенов на текущем этапе (C0). Инструментарий: браузер, логи BFF, админка и события в Keycloak. Большую часть сценариев с 2026-10-28 закрывают автотесты (`Bff/Bff.Web/tests`, см. [README](../Bff/Bff.Web/tests/README.md)), руками остаётся то, что видно только в настоящем браузере и тяжело или невозможно достать в текущих автотестах.

Связанные решения: ADR 0002 (BFF), 0021 (хранилище сессий), 0025 (фреймворк BFF), 0027 (политика сессий и обновление токенов).

## Что покрываем и что нет

Проверяем сейчас: базовый вход/выход, упреждающий refresh, дедупликацию параллельных обновлений, стабильность ключа сессии, независимость нескольких сессий одного пользователя, поведение при провале refresh, переживание временного сбоя Keycloak, когерентность cookie с режимом «запомнить меня», параллельные запросы после простоя (встроенное продление не затирает новые токены).

Покрытие автотестами (`Tests.Integration`; категория `InProcess` с поддельным Keycloak, категория `Keycloak` с тестовым realm):

| Сценарий | Автотесты | Руками |
|---|---|---|
| 1. Вход и выход | нет: вход через страницы Keycloak не автоматизирован | **да**, при изменениях кода входа |
| 2. Упреждающий refresh | InProcess и Keycloak: refresh у порога, новые токены, роли из нового токена | нет |
| 3. Дедупликация параллельных обновлений | InProcess: пять параллельных запросов, один POST | нет |
| 4. Стабильность ключа сессии | косвенно: refresh сохраняет сессию тем же ключом (`RenewAsync`), сессия видна после refresh | по желанию |
| 5. Несколько сессий одного пользователя | нет | по желанию |
| 6. Провал refresh | InProcess (400, нет refresh-токена) и Keycloak (повторно использованный refresh-токен, неверный секрет) | нет |
| 7. Режим «запомнить меня» | A/B: нет, нужен перезапуск браузера. C: InProcess (окно и `expires=` после refresh, без refresh нет `Set-Cookie`) | **A и B** |
| 8. Keycloak недоступен | InProcess: 502 и таймаут, пауза, повтор после неё | нет |
| 9. Параллельные запросы после простоя | InProcess: окно 6 мин, один `Set-Cookie`, в сторе токены из refresh | нет |

Пока не проверяем:

- Token exchange: без потребителя (монолит) наблюдать нечего до Этапа C.
- Вытеснение уборщиком по простою установлен дефолт в 30 минут простоя и проход раз в 5 минут, за разумное время не увидеть без временного снижения порогов.

## Предусловия

1. Стек поднят: `docker compose up` из корня `RecallApp`. Контейнеры `edge-proxy`, `iam`, `iam-db`, `bff` живы.
2. Локальный Root CA импортирован в доверенные Windows (замок на `https://*.localhost` валиден).
3. В realm `recallapp` есть тестовый пользователь с клиентской ролью `app-user` (клиент `RecallApp`).
4. Хосты: приложение BFF - `https://bff.localhost`, Keycloak - `https://auth.localhost`.

### Эндпоинты BFF

| Путь | Назначение |
|---|---|
| `GET https://bff.localhost/login` | старт OIDC-входа, редирект на Keycloak, затем обратно |
| `GET https://bff.localhost/session` | состояние сессии (белый список, `Cache-Control: no-store`): `{ isAuthenticated, sub, name, email, roles }` |
| `POST https://bff.localhost/logout` | выход: сброс cookie и OIDC sign-out (только POST; GET отвечает 405) |

### Где смотреть логи

- **Консоль контейнера** (`docker compose logs -f bff`) - уровень Info и выше: `Performing token refresh…`, `…succeeded`, предупреждения.
- **Файл** `Bff/Bff.Web/Host/logs/<дата>.log` - уровень Debug: `Token refresh check…`, `…skipped (double-check)…`. Эти строки в консоль не попадают.

Опорные строки лога:

| Строка | Уровень | Значит |
|---|---|---|
| `Performing token refresh for session={key}` | Info | начато реальное обновление |
| `Token refresh succeeded for session={key}` | Info | обновление прошло, тикет переписан |
| `Token refresh skipped (double-check): session={key}` | Debug | параллельный запрос не стал обновлять повторно |
| `Token refresh check: timeUntilExpiry=…, threshold=…, session={key}` | Debug | решение «рано / пора» на каждом запросе |
| `Token refresh rejected by IdP with status {code}` | Warning | Keycloak окончательно отказал (400/401), дальше sign-out |
| `Token refresh failed with transient status {code}` | Warning | временный сбой: Keycloak или прокси ответили 5xx и т.п. |
| `Token refresh request failed` | Warning | временный сбой: сеть, таймаут HttpClient (5 с) или битый JSON |
| `Token refresh deferred: IdP unavailable, session kept, retry after {time}` | Warning | сессия сохранена, повтор не раньше `{time}` |
| `Token refresh skipped (retry backoff until {time}): session={key}` | Debug | идёт пауза после сбоя, запрос не пытается обновлять |
| `BFF session id missing, falling back to sub` | Warning | cookie без идентификатора сессии (деградация на sub) |

### Ускорение timing-сценариев

Порог `RefreshThreshold` задаётся переменной окружения контейнера `bff` (в `docker-compose.override.yml`, секция `bff.environment`):

```yaml
Oidc__TokenRefresh__RefreshThreshold: "00:10:00"
```

Нужны два разных режима, не один. Порог служит сразу и триггером «пора обновлять» (`timeUntilExpiry < threshold`), и окном анти-дубля (`now - lastRefreshed < threshold`, в течение которого запрос обновление пропускает).

**Режим A — «обновлять сразу» (сценарии 2, 4, 5).** Порог выше времени жизни access, напр. `00:10:00`. Тогда `timeUntilExpiry < threshold` истинно с первого запроса, refresh срабатывает немедленно. Realm трогать не нужно. Минус: после первого обновления окно анти-дубля держит пропуск 10 минут.

**Режим B — «обновлять часто» (сценарии 3, 6, 8).** Режим A здесь вреден: 10-минутное окно анти-дубля означает, что BFF 10 минут вообще не пытается обновлять токен, а значит не узнает про убитую в Keycloak сессию. Нужно, наоборот: короткий порог И короткий access, чтобы refresh предпринимался часто.

- env: `Oidc__TokenRefresh__RefreshThreshold: "00:00:30"`.
- realm: Access Token Lifespan = 1 минута.
- после смены войти заново (чтобы выдался короткий токен).

Так refresh предпринимается примерно раз в 30 секунд, и убитая сессия обнаруживается за ≈30–60 секунд.

После тестов вернуть: убрать env-переключатель (дефолт 1 минута) и Access Token Lifespan на боевое (5 минут, ADR 0027).

## Сценарий 1. Базовый вход и выход

**Цель.** Регресс после рефакторинга: вход, сессия с ролью, выход.

**Шаги.**
1. Открыть `https://bff.localhost/session` без входа.
2. Пройти `https://bff.localhost/login`, войти под тестовым пользователем.
3. Снова открыть `/session`.
4. Выйти: `POST /logout` (в консоли браузера `fetch('/logout', { method: 'POST' })`).
5. Снова открыть `/session`.

**Ожидаем.**
- Шаг 1: `isAuthenticated: false`.
- После входа в браузере появляется cookie `recall_bff`.
- Шаг 3: `isAuthenticated: true`, `name` заполнен, `roles` содержит `app-user`.
- Шаг 5: `isAuthenticated: false`.

## Сценарий 2. Упреждающее обновление токена

**Цель.** Ядро фичи: access обновляется до истечения, без разлогина.

**Предусловия.** Включён ускоряющий порог (`RefreshThreshold` = 10 минут), пользователь вошёл в аккаунт.

**Шаги.**
1. Сделать запрос `/session`.
2. Смотреть консоль `bff`.

**Ожидаем.**
- В консоли: `Performing token refresh for session=…`, затем `Token refresh succeeded for session=…`.
- `/session` по-прежнему `isAuthenticated: true`, разлогина нет.
- В событиях Keycloak (`auth.localhost` -> realm -> Sessions/Events) видно обновление токена для клиента `Bff.Web`.

---

## Сценарий 3. Дедупликация параллельных обновлений

**Цель.** На одну сессию один реальный refresh, параллельные запросы не плодят POST.

**Предусловия.** Режим B (порог `00:00:30` + Access Token Lifespan 1 минута), вход выполнен заново.

Режим A здесь не подходит. Запрос на адрес возврата сразу после входа (`GET /`) сам делает refresh и включает 10-минутное окно анти-дубля. Пачка после этого всегда даёт пять `skipped (double-check)` без POST, и замок не проверяется. В режиме B landing-запрос refresh не делает (до истечения 60 с, порог 30 с).

**Шаги.**
1. Войти, затем 30–55 секунд не делать запросов.
2. Отправить пачку параллельных запросов из DevTools-консоли:

   ```js
   Promise.all([...Array(5)].map((_, i) => fetch('/session?i=' + i, { cache: 'no-store' })))
   ```

   Разные URL и `cache: 'no-store'` обязательны: на одинаковые GET по одному URL Chromium держит блокировку HTTP-кэша и отправляет их на сервер по очереди (проверено 2026-10-28). Либо `curl` с общим cookie-файлом, запуская запросы параллельно.
3. Смотреть консоль и файл-лог `bff`.

**Ожидаем.**
- В консоли ровно одна пара `Performing… / …succeeded`.
- В файл-логе остальные запросы: `…skipped (double-check): session=…`.
- Если Keycloak ответил быстро, остальные запросы могут прийти уже после refresh и отсеяться на double-check без ожидания замка. Это тоже проход. Ожидание замка надёжно видно в сценарии 8A.
- В Keycloak один POST обновления на серию, не несколько.

## Сценарий 4. Стабильность идентификатора сессии через refresh

**Цель.** `bff_session_id` не меняется при обновлении токенов.

**Шаги.**
1. Войти, вызвать `/session` до порога - зафиксировать `session=…` в логе.
2. Дождаться (или форсировать порогом) обновления.
3. Сравнить `session=…` в строках `Performing…` / `…succeeded` с зафиксированным.

**Ожидаем.** Значение `session=` одно и то же до и после обновления.

---

## Сценарий 5. Несколько сессий одного пользователя

**Цель.** Вход с двух устройств/браузеров не связывает сессии: каждая цепочка рефрешится независимо, обновление одной не мешает обновлению другой.

**Предусловия.** Ускоряющий порог включён.

**Шаги.**
1. Войти под одним аккаунтом в браузере A и браузере B (либо два независимых cookie-jar).
2. Подёргать `/session` в обоих.
3. Смотреть логи.

**Ожидаем.**
- Два разных значения `session=` (по одному на браузер).
- Обновление идёт отдельно для каждого: активность в A не отменяет обновление в B (нет ситуации, когда B перестаёт обновляться, пока активен A).

## Сценарий 6. Провал refresh - выход и повторная аутентификация

**Цель.** Протухший или отозванный refresh ведёт к sign-out и возврату на вход (при живой SSO-сессии Keycloak - без пароля).

**Предусловия.** RefreshThreshold=00:00:30; AccesTokenLifespan=00:01:00 (в Keycloak).

**Предусловия.** Режим B (короткий порог `00:00:30` + Access Token Lifespan 1 минута), вход в аккаунт выполнен заново после смены паметров.

**Шаги.**
1. Войти в BFF.
2. В админке Keycloak завершить эту сессию пользователя (Sessions -> Logout).
3. Дёргать `/session` раз в ~15 секунд.

**Ожидаем.**
- Через ≈30–60 секунд в консоли: `Token refresh rejected by IdP with status BadRequest`, затем BFF делает sign-out. Строки `deferred` здесь быть не должно: отказ 400 не временный сбой.
- Cookie `recall_bff` сброшена, `/session` -> `isAuthenticated: false`.
- Переход на `/login`: если SSO-сессия Keycloak ещё жива - вход без ввода пароля (silent re-auth), иначе полный вход.

**Важно про тайминг ответа.** Sign-out в middleware вешает очистку cookie на ответ, но принципал текущего запроса уже проставлен на `UseAuthentication`. Поэтому запрос, на котором refresh провалился, может ещё раз отдать `isAuthenticated: true` (с заголовком удаления cookie), а `false` придёт на следующем поллинге, когда cookie уже нет. Это отставание на один запрос, не ошибка.

**Про задержку обнаружения.** Убийство сессии в Keycloak не разлогинивает BFF мгновенно. BFF узнаёт об этом только на следующей неудачной попытке refresh, поэтому окно обнаружения ограничено частотой refresh, то есть сроком жизни access-токена (ADR 0027).

## Сценарий 7. Cookie следует режиму «запомнить меня»

> Статус: **прошёл 2026-10-27** (A и B в Edge, C в patchright в режиме B ускорения). Код входа менялся 2026-10-27 (события OIDC объединены в `OnTokenValidated`, окно cookie через `SessionCookieLifetime.ResetWindow`).

**Цель.** Срок и персистентность cookie `recall_bff` совпадают с режимом входа (ADR 0027): без галочки cookie сессионная с окном SSO Idle (30 минут), с галочкой persistent с окном SSO Idle Remember Me (30 дней).

**Предусловия.** В realm включён Remember Me, SSO Session Idle = 30 минут, SSO Session Idle Remember Me = 30 дней. Порог `RefreshThreshold` по умолчанию, Access Token Lifespan боевой (5 минут). В браузере выключено восстановление сессии («Продолжить с того же места» или «Работать в фоне после закрытия окон»)

**Где смотреть.** DevTools → Application → Cookies → `https://bff.localhost` → `recall_bff`, столбец Expires / Max-Age: `Session` или дата. Либо Network → ответ на `/signin-oidc` → заголовок `Set-Cookie`, есть ли в нём `expires=`.

**Шаги A: без галочки.**
1. POST `/logout`, затем `/login`, войти без отметки Remember me.
2. Посмотреть cookie.
3. Полностью закрыть браузер (все окна), открыть `/session`.

**Шаги B: с галочкой.**
1. POST `/logout`, затем `/login`, войти с отметкой Remember me.
2. Посмотреть cookie.
3. Полностью закрыть браузер, открыть `/session`.

**Шаг C: сдвиг окна на refresh.** В сессии из B дождаться refresh (или включить режим A ускорения) и сравнить `expires=` в `Set-Cookie` ответа, на котором прошёл refresh, с предыдущим.

**Ожидаем.**
- A: Expires = `Session`; после перезапуска браузера `/session` → `isAuthenticated: false`.
- B: Expires ≈ сейчас + 30 дней; после перезапуска браузера `/session` → `isAuthenticated: true` (протухший access обновится refresh-ем).
- C: `expires=` сдвинулся вперёд на время, прошедшее с прошлой выдачи cookie. `Set-Cookie` есть только в ответах, на которых прошёл refresh.

**Нюанс по cookie.** Панель Application → Cookies показывает cookie только для origin, у которого сейчас открыта страница. Пока `bff.localhost` не загружен, список пуст, хотя cookie на месте.

**Если в варианте B получилось `Session`.** Не сработала эвристика: проверить, что в realm SSO Session Idle Remember Me действительно 30 дней, и что `refresh_expires_in` при входе с галочкой больше `Oidc:TokenRefresh:RememberMeThreshold`.

## Сценарий 8. Keycloak временно недоступен: сессия выживает

> Статус: **прошёл 2026-10-27** (оба варианта, patchright). Код добавлен 2026-10-27: исходы refresh `Success` / `Rejected` / `Unavailable`, пауза `Oidc:TokenRefresh:RefreshRetryBackoff`.

**Цель.** Временный сбой Keycloak (завис, остановлен, отвечает 5xx) не разлогинивает пользователя. BFF сохраняет сессию и повторяет refresh не чаще раза в `RefreshRetryBackoff` (15 секунд). Когда Keycloak вернётся, токены обновятся как обычно.

**Предусловия.** Режим B (порог `00:00:30` + Access Token Lifespan 1 минута), вход выполнен заново. Попытки refresh тогда идут примерно раз в 30 секунд, и сбой проявляется быстро.

**Как BFF ходит в Keycloak.** `Authority` указывает на `https://ah.localhost`, запрос проходит через `edge-proxy` (nginx) в контейнер `iam`. Два способа уронить Keycloak ведут в разные ветки кода:

| Вариант | Команда | Что видит BFF | Строка лога |
|---|---|---|---|
| A: заморозить | `docker compose pause iam` | соединение есть, ответа нет, срабатывает таймаут HttpClient 5 с | `Token refresh request failed` (`TaskCanceledException`) |
| B: остановить | `docker compose stop iam` | nginx отвечает 502 или соединение не устанавливается | `Token refresh failed with transient status BadGateway` либо `Token refresh request failed` |

Основной вариант A. В B есть ловушка инфраструктуры: nginx сейчас резолвит `iam` один раз при старте, и после `start iam` контейнер может получить другой IP. Если после возврата Keycloak BFF всё ещё видит 502, перезапустить прокси: `docker compose restart edge-proxy`.

**Шаги A: заморозка.**
1. Войти, `/session` → `isAuthenticated: true`.
2. `docker compose pause iam`.
3. Когда refresh уже пора делать, отправить пачку параллельных запросов из DevTools-консоли: `Promise.all([...Array(5)].map((_, i) => fetch('/session?i=' + i, { cache: 'no-store' })))` (почему не один URL, см. сценарий 3).
4. Минуту запрашивать `/session` раз в ~5 секунд.
5. `docker compose unpause iam`, ещё минуту запрашивать `/session` раз в ~5 секунд.

**Шаги B: остановка.** Как в A, только без выпуска пачки и на шаге 2 `docker compose stop iam`, а на шаге 5 `docker compose start iam` и ожидание готовности Keycloak (в `docker compose logs iam` строка `Listening on`).

**Ожидаем (оба варианта).**
- Во время сбоя `/session` всё время отвечает `isAuthenticated: true`, cookie `recall_bff` не сброшена.
- На каждую попытку в консоли два Warning: причина (см. таблицу выше) и `Token refresh deferred: IdP unavailable, session kept, retry after …`.
- Попытки идут не чаще раза в 15 секунд. Между ними в файл-логе Debug `Token refresh skipped (retry backoff until …)`.
- В варианте A запрос с попыткой отвечает примерно через 5 секунд, остальные запросы во время паузы отвечают сразу.
- Пачка в A: все пять ответов примерно через 5 секунд (четыре ждали замок). В логе одна пара `request failed` + `deferred`, затем четыре `skipped (retry backoff …)`. Это проверка повторной проверки паузы под замком: без неё было бы пять попыток подряд, около 25 секунд.
- После возврата Keycloak ближайшая попытка даёт `Performing token refresh…`, затем `Token refresh succeeded…`.

**Известное ограничение.** Если сбой длится дольше остатка жизни access-токена, access протухает, а BFF-сессия остаётся живой. `/session` этого не покажет, он отвечает из cookie. Вызовы API с таким токеном получали бы 401 до возврата Keycloak, но потребителя access пока нет (до Этапа C).

**Пограничный случай варианта A.** Замороженный Keycloak мог успеть принять запрос в буфер сокета. После `unpause` он его обработает и выпустит новый refresh-токен, хотя BFF уже отбросил ответ по таймауту и держит старый. При включённом Revoke Refresh Token повтор со старым токеном получит 400: `Token refresh rejected by IdP with status BadRequest`, затем sign-out. Такой исход подтверждает известный риск короткого таймаута и регрессом сценария не считается. Записать в итоги, решать отдельно.

## Сценарий 9. Параллельные запросы после простоя: встроенное продление не затирает новые токены

> Статус: **прошёл 2026-10-28** после исправления (`SlidingExpiration = false`). До исправления упал, баг из [bff-session-design.md, п. 8.1](bff-session-design.md#81-параллельное-продление-затирает-новые-токены) подтверждён.

**Цель.** После простоя дольше половины окна cookie несколько параллельных запросов не должны вернуть в стор старый, уже отозванный refresh-токен.

**Механика бага (до исправления).** После простоя у каждого из параллельных запросов срабатывало встроенное скольжение cookie: прошло больше, чем осталось. Каждый запрос клонирует свою копию тикета со старыми токенами. Один запрос делает refresh и сохраняет новые токены. Остальные пропускают refresh на double-check, но в конце ответа продлевают cookie своим клоном и перезаписывают запись стора старыми токенами. Следующий refresh идёт со старым refresh-токеном, Keycloak его уже отозвал.

**Предусловия.**
- Realm: Revoke Refresh Token = On, Refresh Token Max Reuse = 0, Access Token Lifespan = 5 минут, SSO Session Idle не меньше 30 минут.
- Порог `RefreshThreshold` по умолчанию (1 минута), env-переключателя режима A/B нет.
- Окно cookie BFF укорочено до 6 минут, чтобы не ждать 16 минут простоя. В `docker-compose.override.yml`, секция `bff.environment`:

  ```yaml
  Oidc__SsoSession__SessionIdle: "00:06:00"
  ```

  Окно BFF при этом короче SSO Idle Keycloak, сессия Keycloak за время теста не истечёт.
- Вход без Remember Me. Других вкладок с `bff.localhost` нет, автоматического поллинга `/session` нет.

**Почему такие тайминги.** Вход в момент 0:00. Окно cookie 0:00–6:00, `expires_at` access 4:30 (срок 5:00 минус `ClockSkewBuffer`; до 2026-10-28 на входе буфер не вычитался, было 5:00).

| Момент | Что выполняется |
|---|---|
| после 3:00 | прошло больше половины окна: до исправления здесь на любом запросе срабатывало встроенное скольжение |
| после 3:30 | до `expires_at` ≤ 1 минуты, refresh нужен |
| 4:15–4:45 | оба условия верны, окно ещё открыто. Параллельные запросы отправлять здесь |

Любой запрос между входом и параллельными запросами сдвинет окно и сорвёт подготовку.

**Шаги.**
1. Войти через `/login` и записать время входа по часам. На входе refresh не выполняется, поэтому ориентира в логе не будет.
2. Оставить открытой страницу `bff.localhost` с DevTools (Network с фильтром `session`, включённый Preserve log). Никаких запросов не делать.
3. В интервале 4:15–4:45 после входа отправить пачку параллельных запросов из консоли:

   ```js
   Promise.all([...Array(5)].map((_, i) => fetch('/session?i=' + i, { cache: 'no-store' })))
   ```

   Разные URL и `cache: 'no-store'` обязательны. Chromium на одинаковые GET по одному URL держит блокировку HTTP-кэша и отправляет их на сервер по очереди: первый запрос успевает сделать refresh, остальные приходят уже со свежим тикетом, и сценарий ничего не проверяет. Признак в логе: у всех запросов, кроме первого, `timeUntilExpiry` около 4:29 и нет `skipped (double-check)`.
4. Через 90 секунд после параллельных запросов (не раньше: окно анти-дубля 1 минута) один раз запросить `/session`.
5. Ещё раз запросить `/session`.

**Ожидаем (корректное поведение).**
- Шаг 3: в логе одна пара `Performing token refresh…` / `Token refresh succeeded…`, в файл-логе четыре `skipped (double-check)`. В Network ровно один `Set-Cookie: recall_bff=…` на пачку (от refresh).
- Шаг 4: `Token refresh check` показывает положительный `timeUntilExpiry`, около 3 минут: новый `expires_at` = момент refresh + 4:30. Refresh не нужен, `isAuthenticated: true`.
- Шаг 5: `isAuthenticated: true`.

**Признаки бага (регресс).**
- Шаг 3: в Network у ответов на параллельные запросы **пять** заголовков `Set-Cookie: recall_bff=…`, а не один. Один выставил refresh, четыре оставшихся выставило встроенное продление.
- Шаг 4: `timeUntilExpiry` отрицательный (в сторе снова старый `expires_at` от входа, 4:30), затем `Performing token refresh…` и `Token refresh rejected by IdP with status BadRequest`. В событиях Keycloak ошибка `REFRESH_TOKEN_ERROR` (переиспользование отозванного токена).
- Шаг 4 отвечает `isAuthenticated: true` с удаляющим `Set-Cookie` (отставание на один запрос, как в сценарии 6). Шаг 5 отвечает `false`.

**Если бага не видно.** Сначала проверить, что запросы дошли до сервера одновременно: четыре `skipped (double-check)` в файл-логе. Затем проверить, что у ответов на параллельные запросы действительно было скольжение (несколько `Set-Cookie`). Если `Set-Cookie` один, подготовка сорвалась: был лишний запрос до параллельных, либо они ушли вне интервала 4:15–4:45.

**После теста.** Убрать `Oidc__SsoSession__SessionIdle` из override. Если сценарий упал, записать в журнал прогонов, повторить после исправления (п. 8.1 дизайн-документа).

## Сценарий 10. Сквозной вызов API: браузер → BFF → монолит (C1)

**Цель.** Первый сквозной проход личности: браузер с BFF-сессией вызывает доменный API монолита; BFF проксирует `/api/**`, прикрепляет access-токен (Bearer) и проксирует в монолит; монолит валидирует JWT, выполняет JIT-провижининг доменного пользователя и отдаёт профиль из домена.

**Покрытие автотестами.** Часть сценариев уже закрыты автотестами: JIT против живой app_db (`Tests.Integration`, `Category=Database`), анонимный `/api/**` → 401 problem+json.

**Предусловия.**
1. Стек поднят: `docker compose up --build -d`; `docker compose logs -f app` показывает применённые миграции и старт `dotnet watch`.
2. Прокси включён: `docker compose config | Select-String AppProxy` показывает `AppProxy__Destination=http://app:8080`.
3. В realm `recallapp` есть тестовый пользователь с клиентской ролью `app-user`.

**Эндпоинт.** `GET https://bff.localhost/api/users/me` → монолит `GET /api/users/me`.

**Шаги.**
1. Анонимно: `GET https://bff.localhost/api/users/me`.
2. `https://bff.localhost/login`, войти под тестовым пользователем.
3. В той же сессии: `GET https://bff.localhost/api/users/me`.
4. Повторить запрос из шага 3.
5. Проверить строку в БД: `docker compose exec app-db psql -U app_runtime -d app -c "SELECT id, keycloak_sub, email, display_name FROM accounts.users;"`.

**Ожидаем.**
- Шаг 1: **401** `application/problem+json`, код `NotAuthenticated`.
- Шаг 3: **200** `{ "id": "<uuid>", "displayName": "<имя из токена>", "email": "<email>", "emailVerified": <true|false> }`.
- Шаг 4: тот же `id` (JIT-upsert идемпотентен).
- Шаг 5: одна строка, email пользователя, `display_name` из токена; владелец таблицы — `accounts_owner`.

**Где смотреть при отказе.**
- 401 `NotAuthenticated` после входа: сессия не создана (сценарий 1).
- 502 от BFF: монолит не поднят (`docker compose logs app`) или `AppProxy__Destination` не доехал.
- 500 из монолита: JWT-валидация (CA из `shared_certs` не доверен в контейнере `app`, недоступен `https://auth.localhost`) или миграции не применены (`logs app`, строка про `AccountsMigrations`).
