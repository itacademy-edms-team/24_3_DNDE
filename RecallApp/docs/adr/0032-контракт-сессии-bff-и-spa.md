# ADR 0032. Контракт BFF → SPA: `/session` как проба живости сессии

- **Status:** accepted
- **Date:** 2026-11-04
- **Decision-maker(s):** Aleksandr
- **Owner:** Aleksandr
- **Scope:** Платформа (общее)

## Контекст

SPA должен понимать, жива ли его сессия на BFF, и показывать личность пользователя в шапке. При этом в системе есть два независимых источника данных о человеке:

- **BFF** - cookie-сессия и токены Keycloak: `sub`, `name`, `email`, client-роли приложения в `resource_access` access-токена (ADR 0024);
- **модульный монолит** - доменный профиль `User` (ADR 0020): `id`, `displayName` (domain-owned), кэш `email`, вычисляемый `emailVerified`.

Первая версия `/session` отдавала всё, что есть у BFF: `{isAuthenticated, sub, name, email, roles}`. По ходу работы выяснилось, что kecloak-роли в браузере не нужны для работы и опасны для публикации в неадминское окружение по соображениям безопасности, а `name` из токена расходится с `displayName` из домена: переименование профиля не видно в шапке до обновления ID-токена. Нужно пересмотреть возвращаемое `/session` тело ответа и согласовать.

Ограничения: браузер - недоверенная среда; авторизацию выполняет монолит по Bearer-токену (ADR 0028); SPA ходит в монолит только через `/api/**` того же BFF; back-office планируется отдельным приложением со своим BFF, поэтому ролевой навигации в публичном SPA не будет.

## Рассмотренные варианты

### Вариант 1. `/session` - проба сессии плюс личность из токена; роли и `sub` не отдаются - ВЫБРАН

```json
GET /session  →  { "isAuthenticated": true, "name": "...", "email": "..." }
GET /session  →  { "isAuthenticated": false }   // аноним
```

- `/session` отвечает только на вопрос «сессия жива и чья она» и **не ходит в монолит**: недоступность App не должна выглядеть как разлогин, иначе браузер уходит в петлю входа и не может даже корректно разлогиниться.
- `name`/`email` нужны для первого рендера шапки и как деградация, когда монолит недоступен; источником правды для профиля остаётся домен (`displayName`).
- Роли не отдаются: они ничего не разрешают в браузере (монолит сам валидирует токен), но раскрывают модель доступа и провоцируют «UI-авторизацию», которая ничего не защищает.
- `sub` не отдаётся: клиенту не нужен, стабильный публичный идентификатор - `id` домена из `/api/users/me`.
- Ответ `no-store`: bfcache и back-навигация иначе показывали бы устаревшее состояние.

### Вариант 2. «Толстая» сессия: `{isAuthenticated, sub, name, email, roles}` - ОТКЛОНЁН

Реализовано первым и заменено этой записью.

- Роли в JS: модель доступа видна браузеру и любому расширению, плюс соблазн строить авторизацию на клиенте.
- Два источника имени: `name` из токена и `displayName` из домена расходятся после редактирования профиля - шапка и страница аккаунта показывают разное.
- Расширение контракта «на будущее» без потребителя: когда появится ролевой UI, он будет в back-office со своим BFF.

### Вариант 3. Тонкий `/session` = `{isAuthenticated, roles}`, личность только из домена - ОТКЛОНЁН

- Шапка становится зависимой от монолита: при недоступном App пользователь видит «Пользователь» вместо имени, хотя сессия жива.
- Лишний доменный запрос на каждой странице ради строки в шапке.
- Роли всё равно уходят в браузер - главный минус варианта 2 сохраняется.

### Вариант 4. Проверять сессию через `/api/users/me`, отдельного `/session` нет - ОТКЛОНЁН

- Аутентификация попадает в зависимость от монолита: падение App превращается в «сессии нет» и петлю входа.
- JIT-провижининг (ADR 0020) выполняется на первом доменном запросе, то есть проверка сессии начинала бы создавать доменные строки.
- Семантика смешивается: `/api/**` - бизнес-данные, а «жива ли сессия» - свойство самого BFF.

## Решение

**`/session` - проба живости сессии BFF.** Отдаёт `{isAuthenticated, name, email}` для авторизованного пользователя и `{isAuthenticated: false}` для анонима; не проксируется в монолит, `no-store`, `sub` и роли не содержит.

**Профиль - только из домена** (`GET /api/users/me`). Клиент отображает `displayName` из домена, а `name`/`email` из `/session` использует как fallback. Fallback полезен для ситуаций, когда монолит по каким-либо причинам не отвечает, тогда связка app -> bff -> keycloak всё ещё считается валидной для получения информации об аккаунте, пускай и в очень ограниченном формате.

**Диагностика - отдельный маршрут** `GET /debug/session`: `{isAuthenticated, sub, name, email, roles, accessTokenExpiresAt}`. Закрыт флагом `Diagnostics:Session` (по умолчанию `false`, включён в `appsettings.Development.json`), при выключенном флаге отвечает `404`. Это инструмент разбора «почему 403», а не контракт для SPA.

**Авторизация выводится из ответов API**, а не из данных в JS: отказ приходит как `403` в ProblemDetails (ADR 0031).

## Последствия

- Клиент: `SessionState` = `{isAuthenticated, name?, email?}`; шапка берёт `displayName` из `useMyAccount()` с fallback на токен; защита от петли входа живёт в `authRedirectGuard`.
- Расширять `/session` ролями при появлении новых экранов **не** будем: либо эндпоинт в монолите, отвечающий по существу (в т.ч. `403`), либо back-office.
- `/session` остаётся единственным маршрутом BFF, который не проксируется в монолит; это свойство нужно сохранять при изменениях конвейера.
- Тесты: контракт `/session` (белый список полей) и `/debug/session` (флаг включён/выключен) на уровне интеграционных.
- Диагностический маршрут нельзя включать в проде: в нём `sub` и роли. Флаг - часть конфигурации, а не признак окружения, потому что контейнер и тестовый хост могут работать не в `Development`.
