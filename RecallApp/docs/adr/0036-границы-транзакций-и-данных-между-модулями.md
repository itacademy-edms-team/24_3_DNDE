# ADR 0036. Границы транзакций и данных между модулями

- **Status:** proposed
- **Date:** 2026-11-10
- **Decision-maker(s):** Aleksandr
- **Owner:** Aleksandr
- **Scope:** Платформа (общее)

## Контекст

Модульный монолит (ADR 0013) живёт в одной PostgreSQL (ADR 0015) со схемой на модуль и собственными миграциями (ADR 0029). Схемы изолированы ролями: runtime-роль модуля имеет DML только в своей схеме, соединения распределены по модулям через `ConnectionPoolBudget` и `PoolLeaseHolder`.

При проектировании модуля Sets (каталог наборов) возникли два связанных вопроса:

1. **Как модулю получить идентификатор текущего доменного пользователя.** JIT-провижининг (ADR 0020) выполняется сквозной ступенью конвейера (`UseDomainProvisioning`) и гарантирует существование строки в `accounts.users`, но текущий контракт `IDomainProvisioner.EnsureProvisionedAsync` возвращает `void` и не отдаёт `User.id`. До этого момента его получали самостоятельно: `GetMyAccount` парсит claim `sub` и ищет пользователя по `keycloak_sub`.
2. **Можно ли и как менять данные сразу в нескольких схемах атомарно** - с гарантией «всё или ничего» и откатом.

Обсуждённые варианты второго вопроса показали, что «правильный на вид» инструмент (межмодульная транзакция) тянет за собой отказ от изоляции модулей, а обходные пути (репликация данных, `sub` как первичный ключ) ломают уже принятые решения.

### Рассмотренные варианты

**Вариант 1. Атомарность в границах модуля, межмодульно - чтение и реакции.**

Транзакция принадлежит модулю и не выходит за его схему. Если другому модулю нужны данные, то он читает их через публичный контракт (`*.Contracts`) или реагирует на доменное событие из того модуля, записывая результат в свою схему. Для схем, допускающих отставание.

- **Плюсы:** модуль остаётся локально-атомарным и выносимым (критерии ADR 0013); нет распределённых транзакций и саг в обычных путях; отказ в одном модуле не ломает операции другого; границы видны в коде и в схеме БД.
- **Минусы:** межмодульные read-модели обновляются с задержкой; удаление данных, распределённым по схемам, требует фоновой чистки; часть проверок (квоты, лимиты) требует одного владельца, а не распределённого.

**Вариант 2. Общий scoped `UnitOfWork` с одной транзакцией на запрос.**

Все `DbContext` модулей цепляются к одной транзакции (`BeginTransaction` + `UseTransaction`), `SaveChanges` вызывается по порядку, ошибка должна производить откат всего процесса.

- **Плюсы:** «всё или ничего» между модулями без брокера и outbox; откат в пределах процесса.
- **Минусы:** граница транзакции становится шире границы модуля - модуль перестаёт быть локально-атомарным и выносимым; сбой в любом участнике откатывает чужие операции (баг в Sets ломает провижининг и вход); требует одного физического соединения, то есть обхода квот `ConnectionPoolBudget`; требует ролей с правами в нескольких схемах, что разрушает ролевую изоляцию; порядок `SaveChanges` и обработка частичных сбоев превращаются в реализацию самодельной саги.

**Вариант 3. Репликация данных смежного модуля через доменные события.**

`Accounts` публикует событие о создании пользователя, `Sets` держит проекцию (`sets.users`) и читает из неё.

- **Плюсы:** модуль автономен, чтение локальное, JOIN внутри своей схемы.
- **Минусы:** для **записи** это не работает: идентификатор нужен в том же запросе, а событие асинхронно (гонка на первом запросе пользователя); появляется второй владелец факта, дублирование и расхождение данных, backfill для ранее созданных пользователей. Для **чтения** (read-модели, например каталог Organization) подход легитимен - там отставание допустимо.

**Вариант 4. `sub` из токена как первичный ключ доменного пользователя.**

- **Плюсы:** идентификатор известен без обращения к Accounts.
- **Минусы:** доменный пользователь становится 1:1 с личностью IdP; закрывает слияние аккаунтов по подтверждённому email (ADR 0022), смену/переезд realm, отдельный realm служебного приложения (ADR 0004). Противоречит ADR 0020, где личность и доменный пользователь разведены.

**Вариант 5. Межсхемные внешние ключи (с каскадами или без), триггеры или хранимые процедуры, пишущие в две схемы.**

- **Минусы:** FK между схемами связывает модули на уровне схемы БД: появляется зависимость порядка миграций (потомок не создаётся раньше родителя), требование `REFERENCES` на чужую таблицу, а главное - при выносе модуля в сервис FK нужно снимать миграциями во всех модулях-потомках. Каскады и триггеры хуже того: один модуль удаляет данные другого в обход его политик. Хранимые процедуры, пишущие в две схемы, атомарны, но уносят доменные правила в SQL и дублируют их.

## Решение

Принимаем **вариант 1**. Правила, обязательные для всех модулей:

### 1. Граница транзакции = граница модуля

Одна доменная операция изменяет данные только своей схемы. Агрегат не пересекает схемы: если данные обязаны меняться вместе, это один агрегат и он живёт в одном модуле. Межмодульная атомарность не является целью проектирования.

### 2. Межмодульное чтение - через контракты, без записи

Модуль читает чужие данные через публичный контракт (`X.Contracts`, ADR 0029). Запись в чужую таблицу запрещена; `JOIN` через границу схемы модуля запрещён. Ссылка на чужую сущность - только идентификатор (`uuid`) с индексом, **без внешнего ключа между схемами**: FK, каскады и триггеры через границу модуля не создаём.

### 3. Межмодульные реакции - доменные события, с допуском на отставание

Модуль-владелец публикует событие, заинтересованные модули обновляют **свои** данные. Отставание считается нормой для read-моделей, счётчиков активности и уведомлений. События не используются как способ получить чужие данные в том же запросе. Межмодульные события и outbox вводятся при первом реальном потребителе (ADR 0029).

### 4. Идентификатор текущего пользователя поставляет конвейер, а не модуль

- Владелец JIT-провижининга - Accounts (ADR 0020).
- Ступень `UseDomainProvisioning` после успешного провижининга публикует `User.id` в scoped-сервис `ICurrentUser` (`Common.Application`).
- Модуль читает `ICurrentUser.UserId` и ничего более: не парсит claims, не ищет пользователя по `keycloak_sub`, не загружает сущность пользователя и не держит её копию.
- Внеконвейерные сценарии (фоновые задачи, доменные события, MCP-агент) получают пользователя через `Accounts.Contracts` - отдельной задачей при появлении первого такого сценария.

**Техдолг, вытекающий из решения:** `IDomainProvisioner.EnsureProvisionedAsync` должен возвращать идентификатор доменного пользователя (например, `Task<Guid?>`), а `ICurrentUser` - получить регистрацию в `Common.Application` и заполнение в ступени провижининга.

### 5. Удаление и жизненный цикл - мягкое удаление у владельца, чистка силами самих модулей

Межсхемные FK, каскады и триггеры запрещены: целостность между модулями обеспечивается процессом, а не ограничениями БД. Удаление сущности, на которую ссылаются другие модули (например, аккаунт, у которого есть наборы), идёт в две ступени:

1. **Модуль-владелец помечает строку удалённой** (`deleted_at` / `is_deleted`) и не стирает её физически. Для читателей сущность с этого момента не существует, но строка пока лежит - чтобы ссылающиеся модули успели увидеть факт удаления.
2. **Каждый ссылающийся модуль убирает свои данные сам** - своим фоновым процессом внутри монолита (hosted service модуля), а не чужим кодом в своей схеме: Sets удаляет или скрывает наборы удалённого владельца, Study - его сессии и SRS-записи, Organization - записи каталога.

Правила, заменяющие FK:

- **Физического удаления строк, на которые могут ссылаться другие модули, нет.** Владелец стирает персональные данные сразу при пометке (152-ФЗ), а tombstone хранит только идентификатор и время.
- **Чтение терпимо к отсутствию родителя.** Если ссылка не разрешается (строка помечена или уже удалена), потребитель трактует сущность как удалённую и не падает со ссылочной ошибкой.
- **Никто никого не ждёт.** Порядок удаления не важен: каждая чистка идемпотентна и повторяется (опрос контракта или событие), цепочки сходятся за несколько проходов.
- **Tombstone проверяется на входе.** Запрос с валидным токеном уже помеченного пользователя отсекается в JIT-ступени - данные в удалённого владельца не пишутся.

Фоновой обработки в монолите сейчас нет: её появление входит в техдолг по lifecycle (стыкуется с ADR 0020).

### 6. Исключение: shared transaction scope

Допускается только под конкретный сценарий, когда атомарность между модулями доказанно необходима, и оформляется отдельным решением (ADR или PDR) до реализации:

- одно физическое соединение, `BeginTransaction` у оркестратора, `UseTransaction` у остальных участников, фиксированный порядок `SaveChanges`, откат по любой ошибке;
- оркестратор один - модуль, владеющий сценарием;
- осознанно принимаются: обход квот `ConnectionPoolBudget` на время операции, необходимость роли с правами в нескольких схемах, потеря возможности вынести участников в сервисы;
- обязателен интеграционный тест, доказывающий откат при сбое второго участника.

## Последствия

- Обычные операции не требуют ни саг, ни межмодульных транзакций; сложность остаётся локальной для модуля.
- Модули сохраняют выносимость по ADR 0013: транзакционные границы совпадают с границами схем.
- Ролевая изоляция схем остаётся структурным запретом межмодульной записи.
- Межсхемных FK нет: ссылки используют `uuid` с индексом; отсутствие FK между схемами проверяется архитектурным тестом (как и запрет ссылок между проектами модулей). За счёт этого вынос модуля в сервис не требует миграций в чужих модулях.
- Read-модели и счётчики могут отставать; для пользовательских сценариев, где отставание недопустимо (деньги, права доступа), данные держит один владелец, остальные читают его состояние.
- Появляется техдолг: доработка `IDomainProvisioner` + `ICurrentUser` (нужна модулю Sets до первой ручки).
- Удаление аккаунта и связанных данных - soft-delete + purge-задачи (стыкуется с техдолгом ADR 0020).
- Любой будущий сценарий «нужно сразу в двух схемах» разбирается по порядку: пересмотреть границу модуля -> владелец + событие -> shared transaction в качестве исключения.
