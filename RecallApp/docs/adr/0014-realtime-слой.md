# ADR 0014. Realtime-слой для мультиплеера

- **Status:** accepted
- **Date:** 2026-10-20
- **Decision-maker(s):** Aleksandr
- **Owner:** Aleksandr
- **Scope:** Платформа (общее)

## Контекст

Нличие мультиплеера в системе есть в требованиях и представляет собой live-соревнование по набору с лидербордом в конце. На нём показываем счётом за правильность и скорость и подиум (US «Мультиплеер», План §3.7). Это по сути своей realtime взаимодействие, в которой как клиент может слать сообщения серверу, так и сервер клиенту, поэтому необходима двусторонняя связь. Требования: низкая задержка (План НФТ, §220), переподключение игрока (US «Мультиплеер»), вход гостя по коду матча без аккаунта (§3.7).

Одиночное обучение от realtime не зависит - это отдельный слой (План §4, ставка про realtime). Бэкенд на C# / .NET (ADR 0012), стиль - модульный монолит, внутри которого realtime-подсистема как первый кандидат на вынос (ADR 0013). Протокол ранее был отложен в spike (Backlog #60); эта запись его закрывает.

## Рассмотренные варианты

Основная развилка заключается в выборе транспорта и уровеня абстракции над ним.

### Вариант 1. Голый WebSocket

Прямое использование WebSocket API без фреймворка.

- **Плюсы:** полный контроль, стандартный протокол, любой клиент.
- **Минусы / почему отклонён:** переподключение, группировку по матчам, рассылку в группу и backplane для нескольких экземпляров придётся писать самому. Это повторная реализация того, что уже реализовано в виде фреймворка и используется людьим. Ещё это очередной, требующий обслуживания, элемент.

### Вариант 2. Server-Sent Events (SSE)

Однонаправленный поток сервер -> клиент.

- **Плюсы:** просто, работает поверх обычного HTTP, закроет авто-переподключение в браузере.
- **Минусы / почему отклонён:** однонаправленность. Матч требует двунаправленного сообщения, что привело бы к проектированию крайне изощрённых решений и применению метода не по назначению.

### Вариант 3. ASP.NET Core SignalR - ВЫБРАН

Realtime-фреймворк поверх транспортов, нативный для .NET.

- **Плюсы:** сам согласует транспорт (WebSocket, фолбэк на SSE/long-polling); встроены переподключение, **группы (через комнаты матчей)**, рассылка в группу (лидерборд, счёт); нативен стеку (ADR 0012); шина сообщений через Redis при будущем масштабировании без переписывания прикладного кода.
- **Минусы:** свой протокол поверх WebSocket, по сути зависимость от поставщика; на веб-клиенты тянем зависимость `@microsoft/signalr` (ADR 0011) и соответсвенно увеличиваем размер бандла.

## Решение

Realtime-слой строим на **ASP.NET Core SignalR** (вариант 3).

**Размещение.** Realtime - **модуль внутри модульного монолита** (ADR 0013), отдельного контейнера пока нет. SignalR-hub поднимается в том же приложении.

**Путь подключения.** Клиент подключается к hub **напрямую**, минуя BFF. BFF со своей stateful cookie-сессией постоянное WS-соединение не проксирует. Аутентификация соединения с помощью **короткоживущего connection ticket**, который BFF выдаёт авторизованному клиенту; клиент предъявляет ticket при открытии соединения. Гость же получает ticket по коду матча без полноценного аккаунта (§3.7).

**Состояние матча.** На старте в виде in-memory процесса внутри одного экземпляр приложения. Для комнат матчей используем SignalR группы.

## Последствия

- На C4-Container realtime пока что считается частью единого контейнера-монолита. Появляется прямая связь «клиент -> монолит» по WebSocket (SignalR) для матчей, **в обход BFF** (у BFF остаётся обычный HTTPS-путь для остального).
- BFF должен будут дорабатываться вместе с realtime-модулем.
- Фронт получает зависимость `@microsoft/signalr` (ADR 0011).
- **Монолит становится stateful** из-за in-memory состояния матчей горизонтальное масштабирование ограничено — либо один экземпляр на систему, либо привязка клиента к конкретному экземпляру (до введения шины).

### Важность будущего выноса

Realtime stateful и чувствителен к задержке - он **первым упрётся в масштаб** среди всех модулей. При росте нагрузки на матчи вынос realtime в **отдельный набор контейнеров** перестаёт быть опциональным и становится необходимым. Что это повлечёт:

- потребуется(ются) отдельный(е) контейнер(ы) realtime-сервиса, масштабируемые независимо от основного монолита;
- развёртыване **шины** (высокоскоростное хранилище с поддержкой pub/sub или брокер) для рассылки событий матча между экземплярами - игроки одного матча могут быть подключены к разным экземплярам;
- отдельное хранилище состояния матчей, раз процесс перестаёт быть единственным.

Однако это забота будущей отдельной ADR. Здесь фиксируется её **неизбежность при нагрузке**, чтобы stateful-решение на старте не воспринималось как постоянное.
