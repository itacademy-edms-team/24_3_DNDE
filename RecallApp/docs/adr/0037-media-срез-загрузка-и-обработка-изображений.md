# ADR 0037. Media-срез: модуль Media, загрузка и обработка изображений

- **Status:** accepted
- **Date:** 2026-11-10
- **Decision-maker(s):** Aleksandr
- **Owner:** Aleksandr
- **Scope:** Платформа (общее)

## Контекст

CREATE-01 требует изображений на сторонах флеш-карточки, а значит в первом же срезе контента появляются файлы. База решений уже есть: объектное хранилище S3-совместимое (ADR 0008), доступ через presigned-ссылки (ADR 0017), многослойная защита изображений с обязательным пересжатием (ADR 0018).

При детализации всплыли три вопроса, которые ADR 0017 не закрывает:

1. **Где живут метаданные файлов.** Набор владеет контентом, но байты и их жизненный цикл лежат в отдельном домене (карта модулей, модуль Media).
2. **Что реально можно зашить в подпись загрузки.** ADR 0017 предполагает presigned PUT с ограничениями «макс. размер, content-type, фиксированный ключ» прямо в подписи. Для PUT это верно лишь частично: ключ задаётся путём, `Content-Type` можно включить в подписываемые заголовки, а **предельный размер в подпись не зашивается**, то есть файл на гигабайт пройдёт, и узнаем мы об этом только после загрузки (или никогда, если не будет `confirm`). Ограничение размера на стороне хранилища умеет только POST-policy с `content-length-range`.
3. **Чем пересжимать.** ADR 0018 требует декодирования и перекодирования на сервере, значит нужна библиотека работы с изображениями, у которой будем допустимая лицензия.

Дополнительно, проверено по документации cloud.ru: endpoint `https://s3.cloud.ru`, регион `ru-central-1`, virtual-hosted адресация (`{bucket}.s3.cloud.ru`; субдомен включается явно в настройках бакета), `AccessKeyId` = `<tenant_id>:<key_id>`, CORS настраивается на бакет (`PutBucketCors`, до 100 правил), presigned-ссылки поддерживаются (SigV4).

## Рассмотренные варианты

**Вариант 1. Метаданные и файлы внутри модуля Sets.** Таблица `sets.media_objects`, сервис загрузки в Sets.
Плюсы: быстро, меньше проектов. Минусы: файлы - это чужой домен (карта модулей), Sets начинает знать про S3, ключи и TTL; при появлении других потребителей медиа (аватары, изображения в других типах элементов, MP) логику придётся выносить. Отклонён.

**Вариант 2. Минимальный модуль Media сразу (выбран).** Схема `media`, четыре проекта по ADR 0029, контракт для потребителей; Sets хранит только `media_id`.
Плюсы: границы по карте модулей, один владелец файлов и их жизненного цикла, потребители не знают про S3. Минусы: +1 модуль в первом срезе, больше кода, миграций, тестов.

**Вариант 3. Проксирование загрузки через монолит.** Уже отклонён в ADR 0017 (нагрузка, масштабирование, буферизация). Не пересматриваем.

**Библиотека обработки изображений:**

- **SkiaSharp** (`SkiaSharp` + `SkiaSharp.NativeAssets.Linux.NoDependencies`) - MIT, декодирование PNG/JPEG/WebP, кодирование WebP, не требует системных библиотек в контейнере. **Выбран.**
- **ImageSharp** - удобнее API, но Six Labors Split License: для коммерческого использования нужна платная лицензия. Отклонён, чтобы не закладывать ограничительную лицензию в основу.
- **Magick.NET** - Apache-2.0, но тяжёлый, с системными зависимостями и широкой поверхностью атаки (в ADR 0018 как раз разобраны эксплойты парсеров). Отклонён.
- **Без пересжатия** (только проверка сигнатуры) - дешевле, но прямое отклонение от ADR 0018. Отклонён.

## Решение

### 1. Модуль Media - владелец файлов и метаданных

- Схема `media` в общей БД, собственные миграции, проекты `Media.Domain` / `Media.Application` / `Media.Contracts` / `Media.Infrastructure` (ADR 0029).
- Таблица `media.media_objects`: `id`, `owner_id` (uuid, без межсхемного FK), `object_key`, `content_type`, `size_bytes`, `width`, `height`, `status` (`pending` / `ready` / `deleted`), `created_at`, `updated_at`, `deleted_at`.
- Sets хранит в payload элемента только `media_id` (uuid, без FK, ADR 0036) и ничего не знает про S3, ключи и TTL.

### 2. Загрузка: presigned POST с policy + подтверждение

Загрузка идёт не `PUT`, а multipart-формой `POST` в бакет с подписанной политикой - это единственный способ ограничить размер **силами хранилища**.

1. `POST /api/media/uploads` (тело: заявленный `contentType` и `size`) -> строка `pending`, возвращается `{ mediaId, url, fields, objectKey, expiresIn }`. На этом шаге `size > 10 МБ` или неподдерживаемый `contentType` отклоняются сразу.
2. Сервер собирает policy через `CreatePresignedPost` (AWSSDK.S3 v4): `expiration` (10 минут), `["eq", "$key", "tmp/{uploadId}"]`, `["eq", "$content-type", "image/..."]`, `["content-length-range", 1, 10485760]`, `success_action_status=201`. SDK возвращает `url` и уже подписанные `fields` (`policy`, `x-amz-algorithm`, `x-amz-credential`, `x-amz-date`, `x-amz-signature`).
3. Клиент отправляет `FormData` (поля политики + файл) прямо в бакет, получает 201 с телом (в нём ключ и ETag).
4. `POST /api/media/uploads/{mediaId}/confirm` -> сервер делает `HEAD`, проверяет размер и тип, запускает обработку, ставит `ready` и возвращает метаданные (`id`, `width`, `height`, `url`).

Почему не PUT: presigned PUT не умеет ограничивать размер, и злоумышленник мог бы залить гигабайты, узнавали бы мы об этом постфактум. POST-policy отклоняет такую загрузку до приёма байт. Ключ объекта фиксирован сервером (клиент не может выбрать путь), `Content-Type` и размер проверяет хранилище.

**Уточнение к ADR 0017:** механизм загрузки меняется с presigned PUT на presigned POST с policy; presigned GET для выдачи остаётся как в 0017. Тело 0017 не меняется (заморожено), уточнение живёт здесь.

### 3. Обработка: конвейер ADR 0018

По порядку, до привязки к элементу:

1. существование и вес (лимит 10 МБ);
2. формат по сигнатуре (magic bytes): PNG / JPEG / WebP; SVG и всё остальное отклоняется;
3. пиксельные размеры и лимит до полного декодирования (максимум 25 Мп, максимум 8000 px по стороне) - защита от декомпрессионных бомб;
4. декодирование и **перекодирование в WebP** со снятием метаданных (EXIF, ICC): убирает polyglot и полезную нагрузку;
5. сохранение вариантов: `display` (длинная сторона <= 1600 px) и `thumb` (<= 400 px);
6. исходный загруженный объект удаляется после успешной обработки - в бакете остаются только перекодированные варианты.

Ключи: `tmp/{uploadId}` для загрузки, `media/{ownerId}/{mediaId}/{variant}.webp` для готовых объектов.

### 4. Выдача

- Видимости набора пока нет (ORG-02), поэтому **всё медиа приватное**: presigned GET с TTL 15 минут, ссылки вычисляются при чтении набора/элемента и возвращаются в ответе (`{ mediaId, url, width, height }`).
- Публичная выдача (публичный URL/CDN из ADR 0018) откладывается до появления видимости: тогда добавим публичный вариант объекта и отдельный домен отдачи.
- `Content-Disposition: inline`, `Content-Type` принудительный - на уровне метаданных объекта и заголовков отдачи.

### 5. Жизненный цикл и чистка

- **Замена:** новая строка `pending` -> обработка -> `ready`; старая помечается `deleted`, её объекты удаляются фоновой задачей.
- **Удаление элемента/набора:** Sets вызывает команду контракта Media (`DeleteMedia(mediaId)`), Media помечает строку `deleted` (свои данные - своим кодом). Сбой вызова не ломает удаление элемента: объект останется до общей чистки.
- **Сироты:** строки `pending` старше 24 часов и объекты `tmp/*` без строки - удаляются фоновой задачей Media.
- Настройки S3 (`Media:S3`: endpoint, region, bucket, ключи) валидируются на старте: отсутствие или неполнота - падение при запуске (как с OIDC).

### 6. Защита от злоупотребления загрузкой

Пять уровней:

1. **POST-policy с `content-length-range`** - размер и тип режет само хранилище, до приёма байт.
2. **Ограничения на `init`**: заявленный размер <= 10 МБ и `content-type` из белого списка проверяются до выдачи политики; лимит одновременных `pending` на пользователя (5); rate limit на `POST /api/media/uploads`.
3. **Lifecycle-правила бакета**: `tmp/*` - удаление через 24 часа, aborted multipart - через сутки. Даже удачная загрузка мусора живёт максимум день. (Нужно проверить поддержку lifecycle в cloud.ru; если недоступно - те же правила реализует фоновая задача Media.)
4. **Фоновая чистка Media**: `pending` старше 24 часов -> удалить объект и строку; `tmp/*` без строки -> удалить.
5. **Наблюдаемость**: ежедневный подсчёт объёма и числа объектов в бакете, счётчик `pending` старше часа, журнал отклонённых загрузок. Порог по объёму - алерт (бюджет бесплатного тира - 15 ГБ).

Почему это важно: без ограничений пятнадцать загрузок по 1 ГБ выедают весь бесплатный тир.

### 7. Ограничения и тесты

- Лимиты: загрузка <= 10 МБ, <= 25 Мп, <= 8000 px по стороне; при нарушении - 400/413 с кодами по ADR 0031.
- Тесты - контейнерные, на реальном cloud.ru (не мок), уникальный префикс `tests/{runId}/` и очистка после прогона; отсутствие кредов - явный провал, не skip.
- Дополнительно: fail-fast конфигурации, юнит-тесты на классификацию формата и лимиты, интеграционные на полный цикл `init -> POST -> confirm -> выдача -> delete`. Проверка policy: загрузка больше 10 МБ отклоняется хранилищем; чужой ключ/чужой `content-type` - тоже.

## Проверено на cloud.ru (spike, 2026-11-10)

Интеграционные тесты `Category=S3` (`App/tests/Tests.Integration/S3SpikeTests.cs`) на реальном бакете:

1. `CreatePresignedPost` работает с endpoint `https://s3.cloud.ru`. **Порядок настройки клиента следующий:** сначала `RegionEndpoint`/`AuthenticationRegion`, потом `ServiceURL` - иначе SDK уходит на `s3.ru-central-1.amazonaws.com`.
2. `content-length-range` действительно ограничивает размер: загрузка больше лимита отклоняется, объект не появляется в бакете.
3. Успешная POST-загрузка cloud.ru отвечает **200**, даже если передан `success_action_status=201`. Поэтому в коде не опираемся на код ответа S3: факт загрузки подтверждается `HEAD` в `confirm`.
4. `ListObjectsV2`, `GetObjectMetadata`, `DeleteObject` и presigned GET доступны с ролями s3.viewer и s3.editor.
5. Браузерная загрузка проверена на этапе клиента. Ключевой вывод: cloud.ru применяет CORS **только к virtual-hosted URL** (`{bucket}.s3.cloud.ru`), а path-style обходит CORS-движок (префлайт 403). Поэтому клиент настраивается **без `ForcePathStyle`** (virtual-hosted), а в настройках бакета нужно явно включить субдомен. CORS-профиль бакета: `POST`/`GET`/`HEAD`, разрешённый `content-type`, экспонированный `ETag`.

## Последствия

- В решении появляется модуль Media и три NuGet-пакета: `AWSSDK.S3` **v4 (4.0.51+)**, `SkiaSharp`, `SkiaSharp.NativeAssets.Linux.NoDependencies`. Версию SDK v4 проверить на совместимость с CPM и на поведение с кастомным endpoint cloud.ru (`ServiceURL` + `RegionEndpoint`).
- Sets больше не содержит медиа-логики: только `media_id` в payload; контракт Media - единственная точка работы с файлами.
- ADR 0017 уточнён: загрузка идёт presigned POST с policy (а не PUT), потому что только policy умеет ограничивать размер на стороне хранилища; presigned GET на выдачу остаётся как в 0017. Тело ADR 0017 не меняется (заморожено), уточнение фиксируется здесь.
- ADR 0018 выполняется полностью, кроме отдачи с отдельного домена/CDN - она приходит вместе с видимостью (ORG-02).
- Появляется CPU-нагрузка на пересжатие: обработка идёт в фоне подтверждения, при массовых загрузках понадобится ограничения.
- Policy генерирует сам SDK: `CreatePresignedPost` / `CreatePresignedPostAsync` появился в AWSSDK.S3 **v4** (релиз 4.0.51.0, июль 2025); в ветке v3 такого метода нет, поэтому без v4 ограничение размера на стороне хранилища недостижимо. Нюанс: при кастомном `ServiceURL` (нужен для cloud.ru) в ранних версиях v4 был `NullReferenceException`, если не задан регион - `RegionEndpoint` указывать обязательно (issue #4003).
- Orphan-объекты возможны (обрыв между загрузкой и `confirm`) - закрываются фоновой чисткой и lifecycle-правилами.
- Тесты перестают быть полностью офлайновыми: прогон с медиа требует сети и валидных ключей cloud.ru.
- Видимость набора (ORG-02) добавит публичную выдачу и домен отдачи - отдельным решением, без переделки модуля.
