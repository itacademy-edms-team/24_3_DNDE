# ADR 0039. Курсорная (keyset) пагинация списков

- **Status:** proposed
- **Date:** 2026-11-12
- **Decision-maker(s):** Aleksandr
- **Owner:** Aleksandr
- **Scope:** Платформа (общее)

## Контекст

Списки в приложении открываются на мобильном клиенте и растут вместе с контентом пользователя: «Мои наборы», затем элементы набора, позже каталог (ORG-03). Нужно на раннем этапе решить, какую пагинацию использовать.

## Рассмотренные варианты

**Вариант 1. Offset-пагинация.** 
- Плюсы:
  - Простая и быстрая в использовании и реализации, поддерживается из коробки большим числом фреймворков и ORM.
  - Навигация по номерам страниц. Пользователь может "пропустить" несколько страниц, перейти на последнюю.
- Минусы: 
  - проблемы с производительностью на глубоких страницах (БД требуется физически пройтись по N записям и пропустить их до нужной страницы);
  - нестабильная выдача при конкурентных изменениях, требует `COUNT` для отображения общего числа доступных страниц пользователю (может быть и преимуществом: можно посчитать общее количество элементов).

**Вариант 2. Keyset (курсорная) пагинация.** Курсор - значения ключей последней строки предыдущей страницы.
- Плюсы: 
  - одинаково быстро работает и для 1-й, и для 10000-й страницы. Используется в бесконечных лентах. 
  - Стабильная выдача при конкурентных изменениях: пагинация как правило идёт по кортежу из нескольких ключей, например (id, created_at, ...). Вставки и удаления показанных строк не будут сдвигать предстоящие страницы.
- Минусы: 
  - нельзя прыгнуть на произвольную страницу, нет общего числа страниц.
  - ключ сортировки должен быть полным и неизменяемым: без уникальности (например, без `id` как дополнительного поля при равных `created_at`) строки на границе страниц могут повториться или потеряться, а правка поля, по которому идёт сортировка, «перетаскивает» строку через курсор.
  - сложнее в реализации в сравнении с вариантом 1.

**Вариант 3. Keyset c подписанным курсором (HMAC).** Защищает от подделки. Отклонено: курсор всё равно применяется только вместе с фильтром по владельцу из контекста запроса, подпись не даёт выигрыша в безопасности и просто добавляет лишние зависимости.

## Решение

### 1. Механика запроса

Сортировка списка - `created_at DESC, id DESC` (для наборов). Курсор - последняя строка предыдущей страницы, запрос идёт сравнением кортежа. Итоговый SQL (его генерирует EF из LINQ-выражения через `EF.Functions.LessThan`):

```sql
SELECT id, owner_id, title, description, created_at, updated_at, deleted_at
FROM sets.sets
WHERE owner_id = @owner_id
  AND deleted_at IS NULL
  AND (created_at, id) < (@cursor_created_at, @cursor_id)
ORDER BY created_at DESC, id DESC
LIMIT @take;
```

- **`id` - обязательное дополнительное уникальное поле для условия сортировки.** Два набора, созданные в одну микросекунду, без второго поля могли бы попасть на обе страницы или исчезнуть между ними.
- **Row comparison, а не `OR`.** PostgreSQL сравнивает кортеж как один ключ и использует индекс; эквивалент `created_at < @c OR (created_at = @c AND id < @i)` планировщик читает хуже. EF Core выражает это через `EF.Functions.LessThan(ValueTuple.Create(set.CreatedAt, set.Id), ValueTuple.Create(cursor.CreatedAt, cursor.Id))` - Npgsql транслирует вызов в `(created_at, id) < (@c, @i)`, поэтому raw SQL для списка не нужен. `Guid` сам по себе сравнивать в LINQ нельзя (у него нет операторов `<`, но можно через CompareTo), сравнение идёт кортежем целиком.
- **Фильтр владельца - часть того же запроса**, иначе курсор стал бы способом читать чужие данные.
- Признак «есть ещё» получается без `COUNT`: запрос выполняется с `LIMIT pageSize + 1`. Если строк пришло больше, чем `pageSize`, следующая страница существует; лишняя строка в ответ не включается и станет первой на следующей странице. Если строк `<= pageSize`, то `nextCursor = null`.

### 2. Индекс

Индекс повторяет фильтр и порядок сортировки:

```sql
CREATE INDEX ix_sets_owner_id_created_at_id
ON sets.sets (owner_id, created_at DESC, id DESC)
WHERE deleted_at IS NULL;
```

Равенство по `owner_id` + упорядоченный хвост дают index scan без сортировки и без чтения чужих строк.

### 3. Формат курсора

Курсор - **непрозрачная строка**: base64url от JSON `{"createdAt": "<ISO-8601 UTC>", "id": "<uuid>"}`. Клиент не разбирает и не собирает курсор, только возвращает полученный `nextCursor`.

- Непрозрачность сохраняет свободу менять состав ключа (например, добавить режим сортировки по `updated_at`) без ломания клиента.
- Время кодируется с точностью до микросекунд - это точность `timestamptz`: тики .NET (100 нс) после круга через БД и JSON дали бы расхождение на границе страниц (дубль или пропуск строки).
- Курсор не подписывается: он бесполезен без `owner_id`, который берётся из контекста запроса, а не из параметров.

### 4. Контракт ответа и ошибок

- Ответ: `{ "items": [...], "nextCursor": "<string>|null" }`; `nextCursor = null` - данных больше нет.
- `pageSize`: 1–100, по умолчанию 20; вне диапазона - 400 с кодом `Set.PageSizeInvalid` и полями `min`/`max` в `Metadata` (ADR 0038).
- Битый или чужой по формату курсор - 400 с кодом `Set.CursorInvalid`; молча начинать с первой страницы нельзя, иначе клиент зациклится на одной странице.
- Общее количество и номер страницы не отдаются: для интерфейса «показать ещё»/бесконечной прокрутки они не нужны.

### 5. Переиспользование

Кодек курсора (`CursorCodec`) и тип страницы (`KeysetPage<T>`) живут в `Common.Application/Pagination`. Модуль описывает свой курсор (для элементов это будет `(position, id)`) и передаёт его в репозиторий; контракт ответа и правила ошибок остаются общими.

## Последствия

- Стоимость страницы не зависит от позиции этой страницы в глубину; список не «дёргается» при вставках и удалениях.
- Строки, оказавшиеся до курсора по порядку, в последующих страницах не появляются: набор, созданный во время прокрутки, попадёт в ленту только после обновления списка сверху. Для «Моих наборов» это ожидаемое поведение, но его нужно иметь в виду при проектировании клиента.
- Нельзя прыгнуть на произвольную страницу и показать «страница 3 из 12» - для мобильного интерфейса это не требуется.
- Порядок списка наборов фиксируется по `created_at`: правка набора не поднимает его наверх. Режим «недавно изменённые» потребует второго индекса (`updated_at DESC, id DESC`) и своего курсора - это отдельное решение, а не расширение текущего.
- Курсор привязан к сортировке: смена ключа сортировки - breaking change контракта, старые курсоры должны отвергаться (`Set.CursorInvalid`).
- Один индекс вместо двух: `ix_sets_owner_id_updated_at` удалён.
