# ADR 0012. Стек бэкенда: C# / .NET

- **Status:** accepted
- **Date:** 2026-10-17
- **Decision-maker(s):** Aleksandr
- **Owner:** Aleksandr
- **Scope:** Платформа (общее)

## Контекст

Бэкенд-контур состоит из нескольких контролируемых нами компонентов: BFF (ADR 0002), MCP-сервер (ADR 0005), доменные сервисы, realtime-узел для матчей (План §4). Для диаграммы контейнеров и дальнейших решений нужен базовый технологический стек, чтобы не выбирать язык под каждый компонент заново.

Разработку и поддержку ведёт один человек с основной компетенцией в C# / .NET.

Речь только о компонентах, которые мы **пишем сами**. Готовое стороннее ПО (Keycloak на Java, СУБД и т.п.) под это решение не попадает, язык там задан вендором.

## Рассмотренные варианты

1. **Полиглот - язык под каждый компонент.** Каждый сервис пишется на том, что для него локально оптимально. Плюс: локальный оптимум по нишам. Минусы: для одного разработчика это распыление: разный тулинг, рантаймы, сборка, отладка; такие системы тяжело обслуживать, тяжелее переиспользование кода и общих библиотек.

2. **Единый стек C# / .NET + исключение для AI/ML.** Все контролируемые бэкенд-компоненты на одном языке. Плюс: один тулчейн и рантайм, переиспользование общих моделей и библиотек, соответствие компетенции владельца, проще поддержка в одиночку. Минус: в нишах, где .NET слабее (прежде всего ML), выбор может быть не оправдан - закрывается введением явного исключением.

## Решение

Все контролируемые нами бэкенд-компоненты пишем на **C# / .NET**.

**Исключение - AI/ML.** Если появится собственный ML-компонент, где Python-экосистема даёт существенный выигрыш, допускается не-.NET реализация. Такой компонент интегрируется как отдельный сервис через API, а не вносится в основной стек. Исключение применяется по обоснованию, а не по умолчанию.

## Последствия

- Стек BFF, MCP-сервера, доменных сервисов и realtime-узла - C# / .NET. Снимает TBD со слотов технологий этих контейнеров на C4-Container.
- Переиспользование доменных моделей, контрактов и библиотек между компонентами за счёт одного языка.
- Текущий AI полностью внешний: генерация наборов - через внешнего агента (ADR 0005), оценка ответов - вызов внешнего LLM по API (ADR 0010). Собственного ML-компонента нет, поэтому **исключение пока не задействовано**; вызовы к ИИ идут из .NET по HTTPS.
- Выбор версии .NET, типа проекта (монолит/сервисы) и конкретных фреймворков - это отдельные ADR.
- Внешние вендоры и готовое ПО не подпадают под решение.
