# ADR 0009. Платёжный провайдер

- **Status:** accepted
- **Date:** 2026-10-16
- **Decision-maker(s):** Aleksandr
- **Owner:** Aleksandr
- **Scope:** Платформа (общее)

## Контекст

Нужен приём оплаты подписки. Что именно монетизируем - это вопрос продуктовый записи (PDR «Монетизация», открытый вопрос §7.2). Здесь же только решаем, **чем принимать платежи**.

Свою платёжную логику и приём карт не пишем: это PCI DSS, безопасность карточных данных и фискализация. Отдаём внешнему платёжному агрегатору. Приём платежей в РФ подпадает под 54-ФЗ (онлайн-касса, чеки) - провайдер должен закрывать фискализацию. Стек проекта - .NET, поэтому важны наличие песочницы и библиотек под .NET.

## Рассмотренные варианты

### Вариант 1: ЮKassa (API / неофициальный SDK YooKassaNet)
Популярный российский агрегатор с развитым API и выделенной песочницей для разработчиков.

- **Плюсы:**
  - Полноценный Sandbox: изолированная тестовая среда, не требующая верификации паспорта или ИНН для генерации ключей.
  - Готовые библиотеки сообщества: стабильный NuGet-пакет (`YooKassaNet`), меньше boilerplate при интеграции на .NET.
  - Документация: качественная, на русском, с примерами REST-запросов и описанием Webhook-уведомлений.
  - Перспектива: при выводе в продакшн сервис предлагает автоматизацию фискализации (чеков) для самозанятых.
- **Минусы:**
  - Нет официального SDK под .NET: интеграция опирается на open-source решения сообщества или ручной маппинг REST API.

### Вариант 2: Robokassa (REST API)
Один из старейших платёжных сервисов в РФ с простой процедурой тестирования.

- **Плюсы:**
  - Простота инициализации: тестовый режим включается флагом `IsTest = 1` в запросе.
  - Интеграция без бэкенда: платёжные ссылки генерируются простыми GET-запросами - удобно для MVP.
- **Минусы:**
  - Устаревший стек SDK: библиотеки под .NET редко обновляются, могут не использовать современные практики, может потребоваться собственная реализация.
  - Сложнее держать чистоту архитектуры: специфичные форматы ответов (MD5-хэширование подписей) требуют дополнительных сервисов-валидаторов.

### Вариант 3: PayAnyWay (REST API)
Российский агрегатор платежей с открытым API.

- **Плюсы:**
  - Стабильное API и прозрачная логика работы с Webhook-уведомлениями.
- **Минусы:**
  - Высокий порог входа: менее развитое .NET-комьюнити, почти весь код для API пишется «с нуля» через `HttpClient`.
  - Интерфейс тестовой среды менее интуитивен для быстрой настройки в сравнении с другими вариантами.

## Решение

Берём **ЮKassa**.

Причины: полноценный sandbox без верификации, стабильный community-пакет `YooKassaNet` (меньше boilerplate на .NET), хорошая русскоязычная документация, путь к фискализации (54-ФЗ) при выводе в прод. Интеграция - размещённая платёжная страница провайдера плюс webhook о статусе платежа (как на C4-Context).

Отсутствие официального .NET SDK принимаем как минус: опираемся на `YooKassaNet` или ручной REST.

## Последствия

- Здесь не рассматривается реализация собственной платёжной логики и хранения карт; PCI DSS (Payment Card Industry Data Security Standard) - забота провайдера.
- Отсутствие официального .NET SDK вынуждает зависеть от community-пакета `YooKassaNet`, либо от ручной реализации HTTP Client, работающего на REST; риск дополнительных накладных расходов в сопровождении пакета.
- Фискализация (54-ФЗ) закрывается провайдером при выводе в продакшн.
- Привязка к API ЮKassa. Смягчается изоляцией: система работает со своим интерфейсом платежей, а код ЮKassa заперт в одном адаптере - смена провайдера затрагивает только его.
- На C4-Context external system «Платёжный провайдер» - это ЮKassa: инициируем платёж, статус приходит webhook-ом.
- Что именно платно - вне этой записи, в PDR «Монетизация» (§7.2).
