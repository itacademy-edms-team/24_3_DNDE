# ADR 0034. Архитектура клиентского SPA: слои, маршрутизация, данные и тесты

- **Status:** accepted
- **Date:** 2026-11-04
- **Decision-maker(s):** Aleksandr
- **Owner:** Aleksandr
- **Scope:** Клиент (Client.Web)

## Контекст

Каркас SPA (C3) собирался под конкретную задачу - вход в аккаунт и просмотр профиля через BFF, - но структура кода и набор решений при этом уже определяют, как будут писаться все следующие экраны и второе веб-приложение (back-office со своим BFF). Решения принимались по официальным гайдам React Router, TanStack Query и Mantine, часть - по опыту эксплуатации в этом же проекте (стили, тесты, отладка).

Ограничения:

- аутентификация - серверная сессия BFF в httpOnly cookie (ADR 0021): клиент не имеет доступа к токенам и не может отрендерить приватную страницу до ответа `/session` (ADR 0032);
- данные сейчас приходят только по HTTP от BFF (`/session`, `/api/**`), поэтому серверного рендера с загрузкой данных у клиента нет;
- ошибки приходят в едином формате ProblemDetails (ADR 0031), и клиент обязан разбирать их одинаково для BFF и домена;
- вход и выход - не запросы из скрипта, а полноценные навигация и отправка формы (ADR 0030);
- интерфейс mobile-first: один SPA на все устройства;
- SPA хостится отдельно от BFF (ADR 0030), домены - в общей зоне (ADR 0033).

## Рассмотренные варианты

### Вариант 1. Feature-sliced слои + React Router data mode + TanStack Query - ВЫБРАН

Структура `src`:

```
app/        каркас: routes, router, providers, layout, globalErrors
pages/      композиция экрана: собирает фичи и раскладку
features/   <домен>/{api, model, ui}: контракты, запросы, компоненты
shared/     api (транспорт, ошибки), ui (общие компоненты)
```

- Каждый домен изолирован: контракты в `model/types.ts`, запросы в `api/`, компоненты в `ui/`. Новый экран - это папка в `features` плюс маршрут в `routes.tsx`, без правок каркаса.
- Маршруты описаны данными (`routes.tsx`), экземпляр роутера - отдельно (`router.tsx`). Тесты строят `createMemoryRouter(routes)`, то есть проверяют то же дерево, что и прод, но без браузерной истории.
- Кэш серверных данных живёт в TanStack Query, локальное состояние - в компонентах. Нет «глобального стора ради глобального стора».
- Транспорт один (axios) и спрятан за `shared/api`: фичи не знают про axios, ошибки получают уже в виде доменного `AppError`.

### Вариант 2. React Router framework mode (файловые маршруты, loaders, SSR) - ОТКЛОНЁН

- SSR бесполезен: данные всё равно запрашиваются у BFF с cookie пользователя, а приватные страницы не рендерятся до ответа `/session`.
- Loaders дублировали бы TanStack Query (кэш, инвалидация, повторные запросы) или конфликтовали с ним.
- Файловая маршрутизация связывает структуру проекта с URL-схемой, что мешает feature-sliced раскладке.

### Вариант 3. Redux Toolkit (+ RTK Query) для состояния и данных - ОТКЛОНЁН на текущем объёме

- Почти всё состояние серверное; клиентского (открытые панели, фильтры) мало - `useState`/`useDisclosure` достаточно.
- RTK Query дублирует TanStack Query; два кэша на одном приложении - лишний источник рассинхрона.
- Решение не догма: `app/providers.tsx` - единственная точка подключения провайдеров, Redux добавляется там без переписывания остального кода. Триггер - сложное клиентское состояние (многошаговые формы, редактор, undo).

### Вариант 4. jsdom + Testing Library - ОТКЛОНЁН

- jsdom не считает layout и не применяет медиазапросы: мобильная раскладка, выезжающий навбар, порядок CSS-слоёв Mantine/Tailwind в нём не проверяются.
- Реальные дефекты этой фазы (навбар, открытый до первого эффекта; кнопки разной ширины в панели) ловятся только в реальном браузере.

### Вариант 5. Персистенция кэша TanStack в `localStorage` - ОТКЛОНЁН

- Сессия и профиль - приватные данные: хранение на диске и показ устаревшего состояния после разлогина недопустимы.
- Синхронный парсинг при инициализации и обвязка `PersistQueryClientProvider` + `useIsRestoring` + условия дегидратации - сложность, не оправданная двумя лёгкими запросами.
- Критерии возврата: офлайн-режим/PWA или тяжёлые списки, кэш которых дорого перезапрашивать. Тогда - отдельная ADR.

## Решение

**Стек.** Vite + React 19 + TypeScript (strict), React Router **data mode**, TanStack Query v5, axios, Mantine для компонентов и темы, Tailwind для утилит и раскладки.

**Слои и файлы.**

- `app/` - каркас: `routes.tsx` (только дерево маршрутов), `router.tsx` (экземпляр `createBrowserRouter`), `providers.tsx` (все провайдеры), `AppLayout.tsx` (AppShell: шапка, навигация), `globalErrors.ts` (единая реакция на утрату сессии).
- `pages/<page>/` - композиция экрана, без собственной бизнес-логики.
- `features/<domain>/` - `model/types.ts` (контракты), `model/*.ts` (чистые функции), `api/*Keys.ts` (ключи кэша), `api/get*.ts` (запросы), `api/use*.ts` (хуки), `ui/` (компоненты фичи).
- `shared/` - `api/clients` (фабрика клиента, `apiClient`, `authClient`), `api/errors` (ProblemDetails → AppError → ErrorView), `ui/` (общие компоненты).
- Один тип - один файл; объявления типов не выносятся в файл с логикой.

**Маршрутизация.** Data mode, но без `loaders`: данные грузят хуки TanStack Query, потому что SSR нет и предзагрузка на сервере невозможна. Внутренние переходы - `<Link>`/`useNavigate`; `href`/`window.location.assign` - только для внешних адресов (вход на BFF). Выход - HTML-форма `POST`, а не fetch.

**Данные.** Ключи кэша - через Query Key Factory (`*Keys.ts`), чтобы `useQuery` и `invalidateQueries` не расходились по строкам. `QueryClient` настраивается в `providers.tsx`: `staleTime: 30_000`, `retry: false`, `refetchOnWindowFocus: false`; глобальные `onError` для запросов и мутаций уходят в `handleGlobalError`.

**Транспорт.** `shared/api/clients/createRestClient.ts` создаёт axios-клиент с `baseURL` из окружения, `withCredentials: true` и **`adapter: "fetch"`** (иначе подмена `fetch` в браузерных тестах не перехватывает запросы). Интерцептор превращает `AxiosError` в `RestApiError` с сохранённым телом problem+json; сетевые ошибки - `status: null`, `retryable: true`. Два клиента: `apiClient` (`/api/**` через BFF) и `authClient` (корень BFF, только `/session`).

**Ошибки.** Чистый слой `ProblemDetails → AppError → ErrorView`: `title` - код (PascalCase), `source` - `bff` | `app` | ..., `detail` - для разработчика, `errors` - по полям формы. UI получает `ErrorView` (`message`, `fieldErrors`, `retryable`, `unauthenticated`) и не знает ни про статусы, ни про транспорт.

**Аутентификация.** Источник истины - `/session` (ADR 0032). `RequireSession` показывает экран ожидания/отказа, а не рендерит приватный контент до ответа; `authRedirectGuard` (счётчик попыток в `sessionStorage`) не даёт уйти в петлю входа, если сессия на BFF жива, а `/session` её ещё не увидел.

**UI.** Mantine (AppShell, Menu, Button и т.д.) и Tailwind сосуществуют через явный порядок CSS-слоёв в `styles/app.css`: `@layer theme, base, mantine, components, utilities` - утилиты Tailwind применяются поверх Mantine, а не наоборот. Тема - в `MantineProvider` (`app/providers.tsx`), не в отдельных файлах-обёртках.

**Алиас.** `@` → `src`: `resolve.alias` в `vite.config.ts` и `paths` в `tsconfig.app.json`. Плагин `vite-tsconfig-paths` не нужен на одном алиасе.

**Тесты.** Только Vitest в browser mode (Playwright/Chromium), viewport `390×844`, `css: true` и общий `src/test/setup.ts`; правила и команды запуска - [конвенции тестирования](../testing-conventions.md).

## Последствия

- Новый экран: `features/<domain>` (при необходимости) + `pages/<page>` + маршрут в `routes.tsx`. AppLayout не трогается.
- Будущий Back-office сможет переиспользовать ту же раскладку слоёв, транспорт и слой ошибок; отличаются origin, BFF и набор фич. Общие части выносятся в пакет, когда появится второй клиент, а не заранее.
- SSR и метатеги не поддерживаются: публичные страницы с индексацией (если появятся) потребуют отдельного решения - пререндер или SSR-хост.
- Персистенция кэша отложена; критерии возврата зафиксированы выше, «на всякий случай» не включается.
- Любое изменение `staleTime`/`retry` затрагивает все экраны: это осознанно централизовано в `providers.tsx`.
- Клиент зависит от двух контрактов BFF: `/session` (ADR 0032) и формата ошибок (ADR 0031).
- Тесты идут в реальном браузере: медленнее jsdom (секунды на файл), зато проверяют настоящий layout и CSS; CI будет обязан ставить Chromium (`npx playwright install chromium`) для воспроизводимости.
