# ADR 0029. Структура решения модульного монолита

- **Status:** accepted
- **Date:** 2026-10-30
- **Decision-maker(s):** Aleksandr
- **Owner:** Aleksandr
- **Scope:** Платформа (общее)

## Контекст

Монолит стартует с одного модуля Accounts (скелет C1), дальше модули растут по карте (docs/ontology/README.md). Стиль задан по ADR 0013. Нужно зафиксировать физическую структуру решения: гранулярность проектов, межмодульные ссылки, использование MediatR, изоляцию данных и контроль границ.

Изучены источники (см. «Источники» ниже): вводная dev.to статья по модульным монолитам, руководство и пошаговая статья Milan Jovanovic по модульным монолитам, шаблон ardalis/CleanArchitecture и локальный пример AspNetModularMonolithExample из руководства Milan'а.

## Рассмотренные варианты

### Вариант 1. Один проект на модуль с папками

Modules/Accounts - один classlib, внутри Domain/Features/Data. Плюсы: минимум проектов, фичи-вертикальные срезы без MediatR. Минусы: слои внутри модуля не выражены ссылками - держатся только дисциплиной; при росте модуля рефактор в проекты болезненнее; добавление MediatR и диспатча доменных событий потом = ретрофит boilerplate.

### Вариант 2. Четыре проекта на модуль, общий Common - ВЫБРАН

Modules/Accounts/{Domain, Application, Infrastructure, Contracts}, cross-module взаимодействие - только через .Contracts, Host ссылается на Infrastructure-проекты модулей. Внутреннее устройство модуля (Clean Architecture) ортогонально модульности (ADR 0013) и здесь выражено ссылками: Domain ни на кого не ссылается, Application - на Domain, Infrastructure - на Application, Contracts - ни на кого из модуля. Правила ссылок контролирует компилятор и архитектурные тесты.

## Решение

Структура решения (папка App/ репозитория):

```
App/
  src/
    Api/                      # Host: Program.cs, конвейер, JwtBearer (ADR 0028),
                              # регистрация модулей, health, --migrate
    Common/
      Common.Application/     # абстракции: Result, маркеры доменных событий - НЕ бизнес-логика
      Common.Infrastructure/  # общая инфраструктура (по мере появления)
    Modules/
      Accounts/
        Accounts.Domain/          # сущности, VO, инварианты;
        Accounts.Application/     # use-cases: команды/запросы, хендлеры, DTO, интерфейсы
        Accounts.Infrastructure/  # DbContext, конфигурации, миграции,
                                  # репозитории, регистрация DI и MediatR
        Accounts.Contracts/       # публичный контракт модуля (интерфейсы, DTO, события)
  tests/
    Tests.Architecture/     # архитектурные тесты
    Tests.Integration/      # сквозные тесты
```

Зависимости проектов: см. Связанные документы, Диаграмма: проекты и ссылки.


Правила:
- **Ссылки**: Domain - ни на кого; Application - Domain + Common.Application + чужие *.Contracts; Infrastructure - Application + Contracts (реализация фасада модуля) + Common.*; Contracts - только Common.Application; Api - Infrastructure-проекты всех модулей (фасады потребляются через DI по интерфейсу, Host на Contracts не ссылается). Между модулями - только X.Contracts (для Accounts пока потребителей нет; Contracts-проект создаётся минимальным).
- **Данные**: schema-per-module (accounts), DbContext на модуль, собственная таблица миграций (__EFMigrationsHistory в схеме модуля); миграции модуля независимы от других.
- **MediatR**: сканирование Application-сборок каждого модуля; доменные события публикуются после успешного SaveChanges в той же операции.
- **Композиция модулей**: статический XModule (AddX/MapX/MigrateX/CanConnectX), как в локальном примере; Host не знает внутренностей модуля.
- **Контроль границ**: архитектурные тесты по образцу локального примера: парсинг csproj на запрещённые ссылки, «публична только композиция модуля», все сущности и FK в своей схеме.
- **Эксплуатация**: --migrate-режим (отдельный job для применения миграций), /health/live и /health/ready (CanConnect по контекстам), TimeProvider в DI.
- **События между модулями**: отложены (см. ontology: без явных сценариев не вводим); outbox - отдельное запланированное решение при первом реальном потребителе.

## Последствия

- Проектов на старте больше, чем в лёгком варианте (~8 вместо ~4), цена за компиляторно-выраженные слои и готовый boilerplate событий.
- Внутри модуля Clean Architecture - деталь реализации модуля (как и заявлено в ADR 0013); наружу модуль виден только через Contracts и композицию.
- Вынос модуля в сервис (ADR 0013) упрощается: Contracts становится API-поверхностью сервиса, Infrastructure - его реализацией.
- Архитектурные тесты роняют сборку при добавлении запрещённой ссылки - контроль границ без ревью-дисциплины.
- YAGNI-ограничение: outbox, межмодульные интеграционные события и второй модуль в скелет не входят.
