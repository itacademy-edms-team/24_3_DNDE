# ADR 0005. MCP-доступ для внешних ИИ-агентов

- **Status:** accepted
- **Date:** 2026-10-16
- **Decision-maker(s):** Aleksandr
- **Owner:** Aleksandr
- **Scope:** Платформа (общее)

## Контекст

Закладываем на вырост работу с внешними ИИ-агентами. У пользователя стоит свой ИИ-ассистент (Kimi, Claude и прочие), которому через MCP-сервер платформы можно поручать работу с контентом: генерировать наборы по материалам пользователя, читать, искать и создавать контент.

По ADR 0002 у каждого класса клиента свой серверный фасад; для агентов это **MCP-сервер**. По ADR 0003 авторизация применяется на доменных сервисах, агент действует делегированными правами пользователя.

Фича **вне 8-месячного горизонта**. Решение нужно зафиксировать заранее, чтобы модель прав и фасадов не ломалась при его появлении.

## Рассмотренные варианты

Аутентификация агента к MCP-серверу:

1. **Классический PAT (персональный токен доступа).** Пользователь генерирует долгоживущий токен (как классические токены GitHub) и добавляет его в агента. Просто в реализации и использовании. Минусы: долгоживущий секрет - плохо для безопасности; отзыв вручную; широкие права на весь аккаунт.
2. **OAuth через Keycloak (device / authorization code).** Агент получает токен от имени пользователя стандартным потоком. Отзываемо, с TTL и refresh, скоупы под конкретные инструменты. Минус: сложнее реализовать, MCP-сервер должен уметь работать по OAuth.
3. **Fine-grained токен.** Тот же bearer-токен, что и PAT, но с узкими правами на конкретные ресурсы/операции и обязательным сроком истечения. Плюсы: наименьшие привилегии (ии агент работает только с разрешённым), встроенный expiry (ротация в модели), отзыв по токену, меньше ущерба при утечке. Минусы: сложнее выдавать и управлять такими токенами, необходимость в поддержке скоуп-модели на платформе; всё ещё bearer-секрет, действует до истечения или отзыва.

## Решение

- **MCP-сервер** - фасад для агентов в контуре системы (контейнер уровня L2). Экспонирует инструменты: чтение, поиск, создание контента, генерация наборов по материалам пользователя.
- Аутентификация агента - **fine-grained токен** (узкие права на ресурс + обязательный срок истечения). PAT-подход (bearer-токен, без OAuth-флоу) остаётся простым и привычным для агентов, а fine-grained модель закрывает его слабые места: узкие скоупы, встроенный expiry, отзыв по токену.
- **Делегирование:** агент действует правами пользователя (ADR 0003), скоупы токена ограничивают доступные инструменты. Прав сверх пользователя и токена агент не получает.
- Авторизация - на доменных сервисах (ADR 0003), как и для остальных фасадов.

## Последствия

- MCP-сервер - новый контейнер (L2), требует обслуживания.
- Реализация вне 8-месячного горизонта; модель закладываем заранее, чтобы не переделывать права и фасады.
- Нужен механизм выдачи, срока истечения и отзыва fine-grained токенов (управление токенами в настройках пользователя).
- Генерацию наборов и работу с ними выполняет сам внешний агент своей моделью: платформа лишь предоставляет инструменты MCP, контент генерирует ИИ-агент.
- Это не решение по собственному LLM для оценки ответов в платформе, для него будет отдельный ADR.
