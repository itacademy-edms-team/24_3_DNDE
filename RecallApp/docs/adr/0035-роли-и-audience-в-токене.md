# ADR 0035. Роли и аудитория в токене: плоский claim roles с префиксом клиента

- **Status:** accepted
- **Date:** 2026-11-10
- **Decision-maker(s):** Aleksandr
- **Owner:** Aleksandr
- **Scope:** Платформа (общее)
- **Уточняет:** [ADR 0020](./0020-провижининг-доменного-пользователя.md), [ADR 0024](./0024-авторизация-client-роли.md), [ADR 0028](./0028-транспорт-личности-bff-монолит.md), [ADR 0032](./0032-контракт-сессии-bff-и-spa.md)

## Контекст

ADR 0024 закрепил роли приложения как client-роли Keycloak (клиент `RecallApp`, роль `app-user`). Пока роли никто не проверял, вопрос их формы в токене не имел последствий. Он появился, когда понадобилось включать связанные с ролями проверки: `.NET`-авторизация читает **плоский** claim - `ClaimsPrincipal.IsInRole` и `[Authorize(Roles = ...)]` смотрят на claim типа `RoleClaimType` и без доработок не разбирают вложенный JSON.

Фактическое состояние access-токена до решения (фрагмент):

```json
"aud": ["RecallApp", "account"],
"realm_access": { "roles": ["default-roles-recallapp", "offline_access", "uma_authorization"] },
"resource_access": {
  "RecallApp": { "roles": ["app-user"] },
  "account":   { "roles": ["manage-account", "manage-account-links", "view-profile"] }
}
```

ID-токен ролей не содержал вообще, а именно из него BFF собирает `ClaimsPrincipal`.

Причина такого состава - дефолты Keycloak, рассчитанные на универсальный resource server:

- client scope `roles` содержит мапперы `realm roles` и `client roles` с **незаданным** `Client ID`. По документации при незаданном `Client ID` будут включены все роли для всех клиентов и этого realm, которые есть у пользователя в этом realm.
- `audience resolve` добавляет в `aud` все клиенты, где у пользователя есть роли;
- `Full scope allowed = ON` (значение по умолчанию для новых клиентов) разрешает ролевым мапперам выводить всё, что есть у пользователя, даже если это не нужно или не используется.

Ограничения, которые нельзя игнорировать:

- **два потребителя одного токена**: BFF (principal из ID-токена) и монолит (валидирует access-токен сам, ADR 0028). Любой маппинг «в коде» пришлось бы держать в двух приложениях;
- **роль-холдеров станет больше одного**: публичное приложение (`RecallApp`), back-office (`RecallAppBackOffice`, свой realm по ADR 0004, но та же модель), в перспективе другие продукты в том же realm;
- имена ролей в Keycloak уникальны **внутри клиента**, между клиентами - нет.

## Рассмотренные варианты

### Вариант 1. Плоский claim `roles` без префикса - ОТКЛОНЁН

Маппер `User Client Role` с `Client ID = RecallApp`, claim `roles`, значения как есть (`app-user`).

- Плюсы: `IsInRole`/`[Authorize(Roles = "app-user")]` работают; нет разбора JSON; читаемо в логах.
- Минусы: нет структурной защиты от коллизий. Как только в одном токене оказываются одинаковые роли двух клиентов, `roles: ["admin"]` перестаёт говорить, чей это `admin` и теоретически позволяет получить доступ к обоим клиентам. Гарантия держится только на дисциплине настройки, а ошибка конфигурации не проявляется ни в логах, ни в тестах - роль просто появляется.

### Вариант 2. Вложенный `resource_access.<client>.roles` + собственный `AuthorizationHandler` - ОТКЛОНЁН

Форма Keycloak остаётся по умолчанию. Реализация: `ClientRoleRequirement(ClientId, Role)` + `AuthorizationHandler`, который парсит claim `resource_access` через `JsonDocument` и ищет роль нужного клиента; политики регистрируются явно (`AddPolicy("BillingAdmin", ... new ClientRoleRequirement("billing-service", "admin"))`).

- Плюсы: коллизии невозможны структурно; формат совпадает с Keycloak-стандартом; явное указание клиента в каждом требовании.
- Минусы: `IsInRole` и `[Authorize(Roles = ...)]` недоступны **навсегда** - вся авторизация обязана идти через policy, и разработчик, написавший `[Authorize(Roles = "app-user")]`, получит неожиданный 403; разбор JSON на каждый чек (кеширование, обработка `JsonException`); роль не видна в стандартных инструментах (метрики, трассировки); реализацию нужно продублировать в BFF и в монолите (сейчас разные решения, нет общей библиотеки), а расхождение поведения между ними не проявится до продакшена; решение **необратимо** - отказ от него означает переписать все проверки.
- Отдельно: вариант технически работоспособен, отклонён не по качеству кода, а по критерию цены ошибки и обратимости.

### Вариант 3. Плоский claim `roles` с префиксом клиента (`Client Role prefix`) - ВЫБРАН

У маппера `User Client Role` в Keycloak есть штатное поле `Client Role prefix`. Заданное там значение подставляется в начало каждой роли, форма claim'а остаётся плоской. Для префикса=ClientId + ":":

```json
"roles": ["RecallApp:app-user"]
```

- Плюсы: коллизии структурно невозможны (имя роли пространственно именовано); `RoleClaimType` и `IsInRole` работают, кода не требуется вообще; один BFF может безопасно обслуживать несколько роль-холдеров; роль видна в логах как есть; маппинг живёт только в Keycloak - один источник правды для BFF и монолита; обратимо (префикс - поле маппера).
- Минусы: в атрибутах появляется префикс (`[Authorize(Roles = "RecallApp:app-user")]`), поправимо вынесением в константу и другими прикладными решениями.

## Проверка на реальном Keycloak (эксперимент)

Конфигурация менялась пошагово, после каждого шага снимался дамп токенов (`GET /debug/keycloak/tokens`):

| Состояние конфигурации | access-токен | ID-токен |
|---|---|---|
| Исходное: `FSA = ON`, встроенный `roles` | `aud: [RecallApp, account]`, `resource_access: {RecallApp, account}`, `realm_access` | без ролей |
| `Full scope allowed = OFF` | ни `aud`, ни `resource_access`, ни `realm_access` | без ролей |
| + client scope `recallapp-roles` с маппером, встроенный `roles` ещё подключён | скоуп виден в `scope`, claim `roles` отсутствует | без ролей |
| + `Assign role` (`RecallApp/app-user`) в `Bff.Web-dedicated -> Scope` | `roles: [app-user]`, `aud: RecallApp`, `resource_access` ушёл | `roles: [app-user]` |
| + `Client Role prefix = RecallApp:` и маппер `Audience` | `roles: [RecallApp:app-user]`, `aud: RecallApp` | `roles: [RecallApp:app-user]`, `aud: Bff.Web` |

Выводы, которые иначе пришлось бы принимать на веру:

- **role scope mappings фильтруют и собственный маппер**: без `Assign role` роли не появляются - молча, без ошибок и предупреждений;
- при `FSA = OFF` встроенные мапперы `roles` **немы**, поэтому «оставить дефолтный скоуп и просто выключить FSA» - ловушка, а не компромисс;
- `audience resolve` исчезает вместе с `aud`: аудиторию нужно задавать явно;
- роли попадают в ID-токен только при `Add to ID token = ON` (у встроенных мапперов - OFF), иначе `IsInRole` в BFF остаётся мёртвым при формально «настроенном» маппинге;
- refresh перевыпускает и ID-токен (роли доехали без повторного входа), но cookie-тикет BFF хранит **снимок** claims на момент входа: `IsInRole` в BFF оживает только после нового логина.

## Решение

**Маппинг в Keycloak, по client scope на роль-холдер.** Для `RecallApp` - скоуп `recallapp-roles`:

- маппер `User Client Role`: `Client ID = RecallApp`, `Token Claim Name = roles`, `Client Role prefix = RecallApp:`, access token **и** ID token, остальные каналы (lightweight, userinfo, introspection) - OFF;
- маппер `Audience`: `Included Client Audience = RecallApp`, access token; в ID-токене audience остаётся `Bff.Web`;
- скоуп подключён к `Bff.Web` как **Default**; в `Bff.Web-dedicated -> Scope` выдано разрешение на роль `RecallApp/app-user`; `Full scope allowed = OFF`; встроенный `roles` снят с `Bff.Web`.

**Соглашения.**

- Префикс роли **равен `Client ID`** буквально: `RecallApp:app-user`, `RecallAppBackOffice:bo-admin`. Никаких выдуманных доменных неймспейсов: соответствие «префикс = клиент» проверяется глазами.
- Префикс - часть контракта: в коде роль берётся из константы (`AppRoles.AppUser = "RecallApp:app-user"`), литерал в атрибуте запрещён; формат покрывается тестом.
- Новый роль-холдер: свой client scope, свой маппер с префиксом, своё `Assign role`. Смешивать мапперы разных клиентов с одним префиксом нельзя.

**Проверка в приложениях.**

- BFF: `RoleClaimType = "roles"`, роли читаются из `ClaimsPrincipal` (он собран из ID-токена).
- Монолит: `RoleClaimType = "roles"`, `ValidateAudience = true`, `ValidAudience` из `Oidc__Audience` (= `RecallApp`). Отключение проверки audience из ADR 0028 было вынужденным (`aud = account`); теперь аудитория задаётся явным маппером, и проверка включена.

**Источник claims — ID-токен.** BFF собирает `ClaimsPrincipal` из ID-токена (`GetClaimsFromUserInfoEndpoint = false`): все нужные claims (`sub`, `name`, `email`, `email_verified`, `roles`) приходят в нём, а отдельный запрос к userinfo — дополнительная точка отказа на входе без пользы. Отсюда обязательное требование к мапперам: «Add to ID token» включён (у встроенных мапперов Keycloak он по умолчанию выключен, что уже приводило к молчаливому отсутствию ролей). Userinfo задействуем, когда ID-токен станет тяжёлым для сетевых запросов: тогда включаем `Add to userinfo` у нужных мапперов и `GetClaimsFromUserInfoEndpoint` в BFF.

**Итоговый контракт токенов.**

```json
// access
"aud": "RecallApp",
"roles": ["RecallApp:app-user"]   // без resource_access и realm_access

// id
"aud": "Bff.Web",
"roles": ["RecallApp:app-user"]
```

## Последствия

- Роли приложения читаются единообразно в BFF и монолите, без кода на разбор вложенных структур; `[Authorize(Roles = ...)]` и `IsInRole` доступны.
- Состав токена перестал зависеть от посторонних клиентов realm: добавление нового роль-холдера не расширяет наши токены автоматически. Роли Keycloak (`default-roles-*`, `uma_authorization`, `offline_access`) в приложение не попадают.
- Аудитория токена управляемая и валидируется; несколько значений `aud` поддержаны штатно (проверка на вхождение), поэтому появление, например, `aud: [RecallApp, RecallAppRealtime]` не ломает монолит - решение о таком расширении принимается отдельно.
- Роли в `ClaimsPrincipal` - снимок на момент входа: смена ролей в Keycloak доезжает до BFF только со следующим логином. Для монолита ограничения нет - он читает роли из access-токена (который обновляется refresh'ем).
- Клиенту роли по-прежнему не передаются (ADR 0032); клиентская авторизация строится на ответах API.
- Регрессия в конфигурации realm не ловится модульными тестами: стражи покрывают типы claim'ов и разбор principal, а сам маппинг проверяется интеграционным тестом категории `Keycloak` - когда появится первая ручка с требованием роли.
- Escape hatch: если появится потребитель, которому нужен каноничный для Keycloak вложенный формат, в тот же скоуп добавляется **второй** маппер (`Token Claim Name = resource_access.<client>.roles`). Плоский `roles` остаётся для .NET-проверок; существующий код не меняется.
- Token Exchange остаётся будущим решением (ADR 0028): исходный токен обменивается на токен с аудиторией конкретного сервиса, каждый сервис валидирует свою аудиторию своим `JwtBearer`. Решение по TE принимается отдельной записью; текущая форма ролей ей не противоречит.
- Связанные диаграммы и документы актуализируются: `docs/bff-manual-tests.md`, `docs/bff-tests-coverage-status.md`, `docs/ontology/accounts.md`.
