# ADR 0002. Backend For Frontend (BFF) для веб-клиентов

- **Status:** proposed
- **Date:** 2026-10-16
- **Decision-maker(s):** Aleksandr
- **Owner:** Aleksandr
- **Scope:** Платформа (общее)

## Контекст

Платформа web-first, фронтенд — SPA, адаптив (План §4.5). Фронтов два: публичное приложение и служебное (back-office). Аутентификация идёт через Keycloak по OIDC (ADR 0001), фронту нужно ходить к API от имени пользователя.

Если SPA хранит токены в браузере (память, `localStorage`), они доступны JS и уязвимы к краже при XSS. Особенно нежелателен refresh-токен в браузере. Нужен безопасный способ держать сессию фронта и доступ к API.

## Рассмотренные варианты

1. **Токены в браузере (public SPA-клиент, Authorization Code + PKCE).** SPA сам ведёт OIDC и хранит токены. Просто, без лишних компонентов. Но токены доступны JS — риск кражи при XSS, refresh-токен в браузере особенно рискован.
2. **BFF (Backend For Frontend).** Серверный компонент на каждый фронт проводит OIDC, хранит токены на сервере, браузеру отдаёт httpOnly secure session-cookie. Токены вне JS. Фронт ходит на свой BFF, тот проксирует к сервисам с токеном. Минус: дополнительный компонент и серверное сессионное состояние.

## Решение

Вводим **BFF на каждый веб-фронт**: публичный BFF и BFF служебного приложения.

- BFF — OIDC-клиент Keycloak (Authorization Code + PKCE), хранит access/refresh-токены на сервере, браузеру отдаёт httpOnly secure session-cookie.
- Фронт общается только со своим BFF; BFF проксирует запросы к доменным сервисам, прикладывая токен.
- Не-браузерные клиенты (внешний MCP-агент) ходят к API напрямую, минуя BFF, со своим токеном.

## Последствия

- Токены не попадают в браузер — XSS их не крадёт.
- Два BFF = два контура доступа (публичный / служебный), совпадает с моделью из [Роли и доступ](../../24_3_DNDE.wiki/RecallApp-Роли-и-доступ.md).
- Дополнительные компоненты: BFF надо разворачивать и хранить сессии.
- На C4 BFF — контейнеры уровня L2 (по одному на фронт), не внешние системы.
- Cookie-сессия требует защиты от CSRF (SameSite + anti-CSRF).
- BFF может делать грубую проверку (аутентифицирован, глобальная роль), но тонкая авторизация — на сервисах, так как MCP-агент BFF минует. Детали — ADR 0003 (авторизация).
