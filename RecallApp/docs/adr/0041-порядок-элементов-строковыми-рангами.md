# ADR 0041. Порядок элементов набора строковыми рангами

**Статус:** accepted
**Дата:** 2026-11-18

## Контекст

До этого решения позиция элемента была плотным целым числом `0..n-1` внутри набора:

- вставка в середину и удаление требовали сдвига всех последующих элементов;
- частичный уникальный индекс `(set_id, position)` не позволял менять позиции «на месте», поэтому запись шла двухфазно (`position += ShiftOffset`, затем целевые значения) через `ExecuteUpdate`;
- домен вычислял назначения (`SetOrdering.ForInsert/ForRemoval/Assign`), а инфраструктура писала их в обход закрытого сеттера `Element.Position`;
- API перестановки принимал полный список id (`PUT /elements/order`), проверяя состав через 409 `OrderMismatch`.

Следствия: обход инкапсуляции держался соглашением; на одну вставку уходило N UPDATE; доменный метод `Element.MoveTo` существовал, но не использовался.

## Решение

Позиция - строковый ранг (fractional indexing, алгоритм LexoRank):

- между любыми двумя рангами всегда вычисляется третий, поэтому вставка и перестановка меняют одну строку;
- ранги сравниваются порядково и хранятся в `text COLLATE "C"` - побайтовая сортировка совпадает с порядком рангов;
- новый элемент получает ранг после последнего (конец набора);
- перестановка - по соседям: `POST /api/sets/{setId}/elements/{elementId}/move` с `{ previousId, nextId }`; `prev`/`next` могут быть `null` - граница набора;
- `PUT /elements/order` и правила `Assign`/`ForInsert`/`ForRemoval` удалены: один контракт на перестановку;
- двухфазная запись и обход сеттера больше не нужны: `Element.MoveTo(rank)` + `SaveChanges` - обычный путь записи;
- уникальный индекс `(set_id, position) WHERE deleted_at IS NULL` сохранён: при конкурентной вставке в тот же интервал база вернёт конфликт, а не сломает порядок.

Реализация алгоритма - пакет `Innoloft.LexoRank` (MIT), адаптер `IPositionGenerator` живёт в Infrastructure, домену только интерфейс.

## Последствия

- Вставка - один INSERT; перестановка - один UPDATE. Плотная нумерация исчезла: в порядке остаются «дырки», это нормально.
- Идемпотентность `move` не требует ключа: вычисление середины детерминировано, повтор с теми же соседями даёт тот же ранг, а изменившиеся соседи дают ошибку (`Element.OrderNeighbourNotFound`/`OrderInvalid`).
- Клиент пересылает соседей, а не полный список; DnD блокируется на время запроса.
- `position` больше не отдаётся в API: в постраничной выдаче абсолютный индекс не определён, а клиенту он не нужен.
- Миграция пересчитывает существующие строки в `0|000001:`-ранги в текущем порядке.
- **Отложено:** фоновая перебалансировка длинных рангов (при больших объёмах) и доменный лимит числа элементов в наборе - техдолг.
