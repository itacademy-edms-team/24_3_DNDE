# ADR 0023. Владение флоу аутентификации

- **Status:** accepted
- **Date:** 2026-10-23
- **Decision-maker(s):** Aleksandr
- **Owner:** Aleksandr
- **Scope:** Платформа (общее)

## Контекст

Фронтенд написан на React SPA (ADR 0011). Удостоверение идёт через BFF как confidential-клиент по потоку Authorization Code + PKCE (ADR 0002): SPA инициирует вход, браузер редиректится в Keycloak, после аутентификации возвращается с кодом, BFF меняет код на токены. Нужно зафиксировать, кто владеет экранами аутентификации - где человек вводит креды и проходит регистрацию, подтверждение email, сброс пароля, соц-вход.

## Рассмотренные варианты

### Вариант 1. Хостовые страницы Keycloak - ВЫБРАН

Keycloak отдаёт страницы входа, регистрации, сброса и подтверждения. BFF редиректит браузер на Keycloak, человек аутентифицируется там, возвращается с кодом.

- **Плюсы:**
  - Штатный Authorization Code + PKCE, на который уже завязан ADR 0002.
  - Пароль не касается нашего SPA и BFF - остаётся в Keycloak. Ключевой выигрыш BFF/OIDC сохранён.
  - Регистрация, подтверждение email, сброс пароля, MFA, соц-вход (ADR 0022) работают из коробки, своей реализации не требуют.
  - Минимум кода на нашей стороне.
- **Минусы:**
  - Вход - full-page редирект на страницу Keycloak, а не экран внутри SPA. Для SPA это штатно.
  - Внешний вид страниц ограничен моделью тем Keycloak; брендинг потребует переноса своей темы.

### Вариант 2. Собственные React-формы (Keycloak как API) - отклонён

SPA рисует свои формы и шлёт креды в Keycloak сам, без редиректа на его страницы.

- Пароль проходит через наш фронт и BFF - мы берём на себя обращение с паролем, теряя ключевое преимущество выбранной модели.
- Ломает поток Authorization Code + PKCE из ADR 0002. Direct Grant (Resource Owner Password) для браузерных приложений - анти-паттерн, плохо дружит с соц-входом, MFA и required-actions.
- Пришлось бы заново реализовать регистрацию, подтверждение email, сброс, соц-вход против API Keycloak - то, что он уже делает безопасно.

## Решение

Экранами аутентификации владеет **Keycloak через хостовые страницы**. Поток остаётся Authorization Code + PKCE с редиректом (ADR 0002). Это распространяется и на публичное приложение, и на back-office (realm персонала, ADR 0004).

- Регистрация, подтверждение email (ADR 0019), сброс пароля, соц-вход через Яндекс (ADR 0022) идут на хостовых страницах Keycloak.
- React SPA владеет всем интерфейсом **после** входа. Экраны аутентификации в SPA не воспроизводятся.

Брендинг и кастомизация хостовых страниц под фирменный стиль (логотип, цвета, вёрстка темы) выносятся в **отдельную запись**, которая будет написана позже. Текущая запись фиксирует только владение флоу, не оформление.

## Последствия

- Пароль не попадает в наш код; граница доверия для аутентификации - Keycloak.
- Вход и регистрация реализуются конфигурацией Keycloak, не фронтом; экономия кода и переиспользование проверенных флоу.
- UX входа - редирект на страницу Keycloak; внутри SPA экранов auth нет.
- Внешний вид по умолчанию - стандартная тема Keycloak до появления своей. Кастомизация - отдельной записью.
- Back-office использует тот же подход.
