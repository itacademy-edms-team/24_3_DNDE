# ADR 0025. Фреймворк и библиотеки для BFF

- **Status:** proposed
- **Date:** 2026-10-23
- **Decision-maker(s):** Aleksandr
- **Owner:** Aleksandr
- **Scope:** Платформа (общее)

## Контекст

BFF выбран как паттерн (ADR 0002): confidential OIDC-клиент, поток Authorization Code + PKCE, токены на сервере, клиенту httpOnly-cookie с сессией. Фронт на React SPA (ADR 0011), стек бэкенда - C#/.NET (ADR 0012). Нужно решить, на чём строить сам BFF: взять готовый фреймворк (Duende.BFF) или собрать свой на ASP.NET Core.

Выбор упирается в лицензию и в то, кто берёт на себя нетривиальные части (управление токенами, гонки refresh).

## Рассмотренные варианты

### Вариант 1. Свой BFF на ASP.NET Core - ВЫБРАН

OIDC-аутентификация через `Microsoft.AspNetCore.Authentication.OpenIdConnect`, cookie-аутентификация для сессии, YARP как reverse-proxy к доменным сервисам.

- **Плюсы:**
  - Полностью OSS, без лицензионных ограничений и платы.
  - Контроль над поведением: управление токенами, сериализация refresh, logout.
  - Ложится на уже выбранный стек C#/.NET.
- **Минусы:**
  - Нетривиальные части пишем и сопровождаем сами: согласованный refresh токенов при параллельных запросах, back-channel logout, обращение с токенами.
  - Больше своего кода, чем у готового фреймворка -> больше обслуживаемых нами элементов с нашей стороны.

### Вариант 2. Duende.BFF - отклонён

Готовый BFF-фреймворк от Duende.

- Продакшн требует платной лицензии (планы Lite/Standard/Advanced).
- Trial-режим ограничен максимумом пять сессий на хост, попытки сверх - ошибки в логах. Для реального многопользовательского MVP не подходит.
- Бесплатный Community Edition по документации покрывает IdentityServer, а не BFF.
- Управление токенами у Duende.BFF опирается на `Duende.AccessTokenManagement`, продукт с отдельной лицензией от того же постащика.
- Для бесплатного учебного MVP лицензионный риск перевешивает экономию кода.

## Решение

Строим **свой BFF на ASP.NET Core**. Стек: `Microsoft.AspNetCore.Authentication.OpenIdConnect` для входа, cookie-аутентификация для сессии, YARP как reverse-proxy к доменным сервисам.

Покрытие требований:
- Confidential-клиент и Authorization Code + PKCE (ADR 0002) - через OIDC-middleware.
- Серверное хранилище сессии за абстракцией, in-memory на MVP (ADR 0021).
- httpOnly secure cookie с сессией, CSRF-защита.
- Редирект на хостовые страницы Keycloak (ADR 0023), BFF их не подменяет.
- Роль api-gateway: проксирование к монолиту через YARP.
- **Согласованный refresh токенов:** параллельные запросы одной сессии не должны запускать несколько refresh одновременно (ротация refresh-токена рвёт гонку). Сериализуем refresh на сессию (семафор по ключу сессии) либо используем reuse refresh-токенов.

## Последствия

- Нет лицензионной платы и риска; стек OSS.
- Согласованность refresh, logout и обращение с токенами - наша ответственность и наш код, покрываются тестами.
- Кода больше, чем с готовым фреймворком; взамен полный контроль.
- Гонки refresh и прочие тонкости переносятся из прошлого опыта осознанно; инфраструктурные тонкости развёртывания (issuer/hostname в docker, dev-TLS) - в ADR 0026.
- При необходимости later переход на другой BFF-фреймворк не затрагивает доменный слой: BFF изолирован как фасад (ADR 0002).
