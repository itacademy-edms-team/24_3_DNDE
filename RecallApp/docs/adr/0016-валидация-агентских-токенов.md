# ADR 0016. Валидация агентских токенов

- **Status:** proposed
- **Date:** 2026-10-20
- **Decision-maker(s):** Aleksandr
- **Owner:** Aleksandr
- **Scope:** Платформа (общее)

## Контекст

По ADR 0005 внешний ИИ-агент аутентифицируется к MCP-серверу **fine-grained токеном**. ADR 0005 фиксирует *что* за токен, но не *как* он проверяется: в каком формате хранится и по какому пути MCP-сервер устанавливает за токеном пользователя и скоупы. Тело 0005 заморожено (`accepted`), поэтому данную деталь выносим в эту запись.

MCP-сервер - это отдельный контейнер (ADR 0005), не имеющий своей БД. Данные домена и хранилище токенов лежат в модульном монолите с одной БД (ADR 0013, ADR 0015). Агентский поток отделён от пользовательского: пользователей выдаёт и проверяет Keycloak (ADR 0001), агентские токены - платформенные (OAuth-поток через Keycloak для них отклонён в ADR 0005).

Нужно определиться с двумя проблемами: какой взять формат токена и как его проверять.

## Рассмотренные варианты

### Формат токена

1. **Opaque (reference) токен.** Случайная строка без содержимого; смысл резолвится по хранилищу: `токен -> (пользователь, скоупы, срок)`. Плюс: **мгновенный отзыв** - удаление записи сразу убивает токен. Минус: чтение хранилища на каждый запрос.
2. **JWT (подписанный платформой).** Самодостаточный токен со скоупами внутри, проверяется верификацией подписи без обращения к хранилищу. Плюс: stateless-проверка, лучше масштабируется. Минус: отзыв даётся тяжело. Самодостаточный токен нельзя погасить на стороне сервера, он действителен, пока не истечёт. Отзыв до истечения требует либо denylist отозванных токенов (а это снова состояние, ради отказа от которого JWT и берут), либо короткого TTL (он лишь сокращает окно, но не отзывает по требованию). Так требование отзыва из ADR 0005 закрывается плохо.

### Путь проверки

1. **Через монолит (introspection-вызов).** MCP-сервер просит монолит разрешить токен и вернуть `(пользователь, скоупы)`. Плюс: хранилище токенов инкапсулировано в модуле доступа монолита, обращение через контракт (ADR 0013); MCP остаётся тонким. Минус: сетевой вызов на каждый запрос.
2. **Напрямую в БД.** MCP-сервер сам читает token-store из БД монолита. Плюс: на один шаг передачи данных меньше. Минусы: появляется ребро `MCP -> БД`; MCP лезет в чужую схему в обход контракта модуля - нарушение изоляции (ADR 0013); два контейнера завязываются на одной БД, миграция схемы потребует актуализации обоих контейнеров.

## Решение

- **Формат - opaque токен** (вариант 1): даёт мгновенный отзыв, которого требует ADR 0005.
- **Путь - через монолит** (вариант 3): MCP-сервер вызывает монолит для резолва токена в `(пользователь, скоупы)`. Хранилище токенов живёт в модуле доступа монолита; MCP к БД напрямую не ходит.
- После резолва запрос идёт к доменным сервисам с `(пользователь, скоупы)`; авторизация - на сервисах (ADR 0003), эффективные права = права пользователя ∩ скоупы токена.
- Резолв кэшируется на срок жизни токена, чтобы не перегружать монолит запросами на каждый вызов.

## Последствия

- C4-Container диаграмма остаётся без изменений.
- Отзыв токена - мгновенный (одно удаление записи в token-store).
- MCP-сервер остаётся тонким фасадом без доступа к БД; границы модулей и единая БD целы (ADR 0013, ADR 0015).
- Монолит несёт модуль доступа: хранение, выдачу, срок истечения, отзыв и резолв opaque-токенов (конкретизирует «скоуп-модель на платформе» из ADR 0005).
- Кэш резолва на TTL: отозванный токен может прожить в кэше до конца TTL - срок кэша держим коротким, чтобы окно отзыва было малым.
- Пользовательский поток (Keycloak, ADR 0001) не затронут: это отдельная система токенов.
