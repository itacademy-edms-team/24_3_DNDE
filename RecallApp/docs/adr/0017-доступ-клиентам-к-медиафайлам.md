# ADR 0017. Доступ клиентам к медиафайлам

- **Status:** proposed
- **Date:** 2026-10-20
- **Decision-maker(s):** Aleksandr
- **Owner:** Aleksandr
- **Scope:** Платформа (общее)

## Контекст

Медиа элементов лежит в объектном S3-совместимом хранилище (ADR 0008). Доступ к объектам из хранилища требует ключей, которые есть только у монолита, они не должны попадать на клиент по соображениям безопасности.

Сейчас храним только **изображения**. Аудио и видео заложены как будущее расширение.

Нужно решить, как клиент (сейчас веб-SPA, в будущем возможны не-web клиенты по ADR 0002) загружает и скачивает медиа. Часть медиа приватна (черновики, непубличные наборы), а часть публична (медиа опубликованного набора).

## Рассмотренные варианты

### Вариант 1. Проксирование через монолит

Файл проходит через монолит: при скачивании монолит читает объект из хранилища и отдаёт клиенту, при загрузке - принимает объекты от клиента и кладёт в хранилище. Клиент хранилище не видит.

- **Плюсы:**
  - Хранилище полностью закрыто, у него нет доступного клиенту сетевого endpoint, ключи не покидают монолит.
  - Единая точка контроля: монолит видит каждый запрос, может на лету проверять права, применять бизнес-правила, логировать и считать доступ.
  - Клиент максимально прост - обычный HTTP к своему API, без работы с подписями и TTL.
- **Минусы:**
  - Монолит становится посредником: каждый байт каждой загрузки и скачивания проходит через него, повышая нагрузку на трафик, CPU и память на буферизацию/стриминг.
  - Плохо масштабируется на крупные файлы и множество параллельных передач (видео/аудио на вырост).
  - Долгие передачи занимают соединения и воркеры приложения: на медленных клиентах это становится значимой проблемой.
  - Двойной сетевой трафик (хранилище -> монолит -> клиент) и, как правило, двойная оплата за него.

### Вариант 2. Presigned URL

Монолит своими ключами подписывает короткоживущую ссылку на конкретный объект и действие (GET или PUT), клиент работает с хранилищем напрямую по этой ссылке.

- **Плюсы:**
  - Монолит не работает посредником в обычном смысле, он только выдаёт ссылку, нагрузка на него минимальна и не зависит от размера файла.
  - Прямой канал клиент <-> хранилище, хорошо масштабируется на крупные файлы и параллельные передачи.
  - Клиенто-независимость: подписанная ссылка - это HTTPS-URL, работает из браузера, мобильного и десктоп-клиента, любого HTTP-клиента.
  - Ограничения можно вшить прямо в подпись (макс. размер, content-type, фиксированный ключ объекта), а хранилище само его отклонит в случае чего.
  - Плата за трафик считается один раз (хранилище -> клиент), без лишнего прогона через приложение.
- **Минусы:**
  - Нужен механизм подписи, выдачи и TTL - реализация сложнее, чем прямой прокси.
  - Хранилище должно иметь сетевой endpoint, доступный клиенту; спрятать его в приватную сеть нельзя.
  - Окно доступа по ссылке: пока TTL не истёк, объект доступен любому, у кого есть ссылка.
  - Монолит не участвует в самой передаче, поэтому факт и корректность загрузки подтверждаются отдельным шагом.
  - Логику на каждый запрос и детальное логирование доступа применять труднее - в момент передачи монолита в цепочке нет.

### Вариант 3. Публичная ссылка / CDN

Объект отдаётся по постоянному публичному URL, при желании через CDN с кэшированием на краю.

- **Плюсы:**
  - Максимально просто и быстро для публичного контента; CDN поглощает нагрузку и даёт низкую задержку географически распределённым пользователям.
  - Нулевая нагрузка на монолит и минимальная на хранилище под популярный контент.
- **Минусы:**
  - Нет контроля доступа: ссылка постоянная и открыта всем, для приватного медиа не годится.
  - Отзыв и инвалидация сложны - кэш CDN и уже разошедшиеся ссылки живут своей жизнью.
  - При смене приватности (набор опубликовали или скрыли) нужно управлять переключением публичного и приватного доступа к объекту.
  - CDN вводит дополнительную инфраструктуру со своей стоимостью.

## Решение

Комбинируем по типу медиа:

- **Загрузка медиа** (при создании или редактировании элемента) - **presigned PUT** (вариант 2): клиент льёт файл напрямую в хранилище по подписанной ссылке. В подпись вшиваются ограничения (макс. размер, content-type, фиксированный ключ объекта).
- **Приватное медиа** (черновики, непубличные наборы) - **presigned GET** (вариант 2): короткоживущая подписанная ссылка после проверки прав на стороне монолита.
- **Публичное медиа** (опубликованный набор) - **публичная ссылка / CDN** (вариант 3): доступ открыт всем, и ограничений обычно не нужно.

Проксирование (вариант 1) не берём как основной путь из-за проблем обработки больших файлов, которые закладываются, как возможные в будущем.

Ссылки одписывает монолит (ключи хранилища только у него). Клиент за ссылкой обращается через свой фасад: браузер через BFF -> монолит, внешний агент через MCP (ADR 0005).

## Последствия

- На C4-Container появляется прямая связь `веб-клиент -> объектное хранилище` (GET/PUT по presigned и чтение публичных ссылок), в дополнение к `монолит -> хранилище` (подпись ссылок, управление объектами).
- Монолит не является посредником для медиа.
- Подход развязан от типа клиента: будущие не-web клиенты (ADR 0002) могут использовать тот же механизм.
- Нужен механизм выдачи presigned-ссылок с коротким TTL и ограничениями в подписи (размер, content-type, ключ).
- Проверка факта загрузки и привязка объекта к элементу - на монолите после заливки (до подтверждения объект orphan). Безопасность загружаемого контента - отдельная запись (ADR 0018).
- Публичное и приватное медиа разделяются по способу отдачи - это должно быть учтено при хранении и выдаче ссылок.
