# ADR 0015. Выбор базы данных для модульного монолита

- **Status:** proposed
- **Date:** 2026-10-20
- **Decision-maker(s):** Aleksandr
- **Owner:** Aleksandr
- **Scope:** Платформа (общее)

## Контекст

Модульному монолиту (ADR 0013) для хранения сущностей нужно хранилище. Считаем, что монолит представляет собой **один контейнер** с одной БД. Каждый модуль по отношению к другим изолирован и предоставляет доступ через публичные интерфейсы.

Модель данных двойственна (План §2). В ней одновременно живут две разные по природе части, и выбор БД должен закрыть обе.

**Реляционная часть.**
Большинство сущностей связаны ссылками: Набор принадлежит Пользователю и содержит много Элементов (1-N); Группа наборов объединяет Наборы; Учебная группа связывает многих Пользователей с многими Наборами (N-N); SRS-запись ссылается на конкретный Элемент; Сессия относится к Пользователю и Набору; Матч объединяет Игроков и Команды.

Отсюда три требования, которые естественны для реляционной модели:
- **Запросы по связям.** «Все наборы пользователя», «элементы набора», «лидерборд матча», «что пора повторить по SRS» - это join'ы по внешним ключам. Без нормальных связей каждый такой запрос превращается в ручную сборку из нескольких выборок.
- **Ссылочная целостность.** Удалили набор - его элементы и SRS-записи не должны остаться «висеть» в никуда. Это каскады и внешние ключи, которые реляционная БД гарантирует сама.
- **Транзакции.** Прогон Сессии за один коммит обновляет Результаты проверки и SRS-записи сразу нескольких элементов. Либо применяется всё, либо ничего. Это тот самый инвариант, которым был обоснован отказ от распределёнки на текущем этапе (ADR 0013).

**Документная.**
Элемент набора самодостаточен, и у каждого типа свой набор полей и свой способ проверки (§2). Поля у типов несовместимы между собой:
- флеш-карточка: лицо, оборот, медиа, направление(я);
- выбор: текст, варианты[], верное подмножество;
- пропуски: текст, массив пропусков;
- сопоставление: набор пар;
- числовой: значение, допуск отклонения.
- ...

Типов уже больше десяти, и список открыто расширяется (§2, новые форматы из Смыслового ядра). Уложить это в жёсткие колонки одной таблицы может быть проблематично. Придётся или писать несколько универсальных таблиц с большим количеством пустых nullable-колонок (разреженная таблица), либо таблицу-на-тип, которая будет множится с каждым новым принятым форматом.

Обе раскладки плохи по одной причине: реляционная таблица навязывает фиксированную схему данным, у которых общей схемы нет. Документная модель снимает это: поля элемента хранятся как самоописывающий документ, каждый тип несёт только свои поля - ни пустых колонок, ни новой таблицы на каждый формат. Оба подхода имеют свою цену за применение.

Итог: системе нужны **одновременно** **строгие связи** для домена и **гибкая схема** для контента элемента. Выбор БД сводится к тому, как совместить оба требования с наименьшей ценой для текущей разработки.

## Рассмотренные варианты

1. **Только реляционная БД.** Хорошая связность, поддержка транзакций. Однако для новых типов элементов приходится заводить новые таблицы (или усложнять схему), гибкости под переменный payload нет.

2. **Только документная БД.** Хорошая гибкость схемы под полиморфные элементы. Однако отсутствуют в привычном виде связи и транзакции - связность домена (наборы, группы, SRS, матчи) и целостность реализуются вручную и слабее.

3. **Реляционная БД и документная БД.** Берёт плюсы вариантов 1 и 2: связи и транзакции в реляционной, гибкий контент в документной. Минус - проблемы с согласованностью данных между двумя базами, а также двойная эксплуатация и стоимость, что для одного контейнера и соло-разработки преждевременно.

4. **Реляционная БД с поддержкой документного функционала - ВЫБРАН.** Одна реляционная СУБД, умеющая хранить и индексировать документные (JSON) поля. Реляционное ядро держит связи, целостность и транзакции; полиморфный payload элемента лежит в JSON-поле той же строки. Один движок, одна БД (ADR 0013), без распределённой согласованности варианта 3.

## Решение

Берём **реляционную СУБД с документным функционалом - PostgreSQL** (вариант 4).

- Реляционное ядро: наборы, элементы, владение, группы, SRS, сессии, матчи - таблицы со связями, которым необходима поддержка транзакций.
- Полиморфные поля элемента выносим в JSONB колонку; при необходимости поиска по ним - GIN-индекс.
- Одна БД на монолит; модули владеют своими таблицами/схемами внутри неё (ADR 0013).

Почему PostgreSQL среди реляционных:
- JSONB - документный функционал первого класса, закрывает полиморфизм без второй БД;
- open-source и бесплатна - под «бесплатное ядро» (Стратегия §6) и бюджет;
- managed-инстансы доступны в РФ-облаках (152-ФЗ);
- встроенный полнотекстовый поиск закрывает публичный поиск (§3.5) на старте.

## Последствия

- На C4-Container появляется контейнер БД, связь `монолит -> БД`.
- Полиморфизм элементов решается в одной БД, без полиглота и распределённой согласованности.
- Realtime-состояние матчей в эту БД не пишется - оно in-memory (ADR 0014).
- Выделенный поисковый движок не вводим; при упоре в возможности полнотекстового поиска - отдельная ADR.
- **При вынесении функционала из монолита в отдельный контейнер** (критерии ADR 0013) для него потребуются **отдельные ADR** с аналогичным выбором БД и решением проблем согласованности данных между хранилищами.
