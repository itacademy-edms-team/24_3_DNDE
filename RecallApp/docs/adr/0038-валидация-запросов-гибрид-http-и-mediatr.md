# ADR 0038. Валидация запросов: гибрид HTTP-конвейера и MediatR

- **Status:** accepted
- **Date:** 2026-11-10
- **Decision-maker(s):** Aleksandr
- **Owner:** Aleksandr
- **Scope:** Платформа (общее)

## Контекст

В монолите (ADR 0029) пока что используется один вход - REST за BFF (ADR 0028). Приложение уже построено на CQRS-подобной схеме: эндпоинты отправляют команды и запросы через MediatR, обработчики возвращают `ErrorOr<T>`, а HTTP-ошибки формируются единым маппером в ProblemDetails по ADR 0031.

Нужно решить, где валидировать входные данные: в HTTP-конвейере (фильтры эндпоинтов, middleware) или в конвейере MediatR (`IPipelineBehavior`). От выбора зависит, где живут валидаторы, кто отвечает за статусы ошибок и что произойдёт, когда у команд появятся другие точки входа (фоновые задачи, MCP-фасад по ADR 0005).

Дополнительно надо зафиксировать терминологию ошибок, потому что от неё зависит клиентский контракт: SPA уже маппит коды ошибок в сообщения (`Client.Web/src/shared/api/errors/restCodes.ts`).

## Рассмотренные варианты

**Вариант 1. Только HTTP-конвейер (endpoint filters).**
Плюсы: возможность реализовать быстрый отказ до входа в приложение по HTTP, прямая отдача `ValidationProblemDetails`, простой код. Минусы: защищает только HTTP; при появлении второго входа (MCP, фоновые задачи) правила нужно будет дублировать; валидация размазывается по эндпоинтам.

**Вариант 2. Только MediatR behavior.**
Плюсы: единый источник правил для любой точки входа, обработчики всегда смогут получать валидные данные независимо от входа. Минусы: до диспетчеризации команды всё равно нужно проверить формат запроса и обязательные заголовки; часть ошибок (битый JSON, content-type, размер тела) возникает раньше и к поведению не относится.

**Вариант 3. Гибрид: HTTP - форма, MediatR - правила команды (выбран).**
Плюсы: каждый слой отвечает за своё; правила команды не зависят от транспорта; маппинг ошибок остаётся одним. Минусы: нужно осознанно держать границу («что считается формой, а что правилом») и не дублировать проверки в двух местах.

## Решение

### 1. Разделение ответственности

| Слой             | Что проверяет                                                                                                                                     | Чем реализуется                                                                                  |
|------------------|---------------------------------------------------------------------------------------------------------------------------------------------------|--------------------------------------------------------------------------------------------------|
| HTTP-конвейер    | форма запроса: валидный JSON, `content-type`, лимит размера тела, обязательные заголовки (`Idempotency-Key`), корректность route/query-параметров | фреймворк (биндинг, лимиты Kestrel) + точечный endpoint-фильтр для того, чего фреймворк не знает |
| MediatR-конвейер | правила команды/запроса: обязательность и длина полей, допустимые значения, согласованность аргументов                                            | `ValidationBehavior<TRequest, TResponse>` + FluentValidation                                     |
| Домен            | инварианты, истинные всегда и везде                                                                                                               | value objects (`SetTitle.Create`, `FlashcardPayload`) и правила сущностей                        |

Правило границы: **форма запроса - в HTTP, смысл команды - в MediatR, инвариант - в домене.** Одна и та же проверка не должна дублироваться: валидатор в Application читает константы домена, вынесенные в отдельные файлы (`SetConstraints`).

### 2. Ошибки - Result-паттерн, без исключений в штатном пути

- Result-паттерн реализован библиотекой **`ErrorOr`**; кастомный `Result` не вводим. Обработчики возвращают `ErrorOr<T>`, домен объявляет ошибки статическими объектами (`SetErrors.NotFound`).
- `ValidationBehavior` не бросает `ValidationException`: он конвертирует ошибки FluentValidation в `Error.Validation(...)` и возвращает их как `ErrorOr`. Исключения остаются только для непредвиденных сбоев.
- Маппинг в HTTP - единственная точка: `ErrorOrHttpExtensions.ToProblem()` (`Common.Infrastructure/Http`), которая по `ErrorType` выбирает статус и складывает ProblemDetails: код в `title`, расширение `source` (ADR 0031).

### 3. Терминология ошибок: четыре уровня

| Поле          | Аудитория                    | Правило                                                                                                                                                       |
|---------------|------------------------------|---------------------------------------------------------------------------------------------------------------------------------------------------------------|
| `ErrorType`   | HTTP-маппер                  | грубая категория (`Validation`, `NotFound`, `Conflict`, `Unexpected`); домен не выбирает HTTP-статус                                                          |
| `Code`        | клиент, логи, метрики        | стабильный контракт вида `<Сущность>.<Правило>` (`Set.TitleRequired`, `Set.OrderStale`, `Media.UploadTooLarge`). Переименование - breaking change для клиента |
| `Description` | разработчик, поддержка, логи | диагностика («Title length 145 exceeds limit 120»). **В UI не выводится**: пользовательские тексты клиент рендерит по `Code`                                  |
| `Metadata`    | клиент, логи                 | структурированные параметры ошибки (`field`, `max`, `value`), чтобы клиент подставлял значения, не разбирая `Description`                                     |

В коды не кодируем протокол: не `Set.404`, а `Set.NotFound`; не `Set.BadRequest`, а `Set.TitleRequired`.

### 4. Регистрация и размещение

- Валидаторы - в `*.Application`, ссылаются на константы домена; регистрация `AddValidatorsFromAssembly` для сборки модуля.
- `ValidationBehavior` - одна реализация в `Common.Application`; ограничение по `TResponse : IErrorOr`, сборка результата через `ErrorOr<T>.From(errors)` с кэшированным делегатом (рефлексия один раз на тип, не на вызов).
- Endpoint-фильтр - только для транспортных проверок (`Idempotency-Key`), чтобы не распылять его по эндпоинтам.

### 5. Защита от дрейфа

- Числа живут в одном месте - константах домена (`SetConstraints`, `ElementConstraints`); на них ссылаются EF-конфигурация, VO и валидаторы.
- Тест-«якорь» фиксирует значения констант с напоминанием обновить ontology; интеграционный тест сверяет длину колонок схемы с константами.
- Клиентский маппер кодов (`restCodes.ts`) тестируется на неизвестный код: неизвестный код не должен ронять экран, только показывать какой-нибудь общий текст.

## Последствия

- Валидация не привязана к транспорту: фоновые задачи и будущий MCP-фасад получают те же правила с минимумом дублирования или даже без.
- Появляется одна точка маппинга ошибок в HTTP; обработчики не знают про статусы.
- Валидаторы зависят от констант домена - изменение лимита не требует правок в двух местах.
- Цена: два механизма вместо одного (фильтр + поведение), нужна дисциплина, чтобы не проверять одно и то же дважды.
- `Description` остаётся вторым текстовым полем; риск «утечки» его в UI закрывается правилом и код-ревью, а не типами.
- Клиентский контракт расширяется: `Metadata` с параметрами ошибок появляется в ProblemDetails-расширениях.
