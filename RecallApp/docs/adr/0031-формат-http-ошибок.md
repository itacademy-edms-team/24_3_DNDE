# ADR 0031. Формат HTTP-ошибок: ProblemDetails с кодом в `title` и происхождением в `source`

- **Status:** accepted
- **Date:** 2026-11-04
- **Decision-maker(s):** Aleksandr
- **Owner:** Aleksandr
- **Scope:** Платформа (общее)

## Контекст

Необходимо закрепить формат возвращаемых HTTP-ошибок клиенту из двух источников: Bff, App. Будущие бэкенд сервисы должны будут унаследовать данный формат, если на то позволяет их API. Данный формат уже несколько раз менялся, поэтому стоит зафиксировать текущий формат как эталонный.

Ограничения: контракт должен быть одинаковым для будущего back-office (своё приложение со своим BFF), ошибки не должны нести stack trace наружу, а происхождение отказа должно быть различимо без разбора текста.

## Рассмотренные варианты

### Вариант 1. Единый формат: код в `title`, текст в `detail`, происхождение в extension `source` - ВЫБРАН

Ответы BFF и монолита имеют одну форму: `title` - машиночитаемый код в PascalCase, `detail` - английское пояснение для разработчика, `status`, `errors` для валидации, extension `source` = `bff` | `app`.

- Код ошибки - это идентификатор для машин, `title` как раз для него и предназначен; человеческий текст живёт в `detail` и на клиенте подменяется своим сообщением.
- Один словарь кодов на клиенте (`restCodes`), один маппер, одинаковые тесты на обеих сторонах.
- `source` различает узел контрактно: не по стилю именования и не по regex, а явным полем. Появляется место для логики «отказ сессии BFF → вести на вход» без угадывания.
- Формат совпадает с тем, что уже генерирует `Results.Problem`/`AddProblemDetails`, - расхождений с фреймворком нет.

### Вариант 2. `code` как extension при человекочитаемом `title` - ОТКЛОНЁН

Так BFF работал до этой записи: `{"title":"Unauthorized","code":"not_authenticated"}`.

- Два поля об одном и том же: клиент и логи должны знать, какое из них «настоящий» код.
- `title` остаётся пустым смыслом - он не человекочитаемый (в интерфейсе всё равно берётся из словаря) и не машиночитаемый.
- Расхождение с монолитом, который кладёт код в `title`; каждая новая проверка контракта вынуждена знать про исключение из правила.

### Вариант 3. Коды BFF в snake_case, различение по стилю - ОТКЛОНЁН

`not_authenticated`, `session_expired`, `csrf_failed` у BFF; `InvalidEmail` у домена.

- Стиль именования начинает нести семантику слоя: `NotAuthenticated` от BFF и гипотетический доменный `NotAuthenticated` стали бы разными сущностями.
- В одном словаре клиента соседствуют два стиля, и каждый новый код требует решения «какой стиль здесь».
- С появлением `source` различение по регистру не нужно вовсе: конвенция превращается в шум.

### Вариант 4. `type` как URI-пространство имён (`urn:recallapp:bff:...`) - ОТКЛОНЁН

- RFC 9457 действительно отводит `type` под идентификатор типа проблемы, и это самый сложный и правильный путь.
- Но `AddProblemDetails`/`Results.Problem` заполняют `type` по HTTP-статусу, и нам пришлось бы переопределять это поведение в обоих приложениях.
- Клиенту пришлось бы разбирать URI ради строки кода; выгода не оправдывает сложность.

## Решение

Единый формат ProblemDetails для BFF и монолита:

```json
{
  "type": "https://tools.ietf.org/html/rfc9110#section-15.5.2",
  "title": "NotAuthenticated",
  "status": 401,
  "detail": "BFF session cookie is missing or no longer valid.",
  "source": "bff"
}
```

Правила:

- `title` - код ошибки в PascalCase, единый стиль для обоих приложений (`InvalidDisplayName`, `NotAuthenticated`). Коды уникальны в общей таблице клиента.
- `detail` - пояснение для разработчика (английский), не для показа пользователю; валидация дополнительно отдаёт `errors` по полям.
- `source` - extension с происхождением (`bff` | `app`), ставится централизованно через `AddProblemDetails(options.CustomizeProblemDetails)`, поэтому покрывает и необработанные исключения.
- BFF-отказы пишутся через `IProblemDetailsService` (не ручным `WriteAsJsonAsync`): тогда `type` и сериализация совпадают с монолитом. Важно: сервис не выставляет HTTP-статус, его обязан поставить вызывающий.
- Не всё является ProblemDetails: `302` на `/login` и form-POST `/logout` - навигация, а не ошибка API.
- Коды BFF объявлены константами `ApiProblem` (`NotAuthenticated`, `SessionExpired`, `CsrfFailed`).

## Последствия

- Клиент: `ProblemDetails.title` - код, `source` - слой; словарь `restCodes` содержит коды обоих приложений; `problem.code` больше не существует.
- Guard-тесты: `ApiProblemCodesTests` (рефлексия по константам, `^[A-Z][A-Za-z0-9]*$` + уникальность) и `restCodes.test.ts` (формат ключей). Новый код в другом стиле роняет тесты.
- Документация и ручные тесты ссылаются на `title = <Code>`, а не на `code`.
- Долг, зафиксированный при принятии: монолит пока не использует `ErrorOrExtensions.ToProblem` (доменные коды недостижимы), `404` отдаётся пустым телом, формат ошибок App не покрыт тестами. Чинится отдельной задачей, эта запись описывает целевой контракт.
- Back-office со своим BFF наследует формат без изменений; при добавлении нового источника (`source`) список расширяется.
