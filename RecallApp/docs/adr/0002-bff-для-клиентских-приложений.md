# ADR 0002. Backend For Frontend (BFF) для клиентских приложений

- **Status:** accepted
- **Date:** 2026-10-16
- **Decision-maker(s):** Aleksandr
- **Owner:** Aleksandr
- **Scope:** Платформа (общее)

## Контекст

Платформа web-first, фронтенд - SPA, адаптив (План §4.5). Фронтов два: публичное приложение и служебное (back-office). Оба могут получить не web-first реализации после 8-месячного горизонта. Аутентификация идёт через Keycloak по OIDC (ADR 0001).

Удостоверение пользователя нужно хранить так, чтобы его нельзя было украсть из браузера (XSS). Плюс нужен унифицированный доступ к API с разных платформ; сейчас рассматриваем веб.

## Рассмотренные варианты

Удостоверение пользователя безопасно держать двумя способами: на клиенте или в серверной прослойке. Токены в JS-доступном хранилище (`localStorage` и прочее, что видят скрипты) небезопасны и не рассматриваются.

1. **Удостоверение на клиенте.** **Хранение токенов/сессии в httpOnly secure cookie**. JS-код не имеет к ним доступа, что защищает от XSS-атак. Или **использование** криптографического механизма Proof-of-Possession через **Web Crypto API** и технологии Passkeys/WebAuthn с неизвлекаемыми ключами. Красть из браузера буквально нечего. Меньше связующих компонентов, архитектура выглядит легче для простых систем. На бэкенде всё равно должен быть компонент (Confidential Client), который безопасно взаимодействует с IdP и обменивает токены. Вариант без сессий технологически сложнее и новее. Подход не решает задачу единой точки входа (API Gateway) для будущей гибридной архитектуры, смена API одного модуля заставит переписывать все клиенты, использующие этот модуль.
2. **Удостоверение в промежуточном слое - BFF (Backend For Frontend).** Тяжёлые токены пользователя (access/refresh) живут на сервере BFF, клиенту выдаётся лёгкий идентификатор сессии в httpOnly secure cookie. Один BFF реализовывается на одно приложение. Дополнительно BFF работает как внутренний API-gateway: прячет различные запросы к различным модулям за единым фасадом для клиента. В контексте работы с модульными монолитами это большой выигрыш в удобстве при распиле его на микросервисы. Минусы: дополнительный компонент для обслуживания на каждый клиент и серверное сессионное состояние; вопросы масштабирования stateful BFF.

## Решение

Принимаем паттерн **BFF-на-фронт**: у каждого клиентского приложения свой серверный BFF. Сейчас это применяется к двум предусмотренным веб-фронтам: публичному BFF и BFF служебного приложения.

- BFF - конфиденциальный OIDC-клиент Keycloak (Authorization Code + PKCE), хранит access/refresh-токены на сервере, клиенту отдаёт лёгкий идентификатор сессии в httpOnly secure cookie.
- Фронт общается только со своим BFF; BFF проксирует запросы к доменным сервисам, прикладывая токен, и выступает внутренним API-gateway перед разрозненным бэкендом.
- У каждого клиента свой серверный фасад перед доменными сервисами: браузерные фронты - BFF, внешние ИИ-агенты - MCP-сервер. MCP-сервер группирует API в набор инструментов, аутентифицирует агента его токеном и ходит к сервисам. Детали MCP - отдельная ADR.

## Последствия

- Токены не попадают в браузер - XSS их не крадёт.
- Cookie-сессия требует действий по защите от CSRF.
- Два BFF = два контура доступа (публичный / служебный), совпадает с моделью из [Роли и доступ](../../24_3_DNDE.wiki/RecallApp-Роли-и-доступ.md).
- BFF может делать грубую проверку (аутентифицирован, глобальная роль), но тонкая авторизация - на сервисах, так как MCP-агент BFF минует. Детали - ADR 0003 (авторизация).
- В контуре появляются дополнительные, требующие обслуживания, BFF компоненты.
- На C4 BFF - контейнеры уровня L2 (по одному на фронт), не внешние системы.
