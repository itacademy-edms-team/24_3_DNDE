# ADR 0021. Хранилище сессий BFF

- **Status:** proposed
- **Date:** 2026-10-23
- **Decision-maker(s):** Aleksandr
- **Owner:** Aleksandr
- **Scope:** Платформа (общее)

## Контекст

BFF - confidential OIDC-клиент: токены держит на сервере, клиенту отдаёт httpOnly secure cookie с идентификатором сессии (ADR 0002). Получаем, что BFF хранит серверное состояние сессии - отображение `session_id` в набор {access-токен, refresh-токен, `sub`, CSRF-токен, сроки}. BFF за счёт этого считается stateful компонентом, а ADR 0002 уже отметил масштабирование stateful BFF как открытый вопрос.

BFF в системе два - публичный и служебный (ADR 0002, ADR 0004), у каждого своя область ответственности и сессий. Запись решает, где это серверное состояние будет физически находится на данном этапе.

## Рассмотренные варианты

### Вариант 1. In-memory за абстракцией - ВЫБРАН

Состояние сессий лежит в памяти процесса BFF, доступ к нему идёт через абстракцию серверного хранилища, а не напрямую.

- **Плюсы:**
  - Ноль дополнительной инфраструктуры, самый быстрый доступ.
  - Абстракция (`ITicketStore` cookie-аутентификации ASP.NET Core либо session-store BFF-фреймворка поверх `IDistributedCache`) делает переезд на внешнее хранилище заменой реализации в DI, без переписывания логики.
- **Минусы:**
  - Состояние привязано к экземпляру. Горизонтальное масштабирование требует одного экземпляра на BFF либо sticky-сессий.
  - Рестарт и деплой BFF теряют сессии.

### Вариант 2. Redis - отклонён для старта

Состояние сессий во внешнем общем Redis.

- **Плюсы:** горизонтальное масштабирование без sticky, сессии переживают рестарт и деплой, общий доступ для всех экземпляров.
- **Минусы:** дополнительный инфраструктурный компонент и его сопровождение; сетевой доступ вместо памяти; хранит токены, значит требует защиты (закрытая сеть, аутентификация, шифрование).
- Сейчас избыточен: при одном экземпляре на BFF выгоды не нужны, а цена инфраструктуры реальна.

## Решение

На MVP берём **in-memory** серверное хранилище сессий, по **одному экземпляру на BFF**. Хранилище держим за абстракцией серверного session-store с самого начала, чтобы переход на другую структуру данных был заменой реализации в DI.

Потеря сессий при рестарте и деплое смягчена: при живой SSO-сессии в Keycloak BFF переполучает токены тихим редиректом (silent re-auth), повторный ввод пароля не требуется. Полный повторный вход - только если истекла и сессия Keycloak.

Переезд на **Redis** выполняется по триггеру, любому из:
- нужно несколько экземпляров BFF;
- появляется требование, чтобы сессии как-то переживали рестарт и деплой BFF (чтобы пользователь при деплое не терял вход);
- Redis всё равно вводится под backplane SignalR при масштабировании realtime (ADR 0014) - тогда сессии BFF переезжают туда почти без дополнительной цены.

## Последствия

- Каждый BFF на MVP - один экземпляр; это принятое ограничение, снимается переходом на Redis.
- Рестарт и деплой BFF сбрасывают серверные сессии; UX смягчён silent re-auth через SSO Keycloak.
- Доступ к хранилищу сессий идёт через абстракцию; смена на Redis локальна, доменный и клиентский код не затрагивает.
- Redis-вариант, когда введём, хранит токены и требует защиты: закрытая сеть, аутентификация, не торчит наружу.
