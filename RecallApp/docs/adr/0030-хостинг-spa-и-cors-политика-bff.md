# ADR 0030. Хостинг SPA на субдомене и CORS-политика BFF

- **Status:** accepted
- **Date:** 2026-11-03
- **Decision-maker(s):** Aleksandr
- **Owner:** Aleksandr
- **Scope:** Платформа (общее)

## Контекст

У нас есть BFF, Keycloak и модульный монолит. Каждый сидит на своём домене: `bff.*`, `auth.*`; исключение - модульный монолит: с ним взаимодействие происходит через `bff.*/api/**`. Далее появится SPA, и нужно решить, как он будет хоститься.

Ключевые ограничения:

- **Вход в аккаунт и выход  - не API-запросы.** Логин - полноценный переход браузера на страницы входа Keycloak (ADR 0023); логаут - отправка HTML-формы, не fetch (кросс-origin редирект под fetch блокируется CORS - проверено вручную при приёмке C0).
- **Сессия - cookie `SameSite=Lax` (ADR 0021).** SPA с другого origin может ходить в API только через явную CORS-политику с `AllowCredentials`: «открыть доступ всем origin'ам» нельзя и считается грубейшей ошибкой в безопасности (запросы с чужих сайтов пройдут с сессией), «закрыть CORS совсем» - SPA не сможет читать ответы.
- **Один SPA на все устройства.** План платформы фиксирует web-first и адаптив (десктоп/планшет/телефон): один origin клиента, отдельных «мобильных» путей не будет.

## Рассмотренные варианты

### Вариант 1. SPA на отдельном origin `app.*`, CORS-политика BFF с allowlist - ВЫБРАН

SPA хостится на собственном субдомене (`app.recallapp.localhost` в dev, `app.<domain>` в проде), BFF разрешает CORS только для `/api/**` и только с доверенных origin'ов: `AllowCredentials` + точный allowlist (не `*`).

- **Плюсы:**
  - **Независимость узлов.** Статика и API развиваются, кэшируются и релизятся отдельно: обновление SPA не трогает BFF, в проде статика уезжает на nginx/CDN без пересборки образа BFF.
  - **Минимальные привилегии.** CORS действует только на `/api/**`; allowlist - явный список origin'ов из конфигурации, wildcard запрещён. Поверхность атаки минимальна по построению.
  - **Чистые namespace'ы по назначению.** `app.*` - статика SPA, `bff.*` - API и cookie-сессия, `auth.*` - Keycloak. Замена любого узла (dev Vite -> prod nginx, смена домена) прозрачна для остальных.
  - **Логин/логаут не затрагиваются.** Это top-level навигация на `/login` и form-POST `/logout` - CORS к ним не применяется вовсе, их устройство (ADR 0023, ADR 0027) не меняется.
  - **Совместимость с будущими клиентами.** Мобильный клиент, PWA, гостевые страницы, вынос статики на CDN - ничего из этого не потребует пересмотра этой записи.
- **Минусы:**
  - **Несколько origin'ов вместо одного.** Политику нужно сопровождать: добавление окружения (staging, prod-домен) - правка конфигурации BFF. Неактуальный или забытый origin ломает взаимодействие, лишний - проблемы с безопасностью; лечится тестами контракта и ревью.
  - **Preflight-запросы.** Непростой cross-origin запрос (метод не GET/HEAD или непростые заголовки) оборачивается в OPTIONS - лишний RTT. Смягчается кэшем preflight (`Access-Control-Max-Age`) и общим правилом API держать запросы простыми.
  - **Dev-сложность.** Необходимы дополнительные настройки для работы HMR и корректной подгрузки статики в edge-proxy.

### Вариант 2. Раздача статики через BFF (единый с bff origin) - ОТКЛОНЁН

BFF отдаёт собранный SPA (StaticFiles middleware), `/api/**` - на том же origin.

- **Плюсы:**
  - **CORS не нужен.** Same-origin: cookie-сессия без cross-site трений, ни allowlist'ов, ни preflight.
  - **Меньше узлов.** Один контейнер и один origin для статики и API в dev и проде; локальная развёртка проще на один сервис.
- **Минусы:**
  - **Смешение ответственностей BFF.** BFF (ADR 0002) задуман как узел сессий и композиции API; хостинг статики добавляет ему третью роль. Каждый релиз SPA - либо релиз BFF, либо отдельный пайплайн, копирующий статику в образ - усложнение в обоих случаях.
  - **Конфликт кэширования.** У статики (долгий кэш по хэшу файла) и API (короткий/отсутствующий кэш) противоположные требования к заголовкам; живя в одном приложении, они конфликтуют на уровне middleware, а инвалидация статики привязана к деплою BFF.
  - **Ранняя привязка к мёртвому весу.** Вынос статики на отдельный веб-сервер/CDN при росте трафика экономически неизбежен; решение «статика из BFF» придётся пересматривать целиком, включая cookie-контекст.
  - **Раздутие поверхности BFF.** Статический контент проходит через .NET-процесс и расширяет образ BFF без пользы для API.

### Вариант 3. SPA через edge-proxy на path (`bff.localhost/app`) - ОТКЛОНЁН

Edge-proxy маршрутизирует префикс `/app` на статический хостинг, API и сессионные эндпоинты остаются на корне того же origin.

- **Плюсы:**
  - **Один origin без CORS.** Статика и API same-origin - те же плюсы, что у варианта 2, без смешения ролей в BFF-процессе.
  - **Статика вне BFF.** За edge-proxy статика может жить на любом бэкенде (включая будущий CDN) - часть минусов варианта 2 снимается.
- **Минусы:**
  - **Смешение namespace'ов приложения и API.** Публичные пути BFF (`/login`, `/logout`, `/session`, ADR 0027) и SPA-пути (`/app/*`) живут на одном хосте: каждый новый маршрут любой стороны требует проверки на коллизию имён.
  - **Базовый путь SPA.** Router требует `basename`, ассеты - префикс в ссылках, deep links (`/app/account`) должны проксироваться на `index.html`. Нестандартные конфиги, риск битых ссылок и путей - всё это «лишнее» по сравнению с корневым хостингом на своём origin.
  - **По сути частный случай варианта 2.** Релизный цикл статики привязан к конфигурации прокси; поздний переход на отдельный домен - переделка путей, basename и всех ссылок.

## Решение

SPA хостится на **отдельном origin `app.*`**. В dev: сервис `client-web` за edge-proxy, server-блок `app.recallapp.localhost` -> `client-web:5173`; в проде: статика за отдельным веб-сервером (детали релизного конвейера - отдельной записью позже). BFF получает CORS-политику `spa`: применяется **только к маршруту `/api/**`**, `AllowCredentials`, allowlist - точные origin'ы из конфигурации (dev: `https://app.recallapp.localhost`, плюс локальные `http://localhost:5173/5179` для запуска Vite без прокси), preflight пропускается без аутентификации. Навигация на вход и выход остаётся полноценными переходами браузера, а не запросами из скрипта: логин - смена URL страницы на `bff.*/login` (пользователь уходит на форму Keycloak и возвращается с кукой сессии), логаут - обычная отправка HTML-формы (`method="POST"`, не fetch). CORS регулилирует только чтение ответов кросс-origin из скриптов (fetch/XHR), на переходы браузера он не действует, поэтому эти эндпоинты в CORS-политику не включаются и отдельных правил для них не требуется. Следствие для клиента: в `/login` и `/logout` ходим только навигацией и формой.

## Последствия

- Edge-proxy: появится новый app-блок в конфиге, потребуется расписать правило для websocket, чтобы работал HMR в dev.
- BFF: новая CORS-политика на YARP-маршруте `/api/**`; preflight (OPTIONS) должен проходить до аутентификации.
- Compose: сервис `client-web` (node, bind-mount `./Client/Client.Web`, анонимный том на `node_modules`), сеть dev_net; Dockerfile для dev - `Dockerfile.development` рядом с шаблонным production-Dockerfile.
- SPA ходит в API по абсолютному URL `https://bff.recallapp.localhost/api` с `credentials: 'include'`; base URL не захардкожен.
- При добавлении окружений (staging, prod-домены) origin'ы добавляются в конфигурацию BFF; wildcard-origины запрещены.
- Офлайн-устойчивость одиночного обучения (план платформы §6) - вне рассмотрения этой записи; при появлении PWA/service worker потребуется отдельная ADR.
