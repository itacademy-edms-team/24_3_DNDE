# ADR 0040. Транзакционный outbox на доменных событиях

- **Status:** accepted
- **Date:** 2026-11-13
- **Decision-maker(s):** Aleksandr
- **Owner:** Aleksandr
- **Scope:** Платформа (общее)

## Контекст

Модуль Media решает, можно ли удалить файл, по числу ссылок на него: пока на файл ссылается хотя бы одна карточка, удаление запрещено (`409 Media.InUse`), а файл без ссылок старше 24 часов убирает фон (ADR 0037, ontology Media §6.4).

Ссылки живут в Sets (payload элемента), но принадлежат Media (`media.media_references`). Значит при каждом сохранении или удалении элемента Sets должен сообщить Media актуальный набор ссылок. Межсхемные записи и внешние ключи запрещены (ADR 0036), поэтому это вызов контракта, а не запись в чужую таблицу.

Проблема в отказоустойчивости: сохранение элемента и уведомление Media - две разные транзакции. Если уведомление не дошло, возможны два исхода:

- **Потеряли «файл привязан».** Карточка ссылается на файл, а Media считает его неиспользуемым. Через 24 часа фон удалит файл - потеря данных.
- **Потеряли «файл больше не нужен».** Файл остаётся в хранилище навсегда - мусор.

Цена ошибок несимметрична, поэтому нужен механизм доставки, переживающий сбой между коммитом бизнес-изменения и вызовом соседнего модуля. ADR 0036 откладывал outbox до первого межмодульного потребителя; им стал Media.

Первая итерация этого ADR писала сообщения вручную (`IOutboxWriter.Enqueue` в каждом хендлере) и хранила payload-записи. При расширении выяснилось: логика «что отправлять» расползается по хендлерам, нет полос доставки, нет состояний для ретраев и версии схемы. Эта редакция обобщает механизм на доменные события и добавляет операционную зрелость.

## Рассмотренные варианты

**Вариант 1. Прямой синхронный вызов из Sets после сохранения элемента (без outbox).**
Плюс: просто. Минус: тот же разрыв между коммитом и вызовом; при сбое уведомление теряется безвозвратно. Отклонён.

**Вариант 2. Флаг «используется» + события attach/detach.**
Плюс: проще payload. Минус: события несут дельту, потеря сообщения ломает состояние, порядок дельт важен. Отклонён: принят декларативный набор ссылок (ontology Media §6.4).

**Вариант 3. Периодическая полная сверка (Sets присылает все используемые `mediaId`).**
Плюс: устойчиво к любым потерям. Минус: сутки лага, дорогие полные выборки. Годится как страховка, не как основной механизм. Отклонён.

**Вариант 4. Outbox с ручным `IOutboxWriter.Enqueue` (первая итерация).**
Работал, но «что и куда отправлять» дублировалось в четырёх хендлерах, а воркер не различал быстрые и медленные сообщения. Заменён вариантом 5.

**Вариант 5. Доменные события + interceptor (выбран).**
Сущности поднимают доменные события в памяти; `SaveChangesInterceptor` материализует их в outbox-записи в той же транзакции; воркер доставляет. Логика «что отправлять» живёт в сущности, механика записи - в interceptor'е один раз.

## Решение

### 1. Доменные события хранят сущности

Из Ardalis.SharedKernel забираем контракт «сущность держит события», адаптированный под MediatR:

- `IHasDomainEvents` - `DomainEvents` + `ClearDomainEvents()`;
- `HasDomainEventsBase` - `List<IDomainEvent>` с `[NotMapped]`, защищённый `RegisterDomainEvent`;
- `IDomainEvent` - чистый маркер со сквозным `EventId` (uuid), `DateOccurred` и стабильным именем `EventType`; `EventId` генерится при поднятии события и едет с ним дальше.

Сущности Sets (`Element`, `Set`) поднимают событие в момент изменения контента/удаления. Событие лежит в памяти до `SaveChanges`, никуда не уходя.

### 2. Interceptor материализует outbox-записи

`SaveChangesInterceptor` в `Common.Infrastructure` сканирует `ChangeTracker` на `IHasDomainEvents`, извлекает и очищает события, пишет `outbox_messages` в той же транзакции. Транзакция откатилась - сообщений нет; прошла - они гарантированно есть.

Никакого immediate dispatch: `IDomainEventDispatcher` вызывает только outbox-воркер. Событие фиксируется в памяти при `SaveChanges`, а доставляется асинхронно.

### 3. Чистая абстракция событий - MediatR только в инфраструктуре

- `IDomainEvent`, `IDomainEventHandler<T>`, `IDomainEventDispatcher` - свои, **без** `: INotification` (домен и Common не зависят от MediatR).
- MediatR знает только `Common.Infrastructure`: событие оборачивается в `DomainEventNotification<TEvent> : INotification`, open-generic `DomainEventNotificationHandler<TEvent>` раздаёт его нашим `IDomainEventHandler<TEvent>`, `MediatRDomainEventDispatcher` публикует через `IPublisher` (обёртка - кэшированная рефлексия в одном месте).

### 4. Таблица

Модуль-продюсер владеет таблицей в своей схеме:

```sql
sets.outbox_messages (
    id                bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY, -- порядок доставки
    type              text        NOT NULL,                            -- стабильное имя события
    version           int         NOT NULL DEFAULT 1,                  -- эволюция схемы payload
    lane              text        NOT NULL,                            -- fast | slow
    payload           jsonb       NOT NULL,                            -- тело события
    status            text        NOT NULL DEFAULT 'pending',          -- жизненный цикл
    checkpoint        jsonb       NULL,                                -- чекпоинт обработчика (opaque)
    attempts          int         NOT NULL DEFAULT 0,
    next_attempt_at   timestamptz NOT NULL DEFAULT now(),
    lease_owner       uuid        NULL,                                -- кто сейчас обрабатывает
    lease_until       timestamptz NULL,
    last_error        text        NULL,
    created_at        timestamptz NOT NULL DEFAULT now(),
    last_processed_at timestamptz NULL,
    finished_at       timestamptz NULL
);

CREATE INDEX ix_outbox_messages_pending
    ON sets.outbox_messages (lane, next_attempt_at, id)
    WHERE status IN ('pending', 'retrying');
```

`id` (identity) - внутренний порядок и PK, в событие не попадает. Сквозная идентичность - это `EventId` (uuid) внутри `payload`: генерится при поднятии события, поэтому доступен уже при сериализации и едет дальше (воркер -> брокер -> потребитель) как correlation/message id. Запихнуть DB-`id` в payload нельзя: identity генерится БД в момент INSERT, а payload пишется тем же INSERT.

Поиск по `EventId` - expression-индекс `(payload->>'eventId')`, заводится при появлении реального запроса; отдельная колонка не нужна.

### 5. Жизненный цикл

Состояния колонки `status`: `pending` -> `processing` -> `processed`, с веткой на ретрай и терминал:

```
pending -> processing -> processed      (успех, терминал)
                    ↘ retrying       (упал, attempts < maxAttempts, next_attempt_at в будущем)
                      -> processing   (воркер берёт в ретрай)
pending | processing | retrying -> dead   (attempts ≥ maxAttempts, терминал, только вручную)
```

- `processing` удерживает **аренду**: `lease_owner` + `lease_until`. Воркер продлевает её по ходу; если упал - аренда истекает, и следующий воркер перехватывает сообщение. Без аренды `in_process` не восстанавливается после падения (паттерн тот же, что в lease-идемпотентности `confirm`).
- `checkpoint` - непрозрачное jsonb-поле, принадлежит обработчику: многошаговый обработчик пишет туда пройденные шаги, чтобы при повторе не переделывать сделанное. Воркер его не читает и не интерпретирует.
- `last_error` - причина последней неудачи; `finished_at` - момент терминального исхода (`processed` или `dead`).

### 6. Полосы доставки

Одна очередь не должна застревать на медленном сообщении (head-of-line blocking). Вводим полосу `lane`:

- `OutboxLanes.Fast` / `OutboxLanes.Slow` - константы в `Common.Application`;
- по одному воркеру на полосу, выборка `WHERE lane = … AND status IN ('pending','retrying') AND next_attempt_at <= now() ORDER BY id FOR UPDATE SKIP LOCKED`;
- `media.references.sync` - `fast`; будущие медленные потребители (email, фоновая обработка) - `slow`.

### 7. Доставка и ретраи

- Доставка **at-least-once**: сообщение повторяется, пока не обработается или не станет `dead`.
- Backoff: 5 с -> 25 с -> 2 мин -> 10 мин -> далее раз в час.
- `maxAttempts` - на полосу/тип события, по умолчанию 10; `1` ≈ at-most-once для некритичных событий. После исчерпания - `dead`, лог уровня error, автоматических повторов нет.

### 8. Семантика доставки

- **Ровно один раз в чистом виде не достижим** (внешний эффект обработчика нельзя сделать атомарным с записью `status`). Получаем **effectively-once**: at-least-once доставка + идемпотентный обработчик.
- **Обработчик обязан быть идемпотентным** - это контракт, а не пожелание. Для многошаговых обработчиков идемпотентность достигается чекпоинтами в `checkpoint`.
- Per-consumer трекинг (кто из потребителей ещё не получил) не вводим: он нужен только для неидемпотентных потребителей. Появится такой - отдельным решением.
- Сообщение помечается `processed` только когда **все** обработчики события вернули успех; частичный успех -> повтор всего набора.

### 9. Версия и тип события

- `type` - **стабильное имя** (`media.references.sync`).
- `version` - отдельный int с `DEFAULT 1`: существующие строки уже `v1` без бэкфилла. Реестр обработчиков маппит `(type, version) -> IDomainEventHandler`.
- Сегодня событие одно, поэтому ветвление по версии не строим - только колонка. Механика `(type, version)` появляется вместе с первым `v2`.

### 10. Первое сообщение: синхронизация ссылок элемента

Событие `MediaReferencesChanged` (живёт в `Media.Contracts`), `type = media.references.sync`, `lane = fast`, `version = 1`:

```json
{ "ownerId": "uuid", "elementScope": "set:{setId}:element:{elementId}",
  "slots": [ { "reference": "set:{setId}:element:{elementId}:front", "mediaId": "uuid" } ] }
```

Семантика - полная замена слотов области: чего нет в `slots` - снимается; слот с другим `mediaId` перезаписывается; новый вставляется. Обработчик Media (`IDomainEventHandler<MediaReferencesChanged>`) применяет это одной транзакцией. Файл не `ready` или чужой - сообщение не применяется и уходит в повтор (причина временная).

Удаление элемента - пустой `slots`; удаление набора - `elementScope` набора (`set:{setId}`) с пустым `slots` (Media снимает всё с этим префиксом).

### 11. Границы и запреты

- Продюсер пишет только в свою схему; потребитель не читает `sets.*`.
- Один outbox на модуль-продюсер; общая таблица на все модули не вводится (ADR 0036).
- Outbox - не замена синхронной проверке: перед сохранением элемента Sets **синхронно** спрашивает Media «файл готов и мой?» (`IMediaReadiness.EnsureReadyAsync`), иначе плохая ссылка попадёт в БД до доставки события.
- `checkpoint` и идемпотентность - зона ответственности обработчика, не диспетчера.

### 12. Чистка

`processed` старше 7 дней удаляются фоновой задачей батчами. `dead` хранятся дольше - до ручного разбора.

## Последствия

- Ссылки на медиа доставляются надёжно; сбой между сохранением элемента и уведомлением больше не удаляет живой файл.
- Согласованность событийная: окно между сохранением элемента и применением ссылок - секунды. Media это терпит: удаление по «нулю ссылок» требует возраста 24 часа (ontology Media §6.4).
- В Sets появляется переиспользуемая инфраструктура: интерфейс событий, interceptor, таблица, воркеры с полосами и ретраями. Следующие межмодульные уведомления пойдут по той же схеме.
- Домен не зависит от MediatR: события и обработчики - свои, MediatR только в `Common.Infrastructure`.
- Нужны наблюдаемость и алерт: размер очереди по полосам, возраст самого старого необработанного, число `dead`.
- Тесты: событие пишется в одной транзакции с изменением и откатывается вместе с ним; воркер повторяет при ошибке; повторная доставка не меняет состояние (идемпотентный обработчик); частичный успех перезапускает весь набор; истёкшая аренда перехватывается; `dead` не крутится вечно; чекпоинт переживает ретрай.
