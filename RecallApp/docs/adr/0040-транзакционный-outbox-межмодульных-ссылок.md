# ADR 0040. Транзакционный outbox для межмодульных ссылок на медиа

- **Status:** proposed
- **Date:** 2026-11-13
- **Decision-maker(s):** Aleksandr
- **Owner:** Aleksandr
- **Scope:** Платформа (общее)

## Контекст

Модуль Media решает, можно ли удалить файл, по числу ссылок на него: пока на файл ссылается хотя бы одна карточка, удаление запрещено (`409 Media.InUse`), а файл без ссылок старше 24 часов убирает фон (ADR 0037, ontology Media §6.4).

Ссылки живут в Sets (payload элемента), но принадлежат Media (`media.media_references`). Значит при каждом сохранении или удалении элемента Sets должен сообщить Media актуальный набор ссылок. Межсхемные записи и внешние ключи запрещены (ADR 0036).

Проблема в отказоустойчивости: сохранение элемента и уведомление Media - две разные транзакции. Если уведомление не дошло (сеть, падение процесса, таймаут), возможны два исхода:

- **Потеряли «файл привязан».** Карточка ссылается на файл, а Media считает его неиспользуемым. Через 24 часа фон удалит файл, и у пользователя пропадёт картинка - потеря данных.
- **Потеряли «файл больше не нужен».** Файл остаётся в хранилище навсегда - мусор, расход квоты бесплатного тира.

Цена ошибок несимметрична, поэтому нужен механизм доставки, который переживает сбой между коммитом бизнес-изменения и вызовом соседнего модуля. ADR 0036 откладывал outbox до появления первого межмодульного потребителя; этим потребителем стал Media.

## Рассмотренные варианты

**Вариант 1. Прямой синхронный вызов из Sets после сохранения элемента (без outbox).**
Плюс: просто, нет новой инфраструктуры. Минус: тот же разрыв между коммитом и вызовом; при сбое уведомление теряется безвозвратно, и мы возвращаемся к проблеме выше. Отклонён.

**Вариант 2. Флаг «используется» + события attach/detach.**
Плюс: проще payload. Минус: события несут дельту, поэтому потеря сообщения ломает состояние (см. выше), а порядок применения дельт важен. Отклонён вместе с идеей флага: принят декларативный набор ссылок (ontology Media §6.4).

**Вариант 3. Периодическая полная сверка (Sets присылает все используемые `mediaId`).**
Плюс: устойчиво к любым потерям. Минус: сутки лага, дорогие полные выборки, нужен отдельный контракт «все используемые id». Годится как страховка, но не как основной механизм. Отклонён как основной.

**Вариант 4. Транзакционный outbox в схеме Sets (выбран).**
Запись сообщения в ту же транзакцию, что и бизнес-изменение; фоновая доставка с повторами; обработчик идемпотентен благодаря декларативному payload.

## Решение

### 1. Где живёт outbox

Модуль-продюсер (Sets) владеет таблицей в своей схеме:

```sql
sets.outbox_messages (
    id              bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY, -- порядок обработки
    type            text        NOT NULL,                            -- тип сообщения
    payload         jsonb       NOT NULL,                            -- тело, схема на стороне обработчика
    created_at      timestamptz NOT NULL DEFAULT now(),
    next_attempt_at timestamptz NOT NULL DEFAULT now(),
    attempts        int         NOT NULL DEFAULT 0,
    processed_at    timestamptz NULL,
    abandoned_at    timestamptz NULL,
    last_error      text        NULL
);
CREATE INDEX ix_outbox_messages_pending
    ON sets.outbox_messages (next_attempt_at, id)
    WHERE processed_at IS NULL AND abandoned_at IS NULL;
```

`id` (identity) обслуживает порядок доставки. Отдельного `uuid` нет: идемпотентность обеспечивает не идентификатор сообщения, а декларативный payload - повторное применение того же набора ссылок ничего не меняет.

### 2. Запись сообщения

Сообщение пишется в той же транзакции, что и изменение элемента (создание, правка, удаление, изменение порядка не пишет - ссылки не меняются). Транзакция откатилась - сообщения нет; транзакция прошла - сообщение гарантированно есть.

### 3. Доставка

- Фоновый диспетчер в `Sets.Infrastructure` (интервал 5 секунд, батч до 50 сообщений).
- Выборка: `WHERE processed_at IS NULL AND abandoned_at IS NULL AND next_attempt_at <= now() ORDER BY id FOR UPDATE SKIP LOCKED`. `SKIP LOCKED` позволяет держать несколько инстансов приложения без дублей.
- Порядок - строго по `id`, батч обрабатывается последовательно; при ошибке батч останавливается, остаток уходит в следующий заход. Это гарантирует, что более поздняя декларация не применится раньше предыдущей (актуальное состояние всегда побеждает).
- Обработчик берётся из DI по строке `type`. Абстракция `IOutboxMessageHandler` живёт в `Common.Application`, реализации регистрирует модуль-потребитель (Media). Sets не ссылается на Media: он знает только строку типа.
- Успех: `processed_at = now()`. Ошибка: `attempts += 1`, `last_error`, `next_attempt_at = now() + backoff` (5 с, 25 с, 2 мин, 10 мин, далее с шагом 1 час).
- После 10 попыток сообщение помечается `abandoned_at` и пишется запись в лог уровня error: автоматических повторов больше нет, разбирается вручную. Молчаливая потеря запрещена - «залипшее» сообщение обязано быть видно.

### 4. Первое сообщение: синхронизация ссылок элемента

Тип `media.references.sync`, payload:

```json
{ "ownerId": "uuid", "elementScope": "set:{setId}:element:{elementId}",
  "slots": [ { "reference": "set:{setId}:element:{elementId}:front", "mediaId": "uuid" } ] }
```

Семантика - полная замена слотов указанной области: слоты, которых нет в `slots`, удаляются; слот с другим `mediaId` перезаписывается; новый вставляется. Обработчик Media выполняет это одной транзакцией. Если хотя бы один файл не `ready` или чужой - сообщение не применяется и уходит в повтор (причина временная: файл мог ещё не подтвердиться).

Удаление элемента - сообщение с пустым `slots`. Удаление набора - сообщение с одним `elementScope` набора (`set:{setId}`) и пустым набором слотов: Media удаляет всё с этим префиксом.

### 5. Идемпотентность и повторная доставка

Доставка at-least-once: сообщение может быть применено дважды. Это безопасно, потому что payload декларативен, а слот уникален (`media.media_references.reference` UNIQUE): повторная синхронизация того же набора - no-op. Обработчик обязан быть идемпотентным по контракту, а не «по договорённости»: уникальный индекс - техническая гарантия.

### 6. Границы и запреты

- Продюсер пишет только в свою схему; потребитель не читает `sets.*`.
- Один outbox на модуль-продюсер; общая таблица на все модули не вводится (жизненные циклы и типы сообщений разные - ADR 0036).
- Outbox - не замена синхронной проверке: перед сохранением элемента Sets **синхронно** спрашивает Media «файл готов и мой?» (`EnsureReadyAsync`), иначе плохая ссылка попадёт в БД, а ошибка придёт через секунды после сохранения.
- События наружу (доменные события для других модулей) этим ADR не вводятся.

### 7. Чистка

Обработанные сообщения (`processed_at` не пуст) старше 7 дней удаляются фоновой задачей тем же приёмом, что чистка ключей идемпотентности (батчами, в своей транзакции). `abandoned_at` хранятся дольше - до ручного разбора.

## Последствия

- Ссылки на медиа доставляются надёжно: сбой процесса между сохранением элемента и уведомлением больше не приводит к удалению живого файла.
- Согласованность становится событийной: окно между сохранением элемента и применением ссылок - секунды. Media обязан это терпеть: удаление по «нулю ссылок» требует возраста 24 часа (ontology Media §6.4), что с запасом перекрывает окно и повторы.
- В Sets появляется инфраструктура, которая пригодится и дальше: таблица, диспетчер, абстракция обработчика. Следующие межмодульные уведомления (форк в каталог, события обучения) пойдут по той же схеме без переизобретения.
- Появляется «голова очереди»: залипшее сообщение задерживает последующие того же продюсера. Для ссылок на медиа объём мал и задержка допустима; если появится поток, добавим версионирование по области (`sequence` на элемент) и параллельную обработку разных областей.
- Нужны наблюдаемость и алерт: размер очереди, возраст самого старого необработанного сообщения, число `abandoned`.
- Тесты: сообщение пишется в одной транзакции с элементом и откатывается вместе с ним; диспетчер повторяет при ошибке обработчика; повторная доставка не меняет состояние; порядок сообщений сохраняется; «отравленное» сообщение уходит в `abandoned`, а не крутится вечно.
