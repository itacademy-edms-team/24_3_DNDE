# ADR 0020. Провижининг доменного пользователя (JIT)

- **Status:** proposed
- **Date:** 2026-10-23
- **Decision-maker(s):** Aleksandr
- **Owner:** Aleksandr
- **Scope:** Платформа (общее)

## Контекст

Про одного человека в системе существует две записи. Первая - это личность в Keycloak: учётка, креды, аутентификация, OIDC-токены; стабильный идентификатор - это claim `sub` (UUID). Вторая - это доменный «Пользователь» в БД монолита (План §2): профиль, владение наборами и элементами, прогресс SRS, подписки, доменные роли и права.

Разделение вытекает из принятых решений: Keycloak как IAM хранит только личность (ADR 0001), доменных данных не держит; авторизация выполняется на доменных сервисах (ADR 0003), поэтому доменные роли и владение висят на доменной строке User, а не на учётке Keycloak.

Регистрация и аутентификация происходят в Keycloak. В этот момент монолит о новом человеке ничего не знает - доменной строки нет. Строка обязана существовать не позже первой доменной операции, которая на пользователя ссылается: вставка набора или элемента, запись прогресса, проверка доменных прав. Сама регистрация строку не создаёт, поэтому механизм провижининга нужен в любом случае. Вопрос записи: в какой момент и каким механизмом доменная строка создаётся и связывается с личностью Keycloak.

Демо-режим для пользователей на MVP не планируется, а write-API для неаутентифицированных запросов закрыт. Realtime-гость входит по коду матча и живёт в in-memory состоянии матча (ADR 0014), доменной строки User не получает. По итогу получаем закрытый API для невошедших в аккаунт пользователей.

## Рассмотренные варианты

### Вариант 1. JIT (just-in-time) при первом доменном запросе - ВЫБРАН

Доменная строка не заводится заранее. На входе аутентифицированного доменного конвейера монолит берёт `sub`, ищет User; если нет строки - создаёт её тут же из claims и продолжает операцию.

- **Плюсы:**
  - Нет кастомного кода в Keycloak: ни Java-SPI, ни слушателей событий.
  - Единообразно для парольной регистрации и соц-входа - оба просто дают `sub`, который всплывает на первом запросе.
  - Надёжность сводится к одной идемпотентной операции БД.
  - Личности, не касавшиеся домена, не плодят осиротевших строк.
- **Минусы:**
  - Шаг провижининга лежит на пути запроса (каждый раз по 1-му запросу и (опц.)1-й команде к бд).
  - Гонку первого запроса обязан кто-то разрешать, например БД через constrait.
  - Удаление и деактивацию не покрывает - это отдельный механизм.

### Вариант 2. Событие или webhook от Keycloak

Keycloak при регистрации шлёт событие (Event Listener SPI или admin-events -> webhook), монолит создаёт строку сразу, до первого входа.

- Требует кастомного Java-кода внутри Keycloak и связности Keycloak -> монолит.
- Доставка события ненадёжна: из коробки нет гарантии и ретраев, нужен свой механизм надёжной доставки на стороне Keycloak. Та же проблема гарантии доставки, которой избегали в доставке почты.
- Жадное создание оправдано лишь если строка нужна до любого запроса. Для MVP таких требований нет.

### Вариант 3. Оркестрация в BFF в потоке регистрации

BFF в одном флоу регистрирует личность в Keycloak и создаёт доменную строку в монолите.

- Распределённая запись в две системы без общей транзакции. Частичный отказ (создано в Keycloak, упал монолит) оставляет рассинхрон, нужна реализация механизма согласования состояний.
- Не покрывает соц-вход: там нет формы регистрации, личность появляется при первом федеративном входе мимо этого флоу.

## Решение

Провижиним доменного пользователя по модели **JIT**.

- **Ключ связи** личность <-> домен - `sub` из Keycloak. В доменной таблице колонка `keycloak_sub`, **UNIQUE NOT NULL**.
- **Место провижининга** - одна сквозная ступень на входе аутентифицированного доменного конвейера (с помощью middleware «ensure provisioned»), чтобы нижележащие сервисы всегда получали готового User. Не размазываем по отдельным сервисам.
- **Идемпотентность** обеспечивается на уровне БД: upsert по `keycloak_sub` (`INSERT ... ON CONFLICT (keycloak_sub) DO NOTHING`) с последующим перечитыванием строки. Проверка «найти, потом вставить» на уровне приложения недопустима - при параллельном первом запросе (с двух вкладок, повтор) она даёт дубль.
- **Источник личности** - провалидированные BFF claims, переданные монолиту по доверенному внутреннему каналу. Монолит в IAM не ходит (ребра `монолит -> IAM` на L2 нет), токен на валидацию не пересылается. Это согласовано с ADR 0002 и ADR 0003.
- **Атрибуты при создании** берутся из claims: `sub` (ключ), `email`, признак верификации, отображаемое имя. Доменные поля (роли, подписка, настройки) заполняются дефолтами; дефолтная доменная роль - по ADR 0003.

## Открытые пункты (решаем до перевода в accepted)

- **Политика свежести атрибутов.** Email и имя меняются в Keycloak позже, кэш в домене протухает. Выбрать: не кэшировать мутабельные identity-атрибуты (строка держит `sub` + доменные данные, email/имя читаются из токена на месте) либо обновлять кэш тем же upsert на каждом проходе.
- **Lifecycle: удаление и деактивация.** JIT покрывает только создание. Осиротевшую при удалении личности строку закрывает отдельный механизм. Расписывается отдельной записью.
- **Дефолтная доменная роль** нового User - конкретное значение согласовать с моделью ролей ADR 0003.

## Последствия

- Не пишем кастомного кода в Keycloak ради провижининга.
- Доменная строка создаётся лениво, ровно к первой доменной операции; надёжность держится на уникальности поля и upsert.
- `keycloak_sub` становится стабильным внешним ключом личности во всей доменной схеме.
- Удаление и деактивация пользователя остаются нерешёнными этой записью и требуют отдельного рассмотрения.
- Доменный write-API закрыт для неаутентифицированных; провижинятся только аутентифицированные пользователи.
