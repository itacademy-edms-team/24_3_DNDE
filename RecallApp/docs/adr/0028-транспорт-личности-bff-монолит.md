# ADR 0028. Транспорт личности из BFF в монолит: форвардинг access-токена (Trusted Domain)

- **Status:** accepted
- **Date:** 2026-10-30
- **Decision-maker(s):** Aleksandr
- **Owner:** Aleksandr
- **Scope:** Платформа (общее)

## Контекст

Монолит (модульный, ADR 0013) получает личность пользователя от BFF: BFF уже провалидировал токен и знает сессию, монолит в IAM не ходит и токен не валидирует сам (ADR 0002, ADR 0020). Решение 2026-10-27 (зафиксировано в ADR 0020) определило принцип «доверенный канал BFF -> монолит», но не фиксировало механизм. Обсуждено три механизма передачи личности.

Ключевые ограничения: монолит один (сервисов с отдельными audience нет); BFF владеет сессией и свежестью access-токена (ADR 0027, TokenRefreshMiddleware); клиент никогда не должен иметь возможности подсунуть монолиту подделанную личность.

## Рассмотренные варианты

### Вариант 1. Доверенные заголовки `X-User-*` - ОТКЛОНЁН

BFF проставляет заголовки `X-User-Sub`, `X-User-Email` и т.п., монолит читает личность из них.

- Самописный trust-механизм: защита сводится к «заголовки принимаем только из внутренней сети», это соглашение, а не криптография.
- Дублирование claims в новый формат: маппинг, сопровождение, риск рассинхрона с токеном.
- Антипаттерн: стандартный механизм (Bearer JWT) уже решает задачу, заголовки - его самодельный аналог с меньшей гарантией.

### Вариант 2. Форвардинг access-токена: `Authorization: Bearer` + JWT-валидация на монолите - ВЫБРАН

BFF перед проксированием `/api/**` прикрепляет access-токен текущей сессии; монолит валидирует JWT сам (подпись Keycloak, issuer) и собирает `HttpContext.User` из claims.

- Стандартный механизм: `JwtBearer` middleware на монолите, никаких самодельных реализаций через заголовки.
- Личность в claims токена (`sub`, `email`, `email_verified`, `name`, `resource_access` для ADR 0024) - без промежуточного маппинга; JIT-провижининг (ADR 0020) читает те же claims.
- Свежесть токена гарантируется существующим конвейером: к моменту проксирования TokenRefreshMiddleware уже обновил тикет при необходимости.
- Монолит привязывается к формату токена Keycloak. Пример: в access-токене Keycloak поле `aud` (audience) по умолчанию содержит служебное значение `account`, а не имя нашего API, поэтому стандартную проверку audience в JWT-валидации придётся отключить или заменить собственной.
- Для проверки подписи токена монолиту нужны открытые ключи Keycloak: он периодически скачивает их (JWKS-эндпоинт, с кэшем и ротацией). Так появляется сетевое взаимодействие монолит -> Keycloak. Это осознанное исключение из правила «монолит в IAM не ходит»: пересылаются только публичные ключи подписи, никакие токены и данные личности между ними не ходят.

### Вариант 3. Token Exchange (RFC 8693) - ОТЛОЖЕН

BFF обменивает access-токен пользователя на токен с audience монолита.

- Плюсы: строгая audience, чистый путь к распределёнке (per-service audience).
- Минусы сейчас: доработки Keycloak (включение exchange, клиент-аудитория, permissions) и код обмена с кэшем на монолит-один - избыточно.
- Триггер: вынос первого сервиса из монолита (кандидат - realtime, ADR 0014). Оформляется отдельной ADR.

## Решение

Личность монолиту передаётся **форвардингом access-токена**: BFF на маршруте `/api/**` через **YARP request transform** (не middleware: трансформация относится к исходящему запросу) сбрасывает входящие `Authorization`/`Cookie` от клиента и прикрепляет access-токен текущей сессии в `Authorization: Bearer`. Монолит валидирует JWT (issuer = Keycloak, JWKS с кэшем) и строит `User` из claims; JIT-провижининг (ADR 0020) работает на этих же claims. Клиентский токен/заголовки к личности монолита допуска не имеют.

Порядок в конвейере: YARP - эндпоинт (`MapReverseProxy`), трансформ исполняется после всех middleware (Routing -> Authentication -> TokenRefresh -> SessionGuard -> Authorization), поэтому к моменту трансформации тикет гарантированно свеж, аноним отсечён с 401, rejected-сессия разлогинена.

## Последствия

- Поправка к формулировке ADR 0020 «монолит в IAM не ходит»: допускается рантайм-запрос за JWKS (открытые ключи подписи, с кэшем); токены и данные личности монолит в Keycloak по-прежнему не пересылает.
- Валидацию audience на монолите кастомизируем (access-токен Keycloak имеет `aud = account`).
- Монолит читает роли приложения из `resource_access` claims (ADR 0024) - механизм подтверждён применимым без изменений.
- При выносе первого сервиса: отдельная ADR на Token Exchange (вариант 3), форвардинг остаётся для монолита или заменяется - решается той записью.
- Диаграммы конвейера BFF дополняются YARP-трансформом (docs/diagrams).
