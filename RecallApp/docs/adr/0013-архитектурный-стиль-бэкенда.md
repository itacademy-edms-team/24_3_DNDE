# ADR 0013. Архитектурный стиль бэкенда: модульный монолит

- **Status:** accepted
- **Date:** 2026-10-17
- **Decision-maker(s):** Aleksandr
- **Owner:** Aleksandr
- **Scope:** Платформа (общее)

## Контекст

Доменные сервисы бэкенда нужно как-то структурировать и развернуть. В план фиксируется только стиль - §4 задаёт только принципы домена.

Домен уже размечен (План §2) и делится на естественные части с чёткими швами: контент, SRS, мультиплеер, геймификация, библиотека/поиск, учебные группы, профиль. Ключевой шов - **Контент - SRS** через контракт «Результат проверки», зависимость односторонняя (§4.1). Фичи реализуются итеративно (§3).

Разработку ведёт один человек. На старте нет ни нагрузки, ни команды, которые оправдывали бы распределённую систему. Необходимо выработать решение, которое в дальнейшем позволило бы из централизованной системы получить распределённую.

## Рассмотренные варианты

### Вариант 1. Распределённая микросервисная архитектура

Разделение системы на независимые сервисы с собственными базами данных, общение по HTTP/gRPC и через брокер сообщений.

- **Плюсы:**
  - Изолированное масштабирование отдельных высоконагруженных компонентов (прежде всего realtime-мультиплеер - §4).
  - Независимый цикл разработки и деплоя по сервисам.
  - Высокая отказоустойчивость: падение одного сервиса не ломает другие.
  - Разнородность стека - прямо ложится на исключение для AI/ML на Python (ADR 0012).
- **Минусы / почему отклонён:**
  - **Избыточная сложность.** Разработку ведёт один человек; ресурс на service-to-service авторизацию, service discovery и трассировку тратить нерационально.
  - **Консистентность данных.** Внутри домена нужна строгая транзакционность. Прогон Сессии атомарно обновляет Результаты проверки и SRS-записи сразу нескольких элементов (§2). Распределённые транзакции (Saga) кратно увеличат сроки и сложность.
  - **Рост инфраструктурных затрат.** Нужны более дорогие среды развёртывания и выделенные DevOps-компетенции, которых сейчас нет.

### Вариант 2. Классический монолит (неструктурированный)

Единое приложение без жёстких внутренних границ. Компоненты тесно связаны и нарушают доменные границы друг-друга.

- **Плюсы:**
  - Максимальная скорость написания кода на самых ранних этапах.
  - Полное отсутствие архитектурных ограничений для разработчика.
- **Минусы / почему отклонён:**
  - **Технический долг на старте.** Быстро превращается в «большой комок грязи» (Big Ball of Mud), неподдерживаемый при росте кодовой базы.
  - **Блокировка эволюции.** Без границ между компонентами будущий переход на микросервисы (когда станет экономически оправдан) практически невозможен без переписывания с нуля. А цель из контекста - сохранить путь к распределёнке.

### Вариант 3. Слоёный монолит по Clean Architecture

Единое приложение со строгой слоёной структурой (Entities/Core, Use Cases, Interface Adapters, Infrastructure) и правилом зависимостей внутрь, к домену. В отличие от варианта 2, архитектура есть и дисциплинирована. Но деление горизонтальное: вертикальных доменных модулей со своими контрактами и владением данными нет, use-cases всех доменов лежат в общих слоях.

- **Плюсы:**
  - Дисциплинированные слои и тестируемость: доменное ядро не зависит от инфраструктуры и фреймворков.
  - Правило зависимостей удерживает направление связей, не скатываясь в хаос варианта 2.
  - Одна БД, ACID, простой деплой.
- **Минусы / почему отклонён:**
  - Слои отвечают на «как устроен код», а не «на какие домены он разрезан». Контент, SRS, матчи живут в общих слоях, вертикальных границ между ними нет, связность между доменами растёт.
  - Для будущего выноса в сервис даёт мало: нет отцепляемого модуля с готовым контрактом, швы домена (§2) в коде не закреплены.
  - Плюсы Clean Architecture при отказе от этого варианта не теряются: она ортогональна и применяется внутри каждого модуля выбранного решения.

### Вариант 4. Модульный монолит

Единое развёртываемое приложение и одна БД, но строгая логическая изоляция доменов на уровне кода и интерфейсов. Каждый модуль владеет своей схемой данных, доступ к ней - только через публичный контракт этого модуля.

- **Плюсы:**
  - Скорость разработки и дешевизна инфраструктуры как в вариантах 2-3, но с сохранением чистоты архитектуры и дешёвым путём миграции на микросервисы (снимает главный минус варианта 1).
  - Границы заданы доменом (§2): ключевой шов Контент - SRS через контракт «Результат проверки», зависимость односторонняя (§4.1).
  - Clean Architecture ортогональна и применяется внутри каждого модуля (плюсы варианта 3 сохраняются).
- **Минусы:**
  - Изоляция держится дисциплиной, а не физической границей: легко случайно дёрнуть чужой модуль или сделать JOIN через общую БД. Нужен контроль - тесты архитектуры, ревью.
  - Деплой общий: релиз или падение одного модуля затрагивает весь процесс, независимого деплоя нет.

## Решение

Бэкенд строим как **модульный монолит** (вариант 4): единое развёртываемое ASP.NET-приложение (ADR 0012) с одной БД, внутри - модули по доменным границам из Плана §2. Каждый модуль владеет своей схемой данных, доступ к ней - только через публичный контракт модуля. Это берёт скорость и дешевизну эксплуатации монолита (варианты 2-3), но сохраняет вертикальные границы доменов и дешёвый путь миграции к распределёнке (снимая главный минус варианта 1). Внутреннее устройство модуля (слои, Clean Architecture из варианта 3) - деталь реализации уровня L3, вне этой записи.

Правила изоляции модулей:
- модуль владеет своими данными; другой модуль обращается к ним только через публичный контракт модуля, не в чужие таблицы напрямую;
- зависимости между модулями однонаправленные там, где это задано доменом (SRS знает про Контент, Контент про SRS - нет, §4.1).

**Критерии выноса модуля в отдельный сервис**:
- модулю нужна иная модель масштабирования или иной рантайм-профиль, чем у остального;
- модуль создаёт нагрузку, мешающую остальным;
- первый кандидат - **realtime-мультиплеер**: отдельный слой, одиночное обучение от него не зависит (§4, ставка про realtime), транспорт иной. Детали в отдельной ADR.

Вынос - следствие по критериям, а не плановый этап. Пока причин нет, всё живёт в выбранной архитектуре в одном монолите.

## Последствия

- Возможное исключение на L2 уже сейчас: realtime-узел может оказаться отдельным контейнером из-за иного транспорта (WebSocket). Решается в отдельной ADR.
- Модули растут по итерациям (§3): контент/аккаунт/создание (MVP), SRS/форматы/библиотека (core), геймификация/мультиплеер (social).
- Изоляция держится дисциплиной, в которой нужен контроль границ (ревью, тесты архитектуры), иначе монолит деградирует в слоёный.
- Дверь к распределению открыта без переписывания: модуль с готовым контрактом выносится в сервис по критериям выше. BFF (ADR 0002) уже прячет разрозненность бэкенда от клиентов, поэтому вынос не затронет фронтенд.
