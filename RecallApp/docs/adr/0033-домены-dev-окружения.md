# ADR 0033. Доменная модель dev-окружения: узлы в общей зоне `*.recallapp.localhost`

- **Status:** accepted
- **Date:** 2026-11-04
- **Decision-maker(s):** Aleksandr
- **Owner:** Aleksandr
- **Scope:** Платформа (общее)

## Контекст

ADR 0026 зафиксировал единую точку входа (edge Nginx на `:443`) и host-маршрутизацию dev-узлов, назвав их `app.localhost`, `bff.localhost`, `auth.localhost`. При подъёме SPA (C3) эта связка не заработала: после успешного входа SPA продолжал видеть гостя и уходил на `/login` по кругу.

Причина - в определении «сайта» у браузера. Для cookie `site` = схема + **registrable domain** (eTLD+1). У `app.localhost` и `bff.localhost` registrable domain - сам `localhost`, то есть они находятся на **одном сайте**, но cookie сессии BFF выставляется как host-only для `bff.localhost` (ADR 0021), а запрос из `app.localhost` в `bff.localhost` - это кросс-origin запрос **внутри одного сайта**, где `SameSite=Lax` не помогает: Lax разрешает отправку cookie только для top-level навигации, а `fetch`/XHR кросс-origin её не получает. В DevTools запрос выглядит как «cookie blocked». Навигация на `/login` при этом cookie видит (top-level переход), поэтому сервер отвечает редиректом обратно в SPA, а SPA снова видит анонима.

`SameSite=Lax` - принятое и обоснованное решение (ADR 0021). Менять нужно имена узлов.

Ключевые ограничения:

- Сессия - cookie сервера BFF, host-only, `SameSite=Lax`. Из JS доступ к ней не планируется.
- Вход и выход - top-level навигация и form-POST (ADR 0023, ADR 0030).
- Dev должен стараться повторять прод по схеме взаимодействия (ADR 0030), иначе дефекты проявятся только в проде.
- Механизм должен переживать появление новых узлов (back-office, realtime) без переделки cookie-политики.

## Рассмотренные варианты

### Вариант 1. Все прикладные узлы в одной зоне `*.recallapp.localhost` - ВЫБРАН

`app.recallapp.localhost` (SPA), `bff.recallapp.localhost` (BFF). Общая зона даёт общий registrable domain `recallapp.localhost`, то есть оба узла - один сайт; при этом cookie остаётся **host-only на `bff.*`**, потому что отправляется на тот же origin, куда идёт запрос.

- Работает без изменения политики cookie: `SameSite=Lax` остаётся, `Secure`/`HttpOnly` остаются.
- Dev воспроизводит прод-схему «SPA и API на родственных субдоменах» - ровно то, что выбиралось в ADR 0030.
- Зона расширяемая: новый узел (`admin.*`, `ws.*`) добавляется в ту же зону и не требует пересмотра cookie.
- `*.localhost` резолвится в loopback без правки hosts-файла (Windows 11 - через встроенный резолвер; браузеры трактуют `*.localhost` как loopback по спецификации).

### Вариант 2. `SameSite=None` для dev - ОТКЛОНЁН

Cookie с `SameSite=None; Secure` действительно уходит в кросс-сайт запросах.

- Прод-поведение не воспроизводится: там по-прежнему нужен общий домен, и дефект просто переезжает в прод.
- Chrome блокирует сторонние cookie по умолчанию, Safari/ITP - тоже; отладка превращается в борьбу с политиками браузера, а не с кодом.
- Разные политики cookie в dev и prod - источник дефектов «у меня на машине всё работает».

### Вариант 3. Порты вместо доменов (`localhost:5173`, `localhost:8080`) - ОТКЛОНЁН

- Для `SameSite` порт значения не имеет, то есть сессия бы заработала, но только потому, что dev стал бы не похож на прод: в проде SPA и BFF - разные хосты, `redirect_uri` и issuer завязаны на хосты, CORS - на origin'ы с портами.
- Все различия dev/prod собрались бы в одном месте и проявились при первом же деплое.
- Регистрация `redirect_uri` в Keycloak включает порт - пришлось бы держать два набора значений.

### Вариант 4. Cookie на родительский домен (`Domain=.recallapp.localhost`) - ОТКЛОНЁН

- Cookie стала бы доступна любому будущему поддомену, включая те, что появятся для служебных нужд: расширение поверхности без необходимости.
- Host-only cookie на `bff.*` достаточно: SPA к cookie не обращается, её отправляет сам браузер на тот же origin.

## Решение

### Узлы dev-окружения

| Узел | Dev-адрес | Куда маршрутизирует edge | Cookie-контекст |
|---|---|---|---|
| SPA | `https://app.recallapp.localhost` | `client-web:5173` (Vite dev-сервер) | своих cookie не имеет |
| BFF | `https://bff.recallapp.localhost` | `bff:8080` | host-only `recall_bff`, `SameSite=Lax` |
| Keycloak | `https://auth.localhost` | `iam:8080` | свои cookie на своём origin |

Правила:

- **Все прикладные узлы живут в зоне `*.recallapp.localhost`.** Новый узел добавляется только в эту зону: смена зоны - отдельная ADR, потому что меняет cookie и CORS.
- **Cookie сессии BFF остаётся host-only на `bff.recallapp.localhost`.** На родительский домен её не расширяем.
- **`SameSite=Lax` не меняется** (ADR 0021). Это ограничение, а не неудобство: если какой-то сценарий требует `None`, значит сценарий требует пересмотра архитектуры, а не послабления cookie.
- **`auth.localhost` остаётся вне зоны** осознанно: cookie Keycloak участвует только в top-level переходах на собственный origin, а смена хоста потянула бы перерегистрацию `redirect_uri`/issuer без выгоды.
- **Внутри docker-сети узлы доступны по тем же именам** через сетевые алиасы edge-прокси (ADR 0026): issuer, `redirect_uri` и `X-Forwarded-*` совпадают снаружи и внутри, поэтому отдельной конфигурации для «внутреннего» адреса нет.
- **TLS-сертификат покрывает всю зону** (SAN на `*.recallapp.localhost` и `auth.localhost`), выпускается локальным Root CA (ADR 0026).

### Почему домены, а не `localhost` с портами

`localhost` как имя для нескольких узлов не даёт браузеру отличить «свой/чужой» сайт так, как это будет в проде: dev обязан повторять схему «SPA и API на родственных субдоменах». Порты этого не моделируют и добавляют различия, которых в проде не будет.

## Последствия

- SPA обращается к BFF по абсолютному `https://bff.recallapp.localhost` (ADR 0030): base URL берётся из окружения, в коде не хардкодится.
- В dev дополнительно разрешены `http://localhost:5173` и `http://localhost:5179` (запуск Vite без прокси) - это ослабление только для прямого запуска клиента, сессионные сценарии в них не работают.
- Появление silent renew / iframe-проверки сессии Keycloak потребует переезда `auth.*` в общую зону: сторонние cookie в iframe заблокированы, и сценарий перестанет работать. Это известное ограничение текущей модели.
- Прод-топология (домены, TLS, оркестрация) этой записью не покрывается - она отложена в ADR 0026 и будет решаться отдельной записью; модель зоны переносится на прод без изменения принципа.
- При добавлении узла обновляются: server-блок edge-proxy, SAN сертификата, при необходимости - CORS-allowlist BFF.
- Известный долг: HMR через edge-proxy (websocket) в этой схеме пока не работает, чинится отдельно; на доменную модель не влияет.
