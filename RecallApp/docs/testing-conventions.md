# Конвенции тестирования

Правила, общие для BFF, монолита и клиента. Отвечают на два вопроса: **какие тесты пишем** и **где их запускать**. Инструкции по конкретным наборам живут рядом с кодом: [Bff/Bff.Web/tests/README.md](../Bff/Bff.Web/tests/README.md), [App/tests/README.md](../App/tests/README.md).

## 1. Среда-зависимые тесты

Часть поведения нельзя проверить без внешней среды: живой PostgreSQL, настоящий Keycloak, реальный браузер. Такие тесты не выкидываем и не «ослабляем», а помечаем так, чтобы они не падали там, где необходимой среды нет.

**Два независимых механизма** - оба нужны, и оба ставятся руками:

| Механизм | Что делает | Где живёт |
|---|---|---|
| `[DatabaseFact]` / `[KeycloakFact]` | пропускает тест (`Skip`), если среды нет: по `ConnectionStrings__AccountsMigrations` и по `KeycloakTests__*` | App (Database), BFF (Keycloak) |
| `[Trait("Category", "...")]` | даёт фильтр для локального прогона и разбиение в отчёте | классы интеграционных тестов |

Категории в проекте: `Database` (живая `app_db`), `Keycloak` (настоящий Keycloak), `InProcess` (конвейер хоста без внешних зависимостей, BFF). Тесты `Tests.Architecture` и интеграционные тесты App без внешних зависимостей категории не имеют - они и так запускаются везде.

Правила:

- **Факт-атрибут, а не `if` внутри теста.** `DatabaseFact`/`KeycloakFact` сами пропускают тест с подсказкой, чего не хватает. Отдельный «флаг-включкатель» не заводим, и ранний `return` вместо `Skip` тоже: тест, который молча ничего не проверил и остался зелёным, хуже отсутствующего - он создаёт ложную уверенность в правильности работы решения.
- **Атрибут не заменяет trait.** Факт-атрибут ничего не выставляет в фильтры: `Category` навешивается отдельно, иначе `Category!=Database` тест не исключит.
- **Часы и внешние ответы подделываются на уровне хоста**, а не внутри тестируемого класса: `FakeTimeProvider` подменяет `TimeProvider` в DI, `FakeKeycloak` - HTTP-обработчик token endpoint. Тестируемый код про подделку не знает.

## 2. Интеграционные тесты - только на реальных контейнерах

**Моки БД и IAM запрещены.** Никакого EF InMemory, поддельного PostgreSQL, «удобного» фейкового Keycloak вместо настоящего в сценариях БД/IdP. Ломается обычно именно на границе: SQL и миграции, состав claims, cookie и редиректы, поведение token endpoint. Тест, который этот стык подменяет, проверяет нашу фантазию, а не систему.

Что допустимо:

- **`WebApplicationFactory` (InProcess)** - для проверки собственного конвейера хоста: middleware, валидация опций, коды ответов, маршруты. Keycloak в таких тестах подделывается на уровне HTTP (`FakeKeycloak`), потому что проверяется реакция на протокол, а не сам IdP.
- **Тестовая аутентификация** - `TestAuth` (заголовок `X-Test-Auth`) и подмена claim `X-Test-Sub` в `AppFactory`. Это **исключение для проверки отказов**: анонимный запрос, невалидный `sub`, отсутствие прав. Такая схема не заменяет интеграцию с IAM: сценарии входа, ролей и refresh проверяются категорией `Keycloak` против настоящего IdP.
- **Поддельные часы** - они не являются моком внешней системы, а способом воспроизвести истечение токена без ожидания.

Правило выбора: если тест проверяет поведение, которое зависит от реальной БД или реального IdP, он **обязан** иметь соответствующую категорию и запускаться в контейнере. Упростить проверку ради скорости нельзя - можно только переместить её в профиль `test` для проверки в контейнере.

Данные в тестах: миграции применяет инфраструктура теста (`DatabaseFixture`), каждый тест работает со своим `sub`, поэтому изоляция достигается уникальностью данных, а не очисткой БД между тестами.

## 3. Клиент: только реальный браузер

- **Единственный раннер - Vitest в browser mode** (`vite.config.ts`, провайдер Playwright, Chromium). Перед первым запуском: `npx playwright install chromium`.
- **jsdom и testing-library не используются** и не добавляются. Тесты должны видеть настоящий layout, CSS и события браузера, а не эмуляцию DOM: именно так уже были пойманы реальные баги.
- **Mobile-first.** Вьюпорт зафиксирован `390×844`; тесты описывают мобильное поведение (навбар за экраном, выезд по бургеру, скрытые desktop-элементы). Подгонять тест под desktop-вьюпорт нельзя - поведение на десктопе проверяется отдельно, если нужно.
- **Сеть стабилизируется через `fetch`**: `vi.stubGlobal("fetch", ...)`; поэтому транспортный клиент обязан создаваться с `adapter: "fetch"` (иначе axios уходит в XHR мимо стаба и тест использует не то, что нужно, и считается невалидным).

## 4. Где что запускать

### Бэкенд: BFF

Из `Bff/Bff.Web`:

```powershell
dotnet test tests/Tests.Unit
dotnet test tests/Tests.Integration --filter "Category!=Keycloak"
```

Категория `Keycloak` без переменных `KeycloakTests__*` пропускается; секрет клиента и пароль тестового пользователя - в корневом `.env` (`BFF_TEST_OIDC_CLIENT_SECRET`, `BFF_TEST_USER_PASSWORD`). За подробностями смотрите `.env.example`.

Полный прогон в контейнере (из корня `RecallApp`, нужен поднятый стек):

```powershell
$env:BFF_TEST_FILTER='Category!=Keycloak'
docker compose --profile test run --rm --build bff-tests

# всё, включая Keycloak (нужен тестовый realm):
docker compose --profile test run --rm --build bff-tests
```

Отчёты доступны по пути: `Bff/Bff.Web/tests/TestResults/`.

### Бэкенд: монолит App

Из `App/`:

```powershell
dotnet test
```

Полный прогон в контейнере (тесты `Database` применяют миграции к `app_db`):

```powershell
# полный
docker compose --profile test run --rm --build app-tests

# без БД:
$env:APP_TEST_FILTER='Category!=Database'
docker compose --profile test run --rm app-tests

# только Database:
$env:APP_TEST_FILTER='Category=Database'
docker compose --profile test run --rm app-tests
```

Отчёты доступны по пути: `App/tests/TestResults/`. Тесты `Database` без `ConnectionStrings__AccountsMigrations` пропускаются.

### Клиент

Из `Client/Client.Web`:

```powershell
npm test            # один прогон, Vitest browser mode
npm run test:watch  # режим разработки
npm run typecheck
npm run lint
```

### Минимум перед коммитом

- BFF: `Tests.Unit` + `Tests.Integration` без `Keycloak`;
- App: `dotnet test` (или `Category!=Database` в контейнере);
- клиент: `npm test`, `npm run typecheck`, `npm run lint`.

Полный набор в профиле `test` (включая `Database` и `Keycloak`) выполняется перед PR или на изменения, затрагивающие схему БД, сессию или IAM.
