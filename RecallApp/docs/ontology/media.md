# Ontology: модуль Media (файлы изображений)

> Статус: черновик (заполнены §1–§8 и §10; §9, §11 - позже, 2026-11-13).
> Назначение: детализация модуля из [карты](./README.md). Структура разделов повторяет [Accounts](./accounts.md).
> Источники: карта модулей (README, п. 7), ADR 0008 (объектное хранилище), ADR 0017 (presigned-ссылки), ADR 0018 (безопасность файлов), ADR 0029 (схема на модуль), ADR 0036 (границы транзакций и данных), ADR 0037 (media-срез: загрузка и обработка).

## 1. Предметная область и границы модуля

Модуль Media - владение файлами изображений и их производными вариантами. Принимает загрузку напрямую в объектное хранилище по одноразовой подписи, подтверждает факт загрузки, перекодирует изображение в WebP нужных размеров со снятием метаданных, выдаёт временные ссылки на чтение и удаляет объекты. Фоном убирает осиротевшие файлы из хранилища и из своей схемы (незавершённые загрузки и объекты, на которые никто не ссылается). О том, что файл используется, Media узнаёт не сама: потребитель (Sets) присылает ей конкретные ссылки на файл (непрозрачный ключ вида `set:{id}:element:{id}:front`), Media хранит их строками, считает и по числу ссылок решает, можно ли удалять объект.

**Внутри модуля:**
- **Медиа-объект** - запись о файле: идентификатор, владелец, состояние, метаданные (размер, ширина/высота, формат), набор производных вариантов; объекты живут в схеме `media` со своими миграциями (ADR 0029).
- **Жизненный цикл загрузки**: инициализация (presigned POST с политикой, ADR 0017), подтверждение после фактической загрузки (HEAD + проверка), переход в готовность, удаление.
- **Обработка изображения**: проверка сигнатуры формата, ограничения до декодирования, перекодирование в WebP со снятием метаданных, нарезка вариантов отображения - `thumb` (<= 400 px) и `display` (<= 1600 px); каждый вариант - отдельная запись в схеме `media` (ADR 0037, ADR 0018).
- **Выдача ссылок на чтение**: presigned GET с коротким TTL; ключи объектов и их схема - ответственность модуля.
- **Сборка мусора**: брошенные загрузки в состоянии `pending`, временные ключи, объекты удалённых записей.

**Сознательно снаружи:**
- **Роли, аутентификация, личность** - Keycloak/BFF (ADR 0001/0024/0035); `owner_id` - доменное отношение, а не роль.
- **CDN, кеширование на периметре, инвалидация** - инфраструктура развёртывания; контракт модуля - только временная ссылка.
- **Что с файлом связано** - Sets. Модуль не хранит `element_id`/`set_id` и не знает, какой именно элемент ссылается на файл; он ведёт строки ссылок (непрозрачные ключи, которые ему даёт потребитель) и их количество (граница по ADR 0036). Борьба с «висящими» ссылками в payload элемента - забота Sets.
- **Жизненный цикл привязки** - Sets: когда привязка появляется и когда снимается, решает владелец набора; Media принимает сообщение и не удаляет используемый файл.
- **Право прикреплять изображение к элементу** - Sets (владение набором). Media проверяет только владение самим файлом.
- **Публичный каталог и модерация** - Organization и back-office (ADR 0004). Media не решает, можно ли показывать файл публично: это следует из видимости набора (ORG-02).
- **Аудио, видео, PDF, аватары профиля** - вне текущего среза. Модуль проектируется как «изображения карточек», расширение типов - отдельное решение.
- **Антивирусная проверка и распознавание контента** - не реализуется: защита строится на allow-list форматов, лимитах и перекодировании (ADR 0018).
- **Байты в БД** - нет: файлы лежат в S3-совместимом хранилище (ADR 0008), в БД только метаданные.

**Зафиксированные ограничения среза** (из ADR 0037):
- форматы: PNG, JPEG, WebP; SVG запрещён (активный контент); анимация (GIF/APNG/анимированный WebP) отклоняется с кодом `Media.UnsupportedAnimation`;
- лимиты: 10 МБ на файл, 25 Мп и 8000 px по стороне - до декодирования;
- варианты: `display` <= 1600 px, `thumb` <= 400 px, оба WebP; исходник после обработки удаляется;
- загрузка идёт клиентом напрямую в хранилище, через API байты не проходят;
- ссылка на чтение живёт 15 минут.

## 2. Ubiquitous Language

| Термин                          | Определение                                                                                                                                                | Не путать с                                                                          |
|---------------------------------|------------------------------------------------------------------------------------------------------------------------------------------------------------|--------------------------------------------------------------------------------------|
| **Медиа-объект** (media object) | Запись о загруженном изображении: владелец, статус, метаданные, два готовых варианта. Идентифицируется `mediaId`                                           | объектом в хранилище (это байты по ключу); файлом в БД (байтов в БД нет)             |
| **Исходник** (source)           | Файл, который загрузил пользователь: временный объект `tmp/{uploadId}`. Живёт только до успешной обработки                                                 | «оригиналом», который остаётся навсегда - его мы не храним                           |
| **Вариант** (variant)           | Уменьшенная перекодированная копия картинки для показа: `thumb` (<= 400 px) или `display` (<= 1600 px). Отдельный объект хранилища со своим ключом и весом | исходником; «версией» файла (версионирования нет)                                    |
| **Обработка** (processing)      | Проверки после загрузки и перекодирование: сигнатура, лимиты, WebP, варианты. Часть `confirm`, не отдельная операция                                       | загрузкой байтов - она уже завершена                                                 |
| **Ссылка** (reference)          | Ключ, которым потребитель сообщает, что файл используется. Для Media - непрозрачная строка                                                                 | FK на элемент; Media не знает, что такое элемент                                     |
| **Слот** (slot)                 | Часть ссылки, обозначающая место использования (`...:front`). Существует в одном экземпляре: замена картинки перезаписывает слот                           | «привязкой» (attach) как отдельным событием - синхронизация декларативна             |
| **Потребитель** (consumer)      | Модуль, который ссылается на файлы: сейчас Sets                                                                                                            | пользователем; потребитель - не человек и не роль                                    |
| **Владелец** (owner)            | Пользователь, загрузивший файл. Только он видит файл и получает ссылки на чтение                                                                           | потребителем; владелец файла != владелец набора                                      |
| **Политика загрузки**           | Подписанный набор ограничений для POST в хранилище: ключ, `content-type`, диапазон размера, срок 10 минут                                                  | «токеном доступа»: это не полномочие, а одноразовое разрешение на запись             |
| **Инициализация** (`init`)      | Первый шаг загрузки: создаётся `pending`, выдаётся политика                                                                                                | загрузкой; на `init` байты не идут                                                   |
| **Подтверждение** (`confirm`)   | Второй шаг: проверка объекта в хранилище, обработка, переход в `ready` или `failed`                                                                        | фоновой обработкой; `confirm` вызывает клиент                                        |
| **Сирота** (orphan)             | Файл без хозяина: `pending`, который не подтвердили, или `ready`, на который никто не ссылается                                                            | мусором в общем смысле - у сироты есть запись, которую мы убираем                    |
| **Транзиентный сбой**           | Отказ инфраструктуры (S3, таймаут, память). Статус не меняется: файл остаётся `pending` и его можно подтвердить заново                                     | `failed` - окончательная непригодность самого файла                                  |
| **Аренда** (lease)              | Техническая метка «этот `confirm` сейчас выполняется мной» с ограниченным сроком и продлением                                                              | блокировкой навсегда: после истечения срока работу выполняет заново следующий запрос |

## 3. Сущности и атрибуты

### 3.1. `MediaObject`

| Атрибут                               | Тип                    | Владелец            | Правило                                                                    |
|---------------------------------------|------------------------|---------------------|----------------------------------------------------------------------------|
| `id`                                  | uuid, PK               | домен               | генерируется при `init`, служит `mediaId` в контракте                      |
| `owner_id`                            | uuid, NOT NULL, индекс | Accounts (значение) | из `ICurrentUser`, без FK;                                                 |
| `status`                              | enum, NOT NULL         | домен               | `pending` / `ready` / `failed` / `deleted`, переходы по §6.1               |
| `declared_content_type`               | text, NOT NULL         | домен               | что заявил клиент на `init`; вшивается в policy                            |
| `source_format`                       | enum, NULL             | домен               | определён по сигнатуре на `confirm` (`png`/`jpeg`/`webp`)                  |
| `source_size_bytes`                   | bigint, NULL           | домен               | фактический размер загруженного файла (из `HEAD`)                          |
| `width`, `height`                     | int, NULL              | домен               | размеры оригинала в пикселях, до перекодирования                           |
| `failure_code`, `failure_description` | text, NULL             | домен               | только для `failed`: код из реестра `Media.*` + описание для лога          |
| `upload_expires_at`                   | timestamptz, NOT NULL  | домен               | конец окна доверия к загрузке (10 минут); после него `confirm` отклоняется |
| `created_at`                          | timestamptz, NOT NULL  | домен               | момент `init`                                                              |
| `updated_at`                          | timestamptz, NOT NULL  | домен               | любое изменение записи                                                     |
| `ready_at`                            | timestamptz, NULL      | домен               | момент успешной обработки; от него считается окно чистки «без ссылок»      |
| `deleted_at`                          | timestamptz, NULL      | домен               | момент перевода в `deleted`                                                |

Индексы: `(owner_id, created_at DESC)` для списка своих файлов; `(status, created_at)` для фоновой чистки; `(status, ready_at)` для удаления `ready` без ссылок.

### 3.2. `MediaVariant`

| Атрибут           | Тип                                              | Правило                                                                |
|-------------------|--------------------------------------------------|------------------------------------------------------------------------|
| `media_id`        | uuid, FK -> `media.media_objects` (внутри схемы) | удаляется вместе с объектом                                            |
| `variant`         | enum `thumb` / `display`                         | часть составного PK                                                    |
| `object_key`      | text, NOT NULL                                   | `media/{ownerId}/{mediaId}/{variant}.webp`, собирается доменом         |
| `width`, `height` | int, NOT NULL                                    | фактический размер варианта (длинная сторона в пределах своего лимита) |
| `size_bytes`      | bigint, NOT NULL                                 | вес объекта после перекодирования                                      |
| `created_at`      | timestamptz, NOT NULL                            | момент обработки                                                       |

PK - `(media_id, variant)`: два варианта на файл - это и есть весь набор. Оригинал в таблице не живёт: после перекодирования он удаляется из хранилища.

### 3.3. `MediaReference` (ссылка на файл из потребителя)

| Атрибут                    | Тип                               | Правило                                                                                        |
|----------------------------|-----------------------------------|------------------------------------------------------------------------------------------------|
| `id`                       | uuid, PK                          | генерируется сервером                                                                          |
| `media_id`                 | uuid, FK -> `media.media_objects` | ссылка живёт, пока жив файл                                                                    |
| `reference`                | text, NOT NULL, UNIQUE            | слот, который задаёт потребитель (`set:{setId}:element:{elementId}:front`); уникален глобально |
| `created_at`, `updated_at` | timestamptz, NOT NULL             | `updated_at` меняется при перезаписи слота на другой `mediaId`                                 |

Владелец ссылки отдельно не хранится: он берётся из `media_objects.owner_id` через FK внутри схемы.

Уникальность по `reference`, а не по паре (`media_id`, `reference`) - иначе замена картинки оставит две строки на один слот (§6.4). Индекс по `media_id` для подсчёта ссылок при удалении.

Смысл `reference` Media не разбирает: это непрозрачный ключ потребителя. Префикс `set:` используется только для массового удаления при удалении набора, как строковый шаблон.

## 4. Агрегаты и границы

### 4.1. `MediaObject` - агрегат файла

**Корень:** `MediaObject`. **Внутри:** его варианты `MediaVariant`.

Инварианты, которые держит корень:
- переходы статусов только по §6.1, и только через методы (`MarkReady`, `MarkFailed`, `MarkDeleted`);
- в `ready` есть ровно два варианта (`thumb`, `display`), в `pending`/`failed` - ни одного;
- ключи вариантов выводятся из `owner_id`/`id` и снаружи не принимаются;
- `failed` всегда имеет `failure_code`; в `ready` этот код пуст.

Варианты меняются только вместе с файлом (создаются при обработке, удаляются при удалении файла), поэтому живут в том же агрегате.

### 4.2. `MediaReference` - отдельный агрегат

Ссылок у файла может быть много, и они меняются пачкой при каждом сохранении элемента. Держать их внутри `MediaObject` значило бы загружать все ссылки ради одной вставки и ловить конфликты на весь агрегат.

Поэтому строка ссылки - **самостоятельный корень**: инвариант «слот уникален» держит уникальный индекс, переход «слот смотрит на другой файл» - один `UPDATE`.

### 4.3. Правило, которое не живёт в одном агрегате

«Нельзя удалить файл, пока на него есть ссылки» - межагрегатное правило. Держим его в слое приложения, в одной транзакции с изменением статуса файла: `count(references where media_id = @id) > 0` -> `409 Media.InUse`, иначе `ready` -> `deleted`. Гонка «между подсчётом и удалением» закрывается тем, что удаление и синхронизация ссылок идут в одной БД и уникальность слота не даёт вставить ссылку на удаляемый файл повторно (проверка `ready` при синхронизации).

### 4.4. Границы транзакций

| Операция                      | Транзакция                                                                                                                                     |
|-------------------------------|------------------------------------------------------------------------------------------------------------------------------------------------|
| `init`                        | одна короткая: строка `pending`                                                                                                                |
| `confirm`                     | две: короткие отметки аренды идемпотентности (до/после) + одна на переход в `ready` с вариантами; работа с S3 и SkiaSharp - **вне** транзакции |
| Синхронизация ссылок элемента | одна на весь набор слотов элемента (все или ничего)                                                                                            |
| `DeleteMedia`                 | одна: проверка ссылок и переход в `deleted`                                                                                                    |
| Фоновая чистка                | батчами, каждый батч в своей транзакции                                                                                                        |

## 5. Value Objects

| VO                | Состав                                       | Правила                                                                                                                                                                                                              |
|-------------------|----------------------------------------------|----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| `ObjectKey`       | строка                                       | формат `tmp/{uploadId}` на время загрузки или `media/{ownerId}/{mediaId}/{variant}.webp` после обработки; относительный, без ведущего слэша и `..`; до 512 символов; собирается только доменом, клиент его не задаёт |
| `MediaStatus`     | enum `pending`, `ready`, `failed`, `deleted` | переходы только по §6.1; `ready` -> `pending` и `failed` -> `ready` невозможны (повторная загрузка - новый `mediaId`)                                                                                                |
| `VariantName`     | enum `thumb`, `display`                      | закрытый список; в пределах одного файла вариант ровно один; длинная сторона: `thumb` <= 400 px, `display` <= 1600 px                                                                                                  |
| `ImageFormat`     | enum `png`, `jpeg`, `webp`                   | определяется по сигнатуре (magic bytes), а не по заголовку; SVG и прочее - `Media.InvalidFormat`; анимация - `Media.UnsupportedAnimation`                                                                            |
| `ImageDimensions` | `width`, `height` в пикселях                 | > 0; ни одна сторона не больше 8000 px; площадь не больше 25 Мп; проверяется до декодирования                                                                                                                        |
| `MediaSize`       | целое, байты                                 | от 1 до 10 485 760 (10 МБ); на `init` проверяется заявленный размер, на `confirm` - фактический                                                                                                                      |
| `MediaReference`  | строка-слот                                  | `{consumer}:{scope}:...` (например `set:{setId}:element:{elementId}:front`); непустая, до 200 символов; уникальна в пределах модуля; смысл ключа Media не разбирает                                                  |
| `MediaFailure`    | код + описание                               | только для `failed`; код из реестра `Media.*`, клиенту уходит код, описание - в лог                                                                                                                                  |

`owner_id` - не value object, а значение из `ICurrentUser` (ссылка без FK, ADR 0036). Аренда идемпотентности (`lease_until`) - техническое состояние, не доменный VO.

Где что валидируется (ADR 0038): форма запроса (заявленный `content-type`, размер) - в HTTP-слое; правила команды (лимит одновременных `pending`, белый список типов на `init`) - в валидаторе; инварианты (формат по сигнатуре, размеры, переходы статусов, формат ключа) - в VO и сущности, потому что они не зависят от способа вызова.

## 6. Политики

### 6.1. Жизненный цикл статусов

| Переход                 | Условие                                                                                                  | Обратный переход                          |
|-------------------------|----------------------------------------------------------------------------------------------------------|-------------------------------------------|
| `pending` -> `ready`    | `confirm` прошёл все проверки, варианты созданы, исходник удалён                                         | нет                                       |
| `pending` -> `failed`   | файл окончательно не годится (формат, анимация, лимиты, битые данные) или объекта нет (ленивая проверка) | нет: повторная загрузка - новый `mediaId` |
| `ready` -> `deleted`    | удаление владельцем при нуле ссылок, либо фон при нуле ссылок старше 24 ч                                | нет                                       |
| `failed` -> `deleted`   | фон через 24 ч                                                                                           | нет                                       |
| `pending` -> `deleted`  | фон через 24 ч                                                                                           | нет                                       |

Инфраструктурный сбой (S3, таймаут, память) статус не меняет: `pending` остаётся, `confirm` можно повторить.

### 6.2. Загрузка и выдача разрешения

- Ключ объекта и `mediaId` назначает сервер; клиент не может выбрать путь или перезаписать чужой объект.
- Политика живёт 10 минут, `content-length-range` 1..10 МБ, `content-type` из белого списка - всё это проверяет хранилище до приёма байт.
- На `init` отклоняются: размер > 10 МБ, неподдерживаемый `content-type`, превышение лимита одновременных `pending` (5 на пользователя), rate-limit.
- Файл без `confirm` не существует для системы: ссылок нет, прикрепить нельзя.

### 6.3. Проверки и обработка

- Формат - по сигнатуре (magic bytes), а не по заявленному `content-type`: PNG / JPEG / WebP. SVG и прочее - отказ.
- Анимация (GIF) отклоняется с `Media.UnsupportedAnimation` (молчаливый первый кадр не допускается).
- Лимиты до декодирования: 25 Мп и 8000 px по стороне - защита от декомпрессионных бомб.
- Обязательное перекодирование в WebP со снятием метаданных (EXIF, ICC); исходник после успеха удаляется.
- Варианты `thumb` <= 400 и `display` <= 1600; ключи детерминированы (`media/{ownerId}/{mediaId}/{variant}.webp`), поэтому повторная обработка перезаписывает те же объекты, а не плодит новые.

### 6.4. Ссылки и удаление

- Ссылка - непрозрачный для Media ключ, который даёт потребитель (`set:{setId}:element:{elementId}:front`); одна строка = одна привязка, уникальность по паре (`media_id`, `reference`).
- Повторная синхронизация того же набора ссылок безопасна: вставка существующей ссылки игнорируется, удаление несуществующей - не ошибка (at-least-once из outbox).
- `DeleteMedia` при ненулевых ссылках -> `409 Media.InUse`; при нуле - `ready` -> `deleted`, объекты удаляются.
- `ready` без ссылок старше 24 ч удаляется фоновой чисткой. Окно выбрано с запасом: outbox повторяет доставку секундами, так что потеря ссылки за 24 ч маловероятна; если такое случится, карточка покажет заглушку (§10 п. 7).
- Смена изображения у элемента - это смена набора ссылок в том же сохранении, отдельный detach не нужен.

### 6.5. Владение и доступ к чтению

- Чужой и несуществующий файл неразличимы: 404 во всех случаях (тот же принцип, что в онтологии Sets §6.4).
- Ссылки на чтение выдаются только владельцу, TTL 15 минут; ссылка не кешируется в данных клиента и запрашивается заново после истечения.
- Публичной выдачи нет до появления видимости наборов (ORG-02): тогда появятся публичные объекты и отдельный домен отдачи, без переделки модуля.
- `Content-Disposition: inline` и принудительный `Content-Type` на уровне объекта и заголовков отдачи.

### 6.6. Идемпотентность операций

- `init` - короткая операция (только БД): режим A, `Idempotency-Key` обязателен; повтор возвращает ту же политику, пока она не истекла; тот же ключ с другим телом -> 409.
- `confirm` - долгая операция (сеть + CPU): режим B, ключ сразу фиксируется как `in_progress` с арендой 60 с, продление каждые 20 с; второй запрос при живой аренде -> `409 Idempotency.InProgress`; финализация только если аренда всё ещё своя; после истечения аренды следующий запрос выполняет работу заново.
- Повторный `confirm` уже готового файла возвращает сохранённый результат; повторный `DeleteMedia` по удалённому файлу возвращает успех.

### 6.7. Гонки, которые надо закрыть

| Гонка                                                 | Правило                                                                                                                   |
|-------------------------------------------------------|---------------------------------------------------------------------------------------------------------------------------|
| Два `confirm` одновременно                            | Аренда идемпотентности + проверка владения арендой при финализации                                                        |
| `confirm` и `DeleteMedia` одновременно                | Удаление сначала убирает строку в `deleted` с условием «нет ссылок»; финализация обработки проверяет, что строка ещё жива |
| Привязка к элементу и фоновая чистка                  | Ссылка появляется раньше сохранения элемента; фон требует нуля ссылок и возраста 24 ч                                     |
| Удаление файла и повторное сохранение старой карточки | Sets получит 404/`NotReady` при синхронной проверке и не сохранит элемент; пользователь видит ошибку                      |

### 6.8. Отказы хранилища и конфигурация

- Настройки `Media:S3` (endpoint, region, bucket, ключи) проверяются при старте: неполные или отсутствующие - падение при запуске, а не ошибка на первом запросе.
- Транзиентные ошибки хранилища в `confirm` не переводят файл в `failed`: отдаётся ошибка клиенту, строка остаётся `pending`, повтор разрешён.
- Ошибка удаления объекта в `tmp/` не ломает `confirm`: объект уйдёт по TTL/lifecycle или фоновой чисткой.

### 6.9. Защита от злоупотребления

- Пять уровней из ADR 0037: policy (`content-length-range`), ограничения на `init` (10 МБ, белый список, 5 `pending`, rate-limit), lifecycle/TTL на `tmp/*`, фоновая чистка, наблюдаемость (объём бакета, `pending` старше часа, журнал отклонений).
- Слот лимита занимают только загрузки с неистёкшим окном (`upload_expires_at > now`): после 10 минут подтвердить загрузку всё равно нельзя, поэтому она не должна блокировать новые. Протухшие `pending` переводятся в `failed` в самом `init` — до подсчёта лимита.
- Квоты на пользователя отложены (§10 п. 10): объём считается запросом по `size_bytes`, отдельного счётчика нет.

### 6.10. Продление ссылок на чтение

- Ссылка живёт 15 минут (`MediaConstraints.ReadLinkLifetime`); набор и его карточки могут быть открыты дольше.
- Продление - отдельной операцией: `POST /api/media/links` с пачкой `mediaIds` (≤ 100) возвращает свежие ссылки страницы, не перезагружая контент.
- Клиент переподписывает ссылки заранее (по таймеру и при возврате к окну); ошибка загрузки картинки - фолбэк на одиночный `GET /api/media/{id}`, одна попытка на файл.
- Выданная ссылка живёт до истечения TTL: отозвать её нельзя - это принимается как цена отказа от прокси байтов через сервер.

## 7. Роли и действия

### 7.1. Роли

| Роль                      | Отношение к модулю                                                                                                                                |
|---------------------------|---------------------------------------------------------------------------------------------------------------------------------------------------|
| Пользователь-владелец     | Загружает файлы и владеет ими; видит их состояние и может удалить. Роль приложения - из токена (ADR 0035), доменная строка - JIT (ADR 0020)       |
| Другой пользователь       | Ничего не видит и не меняет: чужой файл -> 404, ссылки на чтение выдаются только владельцу (видимости наборов пока нет, ORG-02)                   |
| Гость                     | Доменной строки нет, операций модуля не имеет                                                                                                     |
| Потребитель (модуль Sets) | Не пользователь: сообщает ссылки на файлы, проверяет готовность и владение, запрашивает ссылки на чтение, просит удалить файл после снятия ссылок |
| Фоновая обработка         | Чистка брошенных загрузок, объектов `tmp/*`, файлов без ссылок и надгробий удалённых записей                                                      |
| Модератор / Администратор | Служебное приложение (ADR 0004); в публичном модуле не реализуется, роль зарезервирована                                                          |

### 7.2. Действия пользователя

| Действие                  | Что происходит                                                                                                                                                                 | Источник               |
|---------------------------|--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|------------------------|
| Загрузить изображение     | Два шага: получить разрешение на загрузку (`init` -> presigned POST) -> отправить байты в хранилище -> подтвердить (`confirm`). Результат - `mediaId` со статусом и вариантами | ADR 0037, US CREATE-01 |
| Узнать состояние загрузки | Свой файл со статусом `pending` / `ready` / `failed`; в `failed` - код причины, в `ready` - ссылки на варианты. Нужно после перезагрузки страницы и на втором устройстве       | §10 п. 5               |
| Посмотреть изображение    | Ссылка на `thumb` или `display` с TTL; в `pending` ссылок нет                                                                                                                  | ADR 0017               |
| Удалить своё изображение  | Если файл нигде не используется - удаляется; если используется - `409 Media.InUse` и изображение остаётся                                                                      | §10 п. 7               |

Неудачную загрузку пользователь не отменяет вручную: клиент убирает слот с ошибкой из формы, а строка `failed` и временный объект удаляются фоновой чисткой. `failed` ставится только когда файл окончательно не годится (формат, анимация, лимиты, битые данные); если отказала инфраструктура (S3, память), строка остаётся `pending` и `confirm` можно повторить.

Чего пользователь не может: прикрепить файл к элементу (это Sets), прочитать чужой файл (404), удалить используемый файл, увидеть ссылку на файл в `pending`, загрузить файл без подтверждения (байты в `tmp/` не являются изображением для системы).

### 7.3. Действия системы

- Присвоение `id`, ключа `tmp/{uploadId}`, временных меток и владельца из текущей личности (клиент владельца не задаёт).
- Выдача presigned POST с политикой: `expiration` 10 минут, фиксированный `key`, `content-type` из белого списка, `content-length-range` 1..10 МБ (ADR 0037).
- Проверка после загрузки (`confirm`): существование объекта, размер, соответствие заявленному типу, сигнатура формата, лимиты до декодирования (25 Мп / 8000 px), запрет анимации.
- Перекодирование в WebP со снятием метаданных и создание вариантов `thumb` / `display`; удаление исходника из `tmp/` после успеха.
- Ведение статусов (`pending` -> `ready` | `failed`, `ready` -> `deleted`) и учёт `media_references` при решении об удалении.
- Идемпотентность `confirm`: режим B (ключ в `in_progress` + аренда 60 с с продлением), повтор не выполняет работу дважды (§10 п. 8).
- Ленивая проверка `pending` при чтении: объекта нет - сразу `failed`, не дожидаясь фоновой чистки (§10 п. 6).
- Отказ инфраструктуры (S3, память, таймаут) не переводит файл в `failed`: строка остаётся `pending`, `confirm` повторяется; `failed` - только окончательная непригодность файла.
- Фоновая чистка: `pending` старше 24 ч (строка + объект), объекты `tmp/*` без строки, `ready` без ссылок старше 24 ч, надгробия `deleted`. Надгробие - гарантированная точка зачистки хранилища: варианты удаляются из S3 до удаления строки, при сбое S3 строка остаётся и попытка повторяется в следующем цикле.
- Проверка владения на каждой операции; чужой или несуществующий файл - одинаковый 404 (тот же принцип, что в онтологии Sets §6.4).
- Проверка конфигурации хранилища на старте: отсутствие или неполнота - падение при запуске, а не ленивая ошибка на первом запросе.

### 7.4. Действия потребителя (Sets)

| Действие                         | Условие                                                                                                                                                                                                                                                  |
|----------------------------------|----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| Синхронизировать ссылки элемента | При сохранении элемента **синхронно** проверяется готовность и владение файлом (`ready`, владелец = автор) - иначе элемент не сохраняется; после сохранения в outbox пишется актуальный набор ссылок (`set:{setId}:element:{elementId}:front` / `:back`) |
| Запросить ссылки на чтение       | После чтения `mediaId` из payload элемента - пачкой, с тем же фильтром владельца; доступность хранилища на чтении не проверяется                                                                                                                         |
| Удалить файл                     | После снятия ссылок (удаление элемента или набора) - иначе `409 Media.InUse`                                                                                                                                                                             |

## 8. Интеграционные контракты

### 8.1. HTTP API для клиента

| Метод и путь                                | Назначение                                           | Тело / ответ                                                                 | Идемпотентность                            |
|---------------------------------------------|------------------------------------------------------|------------------------------------------------------------------------------|--------------------------------------------|
| `POST /api/media/uploads`                   | `init`: создать `pending` и выдать политику загрузки | `{contentType, sizeBytes}` -> `{mediaId, url, fields, objectKey, expiresIn}` | `Idempotency-Key` обязателен (режим A)     |
| `POST /api/media/uploads/{mediaId}/confirm` | подтвердить загрузку и запустить обработку           | без тела -> `{mediaId, status, variants}`                                    | `Idempotency-Key` обязателен (режим B)     |
| `GET /api/media/{mediaId}`                  | состояние своего файла                               | -> `{mediaId, status, failureCode?, variants?, createdAt}`                   | нет                                        |
| `DELETE /api/media/{mediaId}`               | удалить свой файл                                    | -> `204`                                                                     | идемпотентно: повтор на `deleted` -> `204` |

`variants` в ответе: `{ "thumb": {url, width, height}, "display": {url, width, height} }`; `url` - presigned GET с TTL 15 минут. В `pending` и `failed` поля `variants` нет.

Статусы HTTP: `200` - чтение/повтор confirm; `201` - создан `pending`; `204` - удаление; `400` - форма или правила команды; `404` - чужой или несуществующий файл; `409` - `Media.InUse` или идемпотентность; `413` - превышение размера.

### 8.2. Внутренний контракт для модулей-потребителей (`Media.Contracts`)

Вызовы в процессе, без HTTP: модули живут в одном приложении и одной БД (ADR 0029), но границы схем и типов соблюдаются.

| Метод                                                                        | Назначение                                                                                   | Ответ                                                                              |
|------------------------------------------------------------------------------|----------------------------------------------------------------------------------------------|------------------------------------------------------------------------------------|
| `EnsureReadyAsync(ownerId, IReadOnlyCollection<Guid> mediaIds)`              | синхронная проверка перед сохранением элемента: файл существует, `ready`, принадлежит автору | успех или `ErrorOr` с `Media.NotFound` / `Media.NotReady`                          |
| `SyncReferencesAsync(ownerId, elementScope, IReadOnlyCollection<MediaSlot>)` | декларативная синхронизация ссылок элемента: `{reference, mediaId}`                          | успех или `ErrorOr` (для outbox - повтор)                                          |
| `GetLinksAsync(ownerId, IReadOnlyCollection<Guid> mediaIds)`                 | пачка ссылок на чтение с фильтром владельца                                                  | `IReadOnlyDictionary<Guid, MediaLinks>`; отсутствующие/чужие в словарь не попадают |
| `DeleteAsync(ownerId, mediaId)`                                              | удаление после снятия ссылок                                                                 | успех или `Media.InUse`                                                            |

`elementScope` - префикс ссылок элемента (`set:{setId}:element:{elementId}`), чтобы при синхронизации удалить слоты, которых нет в наборе, не разбирая строки на стороне Media.

### 8.3. Сообщения outbox (потребитель -> Media)

| Тип                     | Payload                                                  | Обработка                                                                                                                                                                   |
|-------------------------|----------------------------------------------------------|-----------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| `media.references.sync` | `{ownerId, elementScope, slots: [{reference, mediaId}]}` | Полная замена слотов области: недостающие удалить, новые вставить, изменённые перезаписать - одной транзакцией. Ошибка «файл не `ready`» - не применяем, сообщение в повтор |

Outbox живёт в схеме Sets (ADR 0036/0037); Media не пишет в чужие таблицы и не публикует события обратно. Доставка at-least-once, поэтому обработчик обязан быть идемпотентным - что и даёт декларативный формат.

### 8.4. Коды ошибок

| Код                            | HTTP   | Когда                                                                                     |
|--------------------------------|--------|-------------------------------------------------------------------------------------------|
| `Media.NotFound`               | 404    | файла нет, он чужой или удалён - неразличимо                                              |
| `Media.NotReady`               | 409    | попытка прикрепить `pending`/`failed` файл при сохранении элемента; `metadata.target` - слот (`element.frontImageId`) |
| `Media.InUse`                  | 409    | удаление файла с ненулевыми ссылками                                                      |
| `Media.UploadExpired`          | 400    | `confirm` после истечения окна (10 минут)                                                 |
| `Media.ObjectMissing`          | 400    | объекта в хранилище нет (ленивая проверка или confirm)                                    |
| `Media.ContentTypeUnsupported` | 400    | тип не из белого списка на `init`                                                         |
| `Media.FileTooLarge`           | 413    | заявленный или фактический размер больше 10 МБ                                            |
| `Media.InvalidFormat`          | 400    | сигнатура не PNG/JPEG/WebP                                                                |
| `Media.UnsupportedAnimation`   | 400    | анимированный GIF/APNG/WebP                                                               |
| `Media.ResolutionTooLarge`     | 400    | больше 25 Мп или 8000 px по стороне                                                       |
| `Media.ImageCorrupt`           | 400    | сигнатура верная, но файл не декодируется (файл -> `failed`)                                  |

Коды - публичный контракт клиента (ADR 0031/0038): описание ошибки не показывается, клиент маппит код в текст; в `metadata` передаются `maxSizeBytes`, `maxPixels`, `maxSide`, а для `Media.NotReady` - `target` (слот элемента).

Инфраструктурные сбои (S3, таймаут, память) отдельного кода не имеют: клиент получает 5xx, файл остаётся `pending` и `confirm` можно повторить. `failed` ставится только когда непригоден сам файл, и всегда сопровождается одним из 400-кодов выше.

### 8.5. Чего в контракте нет

- **Событий наружу** (например «файл готов»): нет потребителей, которые бы их ждали; при появлении аналитики или уведомлений - отдельное решение.
- **Списка своих файлов** с пагинацией: срез images для карточек в нём не нуждается; появится вместе с экраном управления загрузками.
- **Публичных ссылок и CDN**: до видимости наборов (ORG-02).
- **Признака `purpose`**: отложен (§10 п. 11).

## 9. Нефункциональные требования

- **Безопасность**: presigned POST-policy режет размер/тип на стороне хранилища до приёма байт (`content-length-range`); формат проверяется по сигнатуре (magic bytes), затем пересжатие в WebP со снятием метаданных (ADR 0018); лимиты пикселей (25 Мп, 8000 px) - защита от декомпрессионных бомб; всё медиа приватное - presigned GET, TTL 15 мин.
- **Надёжность**: fail-fast конфигурации S3 на старте; идемпотентность `confirm` (аренда 60 с, at-least-once); фоновая чистка `pending`/`failed`/`ready`-без-ссылок/`deleted`; синхронизация ссылок - outbox в Sets (ADR 0040), обработчик идемпотентен.
- **Производительность**: байты идут мимо модуля (presigned POST) - экономия трафика/CPU; CPU - только пересжатие (SkiaSharp) на `confirm`; ссылки на чтение подписываются пачкой на страницу, а не по одному.

## 10. Открытые вопросы

Черновик: решения по ходу согласования разделов. Отмеченные «решено» уже зафиксированы и переносятся в §6/§3 при их заполнении.

1. **Носитель вариантов - решено: отдельная таблица** `media_variants` (`media_id`, `variant`, `object_key`, `width`, `height`, `size_bytes`). JSON-поле в `media_objects` отклонено: цена - JOIN при чтении файла, выигрыш - явные запросы по вариантам и частичная перегенерация без переписывания документа.
2. **Единица контракта - решено: один `mediaId`** в payload элемента; в ответе API - карта вариантов (`variants.thumb`, `variants.display` со ссылкой и размерами). Клиент выбирает размер сам, добавление нового варианта не меняет ни payload карточки, ни контракт.
3. **Состав вариантов - решено: два** (`thumb` <= 400 px, `display` <= 1600 px). Retina-вариант (`display2x`) отложен: добавляется новым значением `variant`, существующие объекты догоняются фоновой переобработкой.
4. **Учёт привязанности - решено: таблица ссылок.** Sets при сохранении элемента присылает актуальный набор ссылок на файлы (непрозрачный ключ вида `set:{setId}:element:{elementId}:front`); Media хранит их в таблице `media_references` (`media_id`, `reference`) и считает количество. Повторная отправка того же ключа ничего не ломает (upsert/skip), поэтому потерянное сообщение лечится повтором; удаление ссылки - идемпотентно. Фон удаляет `ready`-объекты с нулём ссылок старше 24 часов и `pending` без подтверждения.
5. **Статусы и видимость - решено:** `pending` / `ready` / `failed` / `deleted`. Владелец видит все свои статусы; в `pending` ссылок на чтение нет, прикрепить файл к элементу нельзя (Sets проверяет через контракт `ready` + владение). `failed` хранит код причины - клиент показывает «файл не подошёл» и предлагает другой.
6. **Брошенные загрузки - решено:** фон раз в час удаляет строки `pending` и `failed` старше 24 ч и их объекты `tmp/*` (оба удаления идемпотентны); плюс ленивая проверка при чтении `pending` - HEAD объекта, и если его нет, сразу `failed`, чтобы клиент не ждал сутки.
7. **Удаление привязанного файла - решено: отказ.** `DeleteMedia` при наличии ссылок возвращает `409 Media.InUse`; Sets сначала снимает ссылки, потом удаляет файл. Если ссылки сняты, а удаление не дошло - файл без ссылок уберёт фон, данные не страдают. Вопрос о том, что видит пользователь при уже битой ссылке в payload (заглушка или ошибка чтения), остаётся открытым.
8. **Идемпотентность `confirm` - решено: режим B с арендой 60 с.** Ключ коммитится отдельно со статусом `in_progress` и `lease_until`; аренда продлевается каждые 20 с по ходу обработки; финализация только если аренда всё ещё своя (иначе воркер молча выходит); после истечения аренды следующий запрос выполняет работу заново (at-least-once безопасно: ключи вариантов детерминированы).
9. **Схема ключей в хранилище**: `tmp/{uploadId}` на время загрузки -> `media/{mediaId}/{variant}.webp` после обработки (ADR 0037 добавляет `ownerId` в путь - уточнить при реализации, нужен ли он для чистки); сохранять ли исходник и хеш содержимого (дедупликация) - сейчас не планируется.
10. **Квоты и учёт объёма - предварительно отложено:** лимит только на файл (10 МБ). Занятый объём считается запросом по `size_bytes` владельца (отдельный счётчик не нужен), отказ при превышении - когда появятся реальные пользователи.
11. **Изображения вне карточек - предварительно отложено:** аватары и обложки не вводят поле `purpose` сейчас; если понадобятся другие лимиты/варианты - добавление поля аддитивно.
12. **Анимированные изображения - решено: запрет** с кодом `Media.UnsupportedAnimation`. GIF/APNG/анимированный WebP отклоняются на `confirm`; молчаливый первый кадр отклонён.
13. **Замена изображения у элемента - решено: смена ссылок.** В том же сохранении элемента Sets снимает старую ссылку (`...:front` для старого `mediaId`) и ставит новую; старый файл остаётся без ссылок и уходит в фоновую чистку. Отдельного detach-вызова не нужно: ключ ссылки детерминирован, повтор безопасен.
14. **Доставка ссылок - решено: outbox в Sets.** Синхронизация ссылок на медиа идёт через transactional outbox в схеме Sets (`sets.outbox_messages`: `id`, `type`, `payload jsonb`, `created_at`, `processed_at`, `attempts`, `last_error`): запись в той же транзакции, что и сохранение элемента; фоновый диспетчер вызывает Media с повторами; обработчик Media идемпотентен по ключу ссылки (at-least-once). Первый межмодульный потребитель, для которого outbox откладывался (ADR 0036, ontology Sets §8) - оформить отдельным ADR.

## 11. Эволюция

- **Публичная выдача/CDN** - с видимостью набора (ORG-02): публичный вариант объекта + отдельный домен отдачи (ADR 0018).
- **Retina-вариант `display2x`** - добавлением значения `variant` + фоновая переобработка существующих (§10 п.3).
- **Аватары/обложки** - поле `purpose` для других лимитов/вариантов (§10 п.11).
- **Квоты объёма** на пользователя (§10 п.10).
- **Дедупликация по хешу** содержимого (§10 п.9).
- **Обновление presigned GET-ссылок** при долгих сессиях редактора: сейчас TTL 15 мин, ссылки протухают.
