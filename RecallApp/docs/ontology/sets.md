# Ontology: модуль Sets (контент: наборы и элементы)

> Статус: черновик (заполнены §1–§2, §3–§11 - каркас; 2026-11-10).
> Назначение: детализация модуля из [карты](./README.md). Структура разделов повторяет [Accounts](./accounts.md).
> Источники: План платформы §2–§5, US `CREATE-01`, US `CORE-01`, US `ORG-01/02`, ADR 0013/0015/0017/0018/0029.

## 1. Предметная область и границы модуля

Модуль Sets - доменное представление **пользовательского учебного контента**: наборов (коллекций заданий на запоминание и проверку знаний) и элементов внутри них, порядка их показа, происхождения наборов и объединения наборов в личные подборки. Модуль не знает, как контент проходят и что запоминает пользователь: этим занимается модуль Study.

**Внутри модуля:**
- **Набор**, **элементы набора** как атомы учебного контента: создание, правка, удаление, порядок показа элементов внутри набора (CREATE-01).
- **Полиморфный контент элемента**: реляционные поля элемента с его типом и его документное поле.
- **Форки и атрибуция**: `origin_set_id` - ссылка на непосредственного родителя; «публичное = копируемое».
- **Группы наборов** (личные папки, ORG-01): объединение своих наборов в тематические подборки, принадлежат пользователю.
- **Ссылки на изображения элементов**.
- Схема `sets` в БД монолита: таблицы модуля и собственные миграции (ADR 0029).

**Сознательно снаружи:**
- **Доменный пользователь** и профиль - Accounts. Sets держит `User.id` владельца.
- **Прохождение, режимы, SRS-расписание** - Study. Sets отдаёт контент по контракту `Sets.Contracts`; проверка ответов, результаты и планирование повторений - не здесь («ключевой шов» карты модулей).
- **Публичный каталог и поиск** - Organization: read-модель над опубликованными наборами.
- **Видимость и публикация набора** (`private` / `unlisted` / `public`), доступ по ссылке - ORG-02 (вместе с каталогом ORG-03). В модели CREATE-01 признака видимости нет: набор доступен только владельцу. Возврат к вопросу - вместе с ORG-02.
- **Учебные группы** (сообщества пользователей) - модуль контекста, не Sets. «Группа наборов» (личная папка) и «учебная группа» - разные сущности.
- **Байты изображений** - объектное хранилище (S3-совместимое, ADR 0008) по presigned-ссылкам (ADR 0017); обработка и безопасность файлов - ADR 0018 и будущий модуль Media.
- **Модерация публичного контента** - служебное приложение (ADR 0004).
- **Аутентификация и роли приложения** - Keycloak/BFF (ADR 0001/0024/0035). Владение набором - доменное отношение, а не роль.
- ИИ-генерация наборов и MCP-доступ (AI-01/02) - off-scope.

## 3. Сущности и атрибуты

### 3.1. `Set` (набор)

| Атрибут       | Тип                    | Владелец            | Правило                                                               |
|---------------|------------------------|---------------------|-----------------------------------------------------------------------|
| `id`          | uuid, PK               | домен               | генерируется сервером при создании                                    |
| `owner_id`    | uuid, NOT NULL, индекс | Accounts (значение) | ссылка без FK (ADR 0036); берётся из `ICurrentUser`, клиент не задаёт |
| `title`       | text, NOT NULL         | домен               | VO `SetTitle`                                                         |
| `description` | text, NOT NULL           | домен               | VO `SetDescription`; пустая строка - единственное представление отсутствия |
| `created_at`  | timestamptz, NOT NULL  | домен               | момент создания                                                       |
| `updated_at`  | timestamptz, NOT NULL  | домен               | меняется при правке атрибутов и состава элементов                     |
| `deleted_at`  | timestamptz, NULL      | домен               | мягкое удаление (ADR 0036); NULL, если живой набор                    |

**Инварианты:** `title` непустой после trim; живой набор всегда имеет владельца; удалённый набор невидим пользователю и не участвует в чужих операциях за исключением тех, где он выступает целевым.

### 3.2. `Element` (элемент набора)

| Атрибут                     | Тип                   | Владелец | Правило                                                                                                      |
|-----------------------------|-----------------------|----------|--------------------------------------------------------------------------------------------------------------|
| `id`                        | uuid, PK              | домен    | генерируется сервером                                                                                        |
| `set_id`                    | uuid, NOT NULL        | домен    | FK внутри своей схемы (`elements.set_id -> sets.id`, `ON DELETE CASCADE`); межсхемные FK запрещены (ADR 0036) |
| `type`                      | text, NOT NULL        | домен    | дискриминатор типа; в CREATE-01 только `flashcard`; после создания не меняется                               |
| `position`                  | text, NOT NULL        | домен    | строковый ранг (LexoRank), уникальный среди живых элементов набора; сортируется побайтово (COLLATE "C") |
| `payload`                   | jsonb, NOT NULL       | домен    | поля, специфичные для типа (VO `FlashcardPayload`); схема проверяется при записи                             |
| `created_at` / `updated_at` | timestamptz, NOT NULL | домен    |                                                                                                              |
| `deleted_at`                | timestamptz, NULL     | домен    | мягкое удаление элемента                                                                                     |

**Инварианты:** элемент всегда принадлежит набору и не существует вне его; `payload` валиден по схеме своего `type`; живой элемент всегда имеет уникальный ранг позиции в наборе (частичный уникальный индекс `(set_id, position) WHERE deleted_at IS NULL`).

### 3.3. Изображения элемента

Файлы принадлежат модулю Media (схема `media`, ADR 0037); в агрегате набора хранятся только ссылки: `frontImageId` / `backImageId` (uuid) в `payload`, без FK (ADR 0036). Байты - в объектном хранилище (ADR 0008), доступ - presigned-ссылки (ADR 0017), обработка и пересжатие - в Media по ADR 0018/0037.

Для выдачи отдаётся вариант `display`/`thumb` с presigned GET (TTL 15 минут), ссылка вычисляется при чтении набора; публичной выдачи пока нет (появится с видимостью, ORG-02).

### 3.4. Группа наборов и форки

Сущности есть в карте модулей (личные папки - ORG-01, форки `origin_set_id` - ORG-06), но в CREATE-01 не реализуются: атрибуты описываются при детализации соответствующих фич.

## 4. Агрегаты и границы

- **`Set` - корень агрегата**, элементы - его часть, а не самостоятельный агрегат: инвариант «элемент всегда в живом наборе» и «ранги позиций уникальны» держится только в одной транзакции.
- **Граница консистентности = один набор.** Любая операция (создать/править/удалить элемент, переставить, переименовать набор, удалить набор) меняет строки этого набора и его элементов в одной транзакции.
- **Частичная загрузка допустима:** операция над одной карточкой не обязана читать весь набор; нужны только соседи перемещаемого элемента, остальные позиции не меняются.
- **Вне агрегата:** пользователь (Accounts, ссылка `owner_id`), изображения (объектное хранилище), прохождение и прогресс (Study).
- **Удаление набора** - мягкое удаление набора и его элементов в одной транзакции; физическая чистка - фоном (ADR 0036).

## 6. Политики

### 6.1. Сохранение и «черновик» (CREATE-01)

- Каждая доменная операция (создание, правка, удаление элемента; переименование набора; смена порядка) фиксируется сразу. Промежуточных «незавершённых» сущностей в домене нет: набор и элемент всегда валидны.
- Повторная отправка создания не приводит к дублю: повтор с тем же ключом идемпотентности возвращает тот же результат (серверная идемпотентность, см. §8). Клиентская защита (блокировка кнопки, отсутствие ретраев на 4xx) - дополнение, а не гарантия.
- Недописанный ввод живёт на клиенте и переживает перезагрузку вкладки; на сервер уходит только целый элемент, подтверждённый на сохранение/обновление.

### 6.2. Владение и доступ

- Любая операция модуля требует владельца набора; `owner_id` берётся из контекста запроса, который заполняет JIT-ступень (`ICurrentUser`, ADR 0036); клиент его не задаёт.
- `owner_id` - обычный `uuid` с индексом, **без внешнего ключа** в `accounts.users`: межсхемные FK не используем (ADR 0036).
- Данные чужого модуля читаются только через его контракт; прямая запись в чужую таблицу и `JOIN` через границу запрещены.
- Чужой набор отвечает тем же кодом, что и несуществующий: **404, а не 403**. Иначе код ответа становится маркером существования: перебором идентификаторов можно собрать карту чужих наборов и понять, что было удалено, а разные ветки формирования 403/404 расходятся ещё и текстом и временем ответа. Разделение простое: ошибка **уровня ресурса** (нет объекта или нет доступа) -> 404 с одинаковым телом; ошибка **уровня операции или роли** (роль не позволяет операцию, состояние набора её запрещает) -> 403, объект при этом клиенту известен. Причина («не найден» / «не твой») остаётся в логах и трейсах и наружу не отдаётся.
- Анонимный вызов отсекается до домена (401 на конвейере BFF); у гостя операций в модуле нет.
- Список наборов отдаёт только наборы текущего владельца.
- Список постраничный и **курсорный**: порядок `created_at DESC, id DESC`, клиент возвращает непрозрачный `nextCursor`, размер страницы 1–100 (дефолт 20). Offset-пагинация не используется (ADR 0039).

### 6.3. Набор

- `title` обязателен: trim, непустой, ограничение длины - §10.
- `description` обязателен на уровне схемы; отсутствие описания выражается пустой строкой (единственное представление, null не используется).
- Набор может быть пустым (0 элементов); запрет прохождения пустого набора - на стороне Study (CORE-01-US-1), не в домене контента.
- Переименование не меняет `id` и порядок элементов. Удаление необратимо для пользователя: корзины и восстановления нет. Физическое удаление - по политике мягкого удаления с фоновой чисткой (ADR 0036).

### 6.4. Элемент

- Хранение обобщённой строкой: общие реляционные поля (принадлежность набору, тип, позиция) + документное поле с полями, специфичными для типа (ADR 0015). Реляционная часть одинакова для всех типов; тип задаёт только состав документного поля и правила проверки его содержимого.
- Обязательные реляционные поля есть у элемента любого типа: набор, тип, позиция.
- Элемент всегда принадлежит ровно одному набору и вне набора не существует (включая flash-карточку).
- Удаление элемента не удаляет и не меняет сам набор, но затрагивает порядок остальных: их позиции не меняются, в порядке остаётся дырка.
- В CREATE-01 реализуется единственный тип - для флеш-карточки. Тип задаётся при создании и дальше не меняется (новый тип - реализация нового элемента).
- Для флеш-карточки обязательны `term` и `definition` (trim, непустые): они лежат в документном поле типа, а не в реляционных колонках. Для других типов обязательность своя (варианты ответа, пропуски, пары и т.д.) - её определяет тип, когда появляется. Ограничения длины - §10.

### 6.5. Позиция и порядок

- Позиция — строковый ранг: между любыми двумя значениями всегда можно вычислить третье, поэтому вставка и перестановка не трогают остальные элементы.
- Новый элемент всегда встаёт в конец: ранг вычисляется после последнего элемента набора.
- Перестановка — по соседям: элемент встаёт между `prev` и `next` (любая граница может быть `null` — начало или конец набора). Остальные элементы не меняются.
- Уникальность `(set_id, position)` — страховка от гонки: при конкурентной вставке в тот же интервал база вернёт конфликт, а не сломает порядок.
- Удаление оставляет «дырку» в рангах: плотная перенумерация не нужна.
- Порядок принадлежит модулю и используется прохождением; перемешивание - временное состояние сессии (Study), на набор не влияет.

### 6.6. Удаление и каскады

- Удаление набора каскадно удаляет его элементы.
- Подтверждение удаления - на клиенте отдельным шагом; домен удаляет по факту запроса и идемпотентен к повтору (удалённое - 404).
- Удаление ступенчатое: (1) мягкое удаление в одной транзакции (набор и его элементы помечаются `deleted_at`), для пользователя сущностей больше нет; (2) окно retention - за него зависимые модули успевают отреагировать; (3) физическая чистка фоном. FK `ON DELETE CASCADE` работает только на третьей ступени и только внутри своей схемы.
- Зависимые модули по-разному реагируют на tombstone: производные данные (SRS-записи, сессии, записи каталога) удаляются сразу и физически - восстанавливать их нечем; soft delete у потребителя оправдан только для контента, который пользователь мог бы вернуть. Персональные данные владелец стирает сразу при пометке (152-ФЗ), tombstone хранит только идентификатор и время.
- Окно retention должно быть больше максимального простоя любого зависимого модуля; отставание потребителей измеряется (tombstones старше окна, которые ещё не потреблены).
- Изображения и их объекты в хранилище: при появлении media-среза - пометка на удаление и фоновая очистка.

### 6.7. Время и конкурентность

- `created_at` / `updated_at` - доменные; `updated_at` набора меняется при смене названия, описания и состава элементов (создание, правка, удаление, перестановка). Перестановка меняет метку набора, но не `updated_at` самих элементов.
- Список наборов сортируется по `created_at` (keyset-курсор `created_at DESC, id DESC`, ADR 0039); `updated_at` в сортировке не участвует.
- Конкурентные правки - last-write-wins, версий/ETag в CREATE-01 нет (осознанно). Сценарий двух вкладок - §10.
- Если `prev`/`next` изменились между чтением и перестановкой (например, удалены в другой вкладке), операция возвращает ошибку `Element.OrderNeighbourNotFound` или `Element.OrderInvalid`; клиент перезагружает набор.

### 7.1. Роли

| Роль                      | Отношение к модулю                                                                                                                                                |
| ------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Пользователь              | Владелец своих наборов: единственный, кто читает и меняет их содержимое. Роль приложения приходит из токена (`roles`, ADR 0035), доменная строка - JIT (ADR 0020) |
| Гость                     | Доменной строки нет, операций модуля не имеет: в CREATE-01 видимости нет, чужой набор недоступен                                                                  |
| Модератор / Администратор | Служебное приложение (ADR 0004); в публичном модуле не реализуется, роль зарезервирована                                                                          |

### 7.3. Действия системы

- Присвоение `id` и временных меток при создании набора и элемента на стороне бэкенда.
- Выдача позиции: в конец набора (ранг после последнего элемента); плотная перенумерация не требуется ни при вставке, ни при удалении, ни при перестановке.
- Обновление `updated_at` набора при изменении его атрибутов или состава.
- Каскадное удаление элементов при удалении набора.
- Защита от дубля при повторной отправке: `Idempotency-Key` обязателен для POST-создания; повтор с тем же ключом и телом отдаёт сохранённый ответ, тот же ключ с другим телом - 409, истёкшие ключи чистит фоновый процесс (§6.1, §8).
- Проверка владения на каждой операции (чужая запись -> 404).

## 8. Интеграционные контракты

Предзаготовка (полностью - после §3, когда будут поля и операции):

- **Вход от BFF (доверенный канал):** access-токен в `Authorization`, монолит валидирует JWT (ADR 0028); личность -> JIT-ступень -> `ICurrentUser.UserId`. Модуль claims не парсит и к Accounts не обращается (ADR 0036).
- **Наружу (REST за BFF):** операции из §7.2 (наборы и элементы), ошибки - ProblemDetails с кодом в `title` и расширением `source` (ADR 0031).
- **Клиентские режимы:** у набора на клиенте два режима на одном и том же контракте - редактирование и предпросмотр (read-only). Предпросмотр - часть CREATE-01; прохождение (переворот, листание, перемешивание, прогресс) - CORE-01, отдельная фича. Визуальные детали (расположение переключателя, слайдер/список) - вне онтологии, решаются в UI.
- **Идемпотентность POST-создания:** обязательный заголовок `Idempotency-Key` (UUID); ключ скопирован по владельцу - PK `(owner_id, key)` в таблице схемы модуля (`operation`, `request_hash`, `status_code`, `response`, `expires_at`).
  - Резервирование ключа и бизнес-запись идут **в одной транзакции**, поэтому статуса «в процессе» не нужно: либо строка зафиксирована вместе с объектом, либо её нет. Конкурентный повтор ждёт на уникальном индексе, затем читает готовую строку.
  - Ветки на конфликт: тот же `request_hash` - сохранённый ответ как есть (тот же статус и `Location`); другой хеш - 409; нет ключа/невалидный - 400. Коды ошибок по ADR 0031.
  - `request_hash` считается по канонической форме тела (стабильный порядок полей, trim строк), иначе один и тот же запрос даст ложный 409.
  - TTL ключей и фоновая чистка по `expires_at` - общая инфраструктура с purge-задачами (ADR 0036). `Idempotency-Key` нужно добавить в allowed headers CORS-политики BFF (ADR 0030).
  - Режим рассчитан на короткие операции, которые целиком укладываются в одну транзакцию: ключ и бизнес-запись коммитятся вместе, поэтому статуса «в процессе» нет. Для операций с сетевым I/O (загрузка и обработка медиа, внешние API) потребуется отдельный режим: короткий коммит ключа со статусом «в процессе» и lease, работа вне транзакции, финализация и восстановление зависших ключей. Такой режим вводится вместе с первым таким сценарием (медиа-срез).
- **Для других модулей:** `Sets.Contracts` - чтение контента для прохождения (Study) и для каталога (Organization); запись в Sets только через его собственные операции.
- **Оповещение об удалении:** базовый способ - опрос контракта (`GetDeletedElementIdsSince(watermark)`, аналогично для наборов); потребитель хранит свой watermark, чистка идемпотентна. Источник данных контракта - журнал удалений (отдельная таблица в схеме модуля с монотонным номером), а не колонка в самих сущностях; состав журнала и момент его ввода досогласуются. Мгновенные события - отдельным решением, если появится требование к задержке.
- **Внешние системы:** изображения - модуль Media поверх объектного хранилища S3: presigned POST с policy на загрузку (ограничение размера силами хранилища), confirm с проверкой и пересжатием в WebP, presigned GET на выдачу (ADR 0017/0018/0037). Контракт Media для Sets: инициализация загрузки, подтверждение, получение ссылок, `DeleteMedia`.
- **События:** в этом пути не используются; межмодульные реакции - по ADR 0036 при первом реальном потребителе.

## 9. Нефункциональные требования

- **Безопасность**: чужой и несуществующий ресурс неотличимы - 404 (ADR 0031); каждая выборка фильтруется по `owner_id`, межсхемных FK нет (ADR 0036). Личность - через BFF (ADR 0028).
- **Надёжность**: POST-создание идемпотентно (`Idempotency-Key` -> `sets.idempotency_keys`, UNIQUE `(owner_id, key)`, TTL 24 ч, фоновая чистка); конкурентное редактирование - last-write-wins без ETag (ETag отложен, §10).
- **Порядок**: перестановка — обновление одной строки (ранг между соседями); остальные элементы и их индексы не трогаются, двухфазный сдвиг не нужен.
- **Производительность**: списки - keyset-пагинация без OFFSET (ADR 0039); редактор грузит набор целиком (нужно для перестановки), предпросмотр - постранично (страницы по 20) + итог одним `COUNT` в `SetResponse.elementCount`.

## 10. Открытые вопросы

1. **Доменный «черновик» элемента** (существует в системе, но не попадает в прохождение) - отложен. Сейчас элемент либо сохранён целиком, либо его нет; отдельный статус тянул бы определение «полноты» по каждому типу и фильтр «кроме черновиков» у всех потребителей. Вернуться, если появятся типы с большим текстом (пропуски, CORE-04) и подтвердятся значимости потери при сбоях.
2. **US-7 в вики** («автосохранение черновика») требует переформулировки: сейчас обещает восстановление «несохранённых изменений», что расходится с немедленным сохранением элементов; фактический смысл решения - клиентский буфер недописанного ввода.
3. **Дефолтное название набора при быстрой карточке** (US-5): шаблон (например, с датой) или пустое имя с подсказкой; как избежать копилки одноимённых «Моих наборов».
4. **Конкурентное редактирование**: остаёмся на last-write-wins или вводим версию/ETag, когда появится реальный сценарий двух окон?
5. **Серверная идемпотентность создания** - принята в CREATE-01 (`Idempotency-Key`, §8). Остаётся согласовать TTL ключей (по умолчанию 24 часа) и момент ввода фоновой чистки.

## 11. Эволюция

- **Новые типы элементов** (`singleChoice`, `multipleChoice`): в домене - новый вариант `ElementPayload`; на клиенте - вариант размеченного объединения + модуль полей (точки расширения уже есть).
- **Вставка в произвольную позицию** в UI редактора: бэкенд `position` уже принимает; клиент пока добавляет только в конец.
- **Обучение (CORE-01)**: флип-предпросмотр уже есть; SRS/оценки/повторения приходят отдельным срезом.
- **Организация и поиск (ORG-01)**: папки/теги/поиск - отдельный срез поверх тех же агрегатов.
- **Видимость набора (ORG-02)**: тянет публичную выдачу медиа (см. Media §11).
- **ETag/версии** - если подтвердится сценарий двух окон (§10 п.4).
