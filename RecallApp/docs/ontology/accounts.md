# Ontology: модуль Accounts (аккаунты и доступ)

> Статус: черновик (C1, 2026-10-30).
> Назначение: детализация модуля из [карты](./README.md). Дорабатывается по ходу.
> Входит в скелет модульного монолита (ADR 0013). Источники личности и сессии находятся вне модуля: Keycloak (ADR 0001) и BFF (ADR 0002/0025).

## 1. Предметная область и границы модуля

Модуль Accounts - доменное представление человека в системе RecallApp: доменный **пользователь** (строка в БД монолита), его профильные атрибуты и доменные роли/владение, которое на него вешают другие модули.

**Внутри модуля:**
- доменный пользователь и его профиль (отображаемое имя);
- кэш email для фоновых задач и уведомлений;
- провижининг (JIT) доменной строки из claims, переданных BFF;
- доменные операции аккаунта: просмотр своего аккаунта, (вне ACCT-01) редактирование профиля и удаление аккаунта.

**Сознательно снаружи:**
- **Личность** (креды, пароль, верификация email, соц-провайдеры, блокировки) - Keycloak. Модуль в IAM не ходит, токены не валидирует (ADR 0020).
- **Аутентификация и сессия** - Keycloak (SSO-сессия) и BFF (cookie-сессия, refresh). Модуль про сессии ничего не знает; он получает уже провалидированную личность.
- **Роль приложения «Пользователь»** - не доменная: это client-роль Keycloak, читается из токена на BFF/монолите (ADR 0024). Модуль её не назначает и не хранит.
- **Контент и его видимость** (наборы, форки, `private`/`unlisted`/`public`) - Sets; **контекстные роли** (в учебной группе, в матче) - модули контекста (Organization/Multiplayer), ссылкой на `User.id` (карта модулей, принцип «публичное = копируемое»).
- Подписки/оплата, аватар-хранилище, уведомления - будущие модули; Accounts даёт им идентификатор пользователя, а не наоборот.

## 2. Ubiquitous Language

| Термин | Определение | Не путать с |
|--------|-------------|-------------|
| **Личность** (identity) | Учётная запись человека в Keycloak: креды, провайдеры, блокировки. Ключ - `sub` (UUID). Не существует в домене | доменным пользователем |
| **Пользователь** (user) | Доменная строка, представляющая человека в системе. Создаётся JIT при первом доменном запросе. Ключ связи с личностью - `keycloak_sub` | личностью, гостем |
| **Аккаунт** | Синоним «вошедшего пользователя» в UI и пользовательских историях (ACCT-01). В коде термин не используем - используем «пользователь» | - |
| **Гость** | Человек без личности/доменной строки. Доменной строки нет и не создаётся; провижининг только для аутентифицированных (ADR 0020) | анонимным вызовом API |
| **Профиль** | Набор доменных атрибутов пользователя: отображаемое имя (+ позже настройки). Владелец - домен | данными Keycloak |
| **Подтверждённый email** | Верификация адреса обязательна: запускается при регистрации/первом входе (required action «verify email» в Keycloak). Признак - стандартный OIDC-claim `email_verified` (scope `email`); домен его не кэширует: в контексте запроса читается из claims, отдельных потребителей у кэша сейчас нет | подтверждением доставки писем |
| **Роль приложения** | Глобальная роль из client-роли Keycloak (`resource_access` токена, ADR 0024): «Пользователь». Не доменная, модуль её не назначает и не хранит | доменной ролью |
| **Контекстная роль** | Доменная роль внутри контекста: учебная группа, матч (wiki «Роли и доступ»). Владение - модули контекста (Организация/Мультиплеер), со ссылкой на `User.id`; при создании пользователя пусты, накапливаются действиями (ADR 0020). В Accounts не живут | ролью приложения |
| **Сессия** | Период работы клиента: BFF-cookie + Keycloak SSO (параметры - ADR 0027). Не сущность модуля Accounts | доменной сущностью |

## 3. Сущности и атрибуты

### 3.1. `User` (доменный пользователь)

| Атрибут | Тип | Владелец | Правило |
|---------|-----|----------|---------|
| `id` | uuid, PK | домен | генерируется при создании |
| `keycloak_sub` | uuid, **UNIQUE NOT NULL** | Keycloak (значение) | стабильный внешний ключ личности; неизменен с момента создания |
| `email` | text, NOT NULL | **Keycloak** | кэш для фоновых задач/уведомлений; освежается upsert'ом JIT на каждом проходе; смена догоняется следующим запросом пользователя (ADR 0020). Обязательность email гарантирует Keycloak (required email при регистрации; broker flow провайдеров требует email - без него вход не завершается) |
| `display_name` | text, NOT NULL | **домен** | сидируется из claim `name` при создании; дальше редактируется в приложении, к Keycloak не синхронизируется |
| `created_at` | timestamptz | домен | момент первого JIT-провижининга |
| `updated_at` | timestamptz | домен | touch при изменении доменных атрибутов (не при кэш-освежении email) |

**Инварианты:**
- `keycloak_sub` уникален и иммутабелен; одна личность - ровно одна строка.
- `display_name` непустой, длина 1–100; допустимы пробелы и Unicode (имена/ники), trim по краям.
- Признак верификации email доменом не кэшируется: в контексте запроса он доступен из claims токена (Bearer-форвардинг, ADR 0028); если будущему потребителю (например, Notifications с правилом «только verified») понадобится кэш - добавим колонку миграцией.

### 3.2. Настройки пользователя (позже ACCT-01)

Value object/owned-сущность `UserPreferences` (тема, язык, таймзона) - закладываем место в модели, реализуем с первой реальной фичей, которой настройки нужны.

## 4. Агрегаты и границы

- **Агрегат `User`** - корень: строка `User` (+ в будущем owned `UserPreferences`). Единая консистентная граница - сама строка.
- Таблица `users` принадлежит модулю Accounts; другие модули ссылаются на пользователя по `id` (FK на уровне схемы модулей допустим как ссылка, запись - только через свой домен; прямые JOIN/запись в чужую таблицу запрещены, ADR 0013).
- Владение, прогресс, SRS, подписки - отдельные агрегаты **других модулей**, у которых User - ссылка, а не часть агрегата.

## 5. Value Objects

| VO | Состав | Правила |
|----|--------|---------|
| `Email` (кэш-тип) | адрес | формат по стандарту; храним нижним регистром; нормализация при сравнении |
| `DisplayName` | строка | 1–100, trim, не пустая после trim |

## 6. Политики

1. **JIT-провижининг** (ADR 0020): одна сквозная ступень конвейера перед доменными эндпоинтами; upsert `ON CONFLICT (keycloak_sub) DO NOTHING` + перечитывание строки; проверка «найти-потом-вставить» запрещена.
2. **Владение атрибутами**: email/верификация - Keycloak (домен = кэш), display_name - домен (Keycloak не источник). Никакой двусторонней синхронизации.
3. **Гость не провижинится**: только аутентифицированный доменный конвейер; гостевой read (шаринг по ссылке, ORG-02) строку не создаёт.
4. **Роли приложения из токена**: модуль не назначает и не хранит client-роли (ADR 0024).
5. **Анонимный write запрещён** на уровне конвейера (до домена).

## 7. Роли и действия

Глобальные роли (полный реестр - wiki «Роли и доступ»):

| Роль | Отношение к модулю |
|------|--------------------|
| Гость | строки нет; доменные операции недоступны |
| Пользователь | своя строка; просмотр аккаунта; (вне ACCT-01) редактирование профиля, удаление аккаунта. Контекстных ролей на старте нет |
| Модератор / Администратор | служебное приложение, отдельный realm (ADR 0004); зарезервированы, в публичном модуле не реализуются |

Действия модуля под ACCT-01:
- `GetMyAccount` - текущий пользователь: профиль + признаки из claims (email, верификация).
- Выход (US-4) выполняет BFF (`POST /logout`), домен не участвует.
- Регистрация/вход/восстановление пароля (US-1,2,3,5) - Keycloak; домен участвует только через JIT.

## 8. Интеграционные контракты

**Вход (от BFF, доверенный канал):** BFF проксирует запрос на монолит через YARP request transform: access-токен текущей сессии кладётся в `Authorization: Bearer`, входящие `Authorization`/`Cookie` отбрасываются. Монолит валидирует JWT (issuer - Keycloak, trusted domain) и читает личность из claims. Детали решения - ADR 0028 (Trusted Domain); полноценный Token Exchange - отдельной ADR при распределёнке.

**Выход (REST, за BFF):**
- `GET /api/users/me` → `{ id, displayName, email, emailVerified }` - **профиль аккаунта, без ролей**. Роли не входят осознанно: роль приложения читается из токена (ADR 0024), контекстные роли отдают модули контекста вместе с данными группы/матча.
- Аноним → 401 `not_authenticated` (конвейер BFF, уже реализовано).

Под ACCT-01 реализуется только `GetMyAccount`; прочие операции модуля - отдельными пунктами бэклога.

**События:** внутри процесса; внешний брокер - только при выносе модуля (ADR 0013).

## 9. Нефункциональные требования

- **Безопасность**: монолит принимает JWT только с валидной подписью Keycloak; токен прикрепляет исключительно BFF (YARP-трансформ), клиентские `Authorization` отбрасываются. Ребро монолит→Keycloak допускается только за JWKS (кэш подписей). Планируется в C1 (пункты 5, 6).
- **Надёжность провижининга**: идемпотентность на UNIQUE-constraint, одна БД, без распределённых транзакций.
- **Производительность**: JIT - один upsert + один select на первом запросе пользователя; дальше строка читается штатно (EF). Кэш email не требует отдельных запросов к Keycloak - никогда.

## 10. Открытые вопросы

1. **Lifecycle: удаление/деактивация** пользователя (хвост ADR 0020) - отдельная запись/ADR; блокирует реализацию «удалить свой аккаунт» из матрицы прав, но не ACCT-01.
2. Редактирование профиля (смена `display_name`) - вне ACCT-01; добавляется отдельным пунктом бэклога.
3. Username/handle (уникальный публичный ник) - нужен ли? Поиска людей в Плане нет (карта модулей); если понадобится - соц-фаза, влияет на uniqueness-политики `display_name` (сейчас уникальность не требуется).
4. Фоновая сверка кэша email для «сменил и больше не заходил» (ADR 0020) - механизм и частота.
5. Модератор/Администратор на публичном приложении - всегда обычный Пользователь или доменная пометка нужна? (Пока: нет.)

## 11. Эволюция

- **Соц-вход и слияние аккаунтов** (ADR 0022): JIT уже агностичен к провайдеру - личность даёт `sub`; слияние по верифицированному email не меняет модуль (меняет только Keycloak).
- **Подписки/биллинг**: отдельный модуль, ссылается на `User.id`.
- **Гостевой прогресс → регистрация**: перенос гостевых матчевых результатов (вне ACCT-01; матчи - in-memory, ADR 0014).
- **Вынос модуля**: не планируется (единая БД, ADR 0013); критерии выноса к Accounts неприменимы.
