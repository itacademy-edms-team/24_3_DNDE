# Ontology: карта модулей модульного монолита

> Статус: черновик (C1, 2026-10-30).
> Назначение: верхнеуровневая карта доменов (модулей) «от общего к частному». Каждый модуль детализируется своим `ontology.md`-файлом по мере работы. Дорабатывается по ходу.
> Основание: ADR 0013, План платформы §2–§5, ADR 0004.

## Принципы декомпозиции

1. **Одна сущность - один владелец.** Ссылка на `User.id` из других модулей - норма; запись в чужую таблицу и JOIN через границу - нет (ADR 0013).
2. **Ключевой шов - Контент ↔ SRS** (План §4.1): Study знает про Sets (через контракт «Результат проверки»), Sets про Study не знает. Односторонняя зависимость.
3. **Мультиплеер - отдельный слой**, от него не зависит одиночное обучение; первый кандидат на вынос в сервис (ADR 0013/0014).
4. **Гость - без доменной строки** (ADR 0020): границы модулей не предполагают аккаунт у читателя/игрока.
5. **Фаза модуля** - по реестру фич Плана §3/§5; скелет строим по MVP-набору, остальное - заготовки границ, не кода.
6. **Области видимости набора: `private` / `unlisted` (по ссылке) / `public`.** Принцип: **публичное = копируемое** (норма сегмента: Quizlet/Anki; согласуется со ставкой против lock-in). Форкать можно только `public`; `unlisted` - просмотр по ссылке без форка и без поиска. Атрибуция сохраняется автоматически: `origin_set_id` - ссылка на непосредственного родителя; «авторы» - вычисляемая цепочка происхождения (обход вверх до корня, отображение «форк от ... · оригинал ...»); владелец набора всегда один, у форка владельцем становится форкнувший. Форк - снимок: обновления оригинала не тянет, публикуется как обычный набор. «Сохранить чужой набор» = только форк.

## Карта модулей

| # | Модуль | Назначение (1 строка) | Данные (сущности Плана §2) | Фаза | Зависимости |
|---|---|---|---|:---:|---|
| 1 | **Accounts** | доменный пользователь: профиль, JIT из личности | Пользователь | MVP | - (источник ссылок для всех) |
| 2 | **Sets** (контент) | наборы и элементы: создание, типы форматов, прохождение без SRS, свои папки, форки | Набор (+`origin_set_id`), Элемент набора, Группа наборов (папки) | MVP | Accounts (владелец) |
| 3 | **Study** (обучение + SRS) | режимы прохождения, SRS-планирование, чередование | Сессия, SRS-запись | MVP → core | Sets (через «Результат проверки», односторонне) |
| 4 | **Organization** (организация и поиск) | шаринг, публичная библиотека, учебные группы | Учебная группа, каталог библиотеки (read-модель) | MVP → core | Sets, Accounts |
| 5 | **Gamification** | достижения, стрики, викторины | Достижение, Награда/стрик | social | Study (факты активности), Accounts |
| 6 | **Multiplayer** | матчи (realtime/асинхрон), игроки, команды | Матч, Игрок, Команда (матчевое состояние - in-memory, ADR 0014) | social | Sets (набор), Accounts (опц.); вынос-кандидат |
| 7 | **Media** | медиафайлы элементов: загрузка, доступ, безопасность (ADR 0008/0017/0018) | медиа-объекты (presigned-доступ) | core/ext | Sets (ссылки из элементов) |
| 8 | **Notifications** | доставка email/push по доменным событиям (ADR 0006/0019) | шаблоны, журнал отправок | ext | Accounts (email-кэш), события модулей |
| 9 | **Billing** | подписки, оплата (ЯКасса, ADR 0009) | подписка, платежи | off-scope (вне горизонта) | Accounts |

**Вне публичного монолита:** back-office приложение (модерация/администрирование, отдельный контур и realm - ADR 0004, зарезервировано); MCP-фасад для ИИ-агентов (ADR 0005, off-scope); realtime-узел матчей (если вынесем - ADR 0014).

## Направления зависимостей

```
Accounts ← Sets ← Study        (Study → Sets только через «Результат проверки»)
Sets ← Organization, Multiplayer
Study ← Gamification           (факты активности для стриков/достижений)
Accounts ← (все другие: ссылка User.id, без владения)
Media ← Sets (Sets хранит ссылки, Media - файлы)
Multiplayer → Study: только доменные события (результаты матча в SRS не пишутся напрямую)
```

Правило чтения: стрелка `A ← B` - B зависит от публичного контракта A. Циклов нет; единственный разрешённый «назад» - доменные события (например, Gamification подписывается на события Study), не прямые вызовы.

## Поиск в модуле Organization

«Поиск» здесь - это **поиск контента** в публичной библиотеке (План §3.5). Пользователь или гость ищет опубликованные наборы, группы наборов и учебные группы по названию/тегам/тексту элементов - с фильтрами, сортировкой и пагинацией. Данные каталога живут в Sets и Organization; Accounts участвует лишь как справочник «автор по `User.id` → `display_name`».

Владение публикацией: **видимость набора (`private`/`unlisted`/`public`) - свойство самого набора в Sets** (меняется владельцем, это жизненный цикл контента); **публичный каталог библиотеки - read-модель в Organization** (проекция опубликованных наборов для поиска: ранжирование, дедупликация форков), строится из фактов публикации, ими не владеет. Шаринг по ссылке (`unlisted`) - без сущности: URL + проверка видимости.

## Порядок детализации ontology

По мере работы, каждый следующий модуль - перед его первой фичей: Accounts → Sets → Study → Organization → остальные.

Вопросы границ решаются в ontology-файлах соответствующих модулей по мере их детализации.
