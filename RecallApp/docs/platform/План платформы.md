# План платформы

> Что строим, в каком порядке и из чего. Зачем и для кого: [Стратегия](../vision/Стратегия.md). Исходный замысел: [Проект](../vision/Проект.md). Научная база форматов и SRS: [Смысловое ядро](../vision/Смысловое%20ядро.md). Разбор конкурентов: [обзор конкурентов](../competitors/README.md).

## 1. Назначение и связи

Это рабочая карта реализации: модель данных, реестр фич, архитектурные решения, порядок работ.

Слои документации:
- **Стратегия**: почему, для кого, чем отличаемся.
- **План платформы** (здесь): что и в каком порядке.
- **Роли и доступ**: роли, права, разделение публичного и служебного приложений.
- **User Stories**: потребности пользователя (будут позже).
- **Decision Records** (PDR/ADR): обоснования продуктовых и архитектурных решений (будут позже).

Что здесь не дублируется: обоснования идут в Decision Records, детали научных методов в Смысловом ядре, факты по конкурентам в их обзоре.

## 2. Модель данных (сущности и связи)

Выведено из [Проекта](../vision/Проект.md) и [Смыслового ядра](../vision/Смысловое%20ядро.md). Модель двухслойная: **контент самодостаточен**, **SRS надстроен поверх него** (обоснование в §4). Контент работает и без SRS.

### Слой 1. Контент (без SRS)

| Сущность | Описание | Связи |
|----------|----------|-------|
| Элемент набора | Атом контента. Имеет тип (см. ниже), задаёт поля и проверку. Контракт: предъявить → принять ответ → проверить → вернуть Результат проверки | принадлежит Набору |
| Набор | Коллекция Элементов (бывший «модуль»), типы могут смешиваться. Проходится и без SRS | 1 Набор — много Элементов; принадлежит Пользователю |
| Группа наборов | Объединение наборов | 1 Группа — много Наборов |
| Учебная группа | Сообщество пользователей с подборками наборов/групп | много Пользователей, много Наборов/Групп |
| Пользователь | Аккаунт; роли и права — см. [Роли и доступ](Роли%20и%20доступ.md) | владеет Наборами, состоит в Учебных группах |

Типы Элемента набора (каждый самодостаточен, у каждого свои поля и проверка):

| Тип | Поля | Проверка | Класс формата |
|-----|------|----------|---------------|
| Флеш-карточка | лицо, оборот, медиа, направление(я) | переворот / самооценка | извлекающий |
| С выбором | вопрос, варианты[], верное подмножество, один/несколько | сверка подмножества | извлекающий |
| Ввод ответа | вопрос, допустимые ответы, правило сверки | сравнение строки | извлекающий |
| Верно/неверно | утверждение, истинность | сверка флага | извлекающий |
| Сопоставление | набор пар | сверка пар | извлекающий |
| Пропуски | текст, пропуски[] | сверка каждого пропуска | извлекающий |
| Последовательность | элементы, верный порядок | сверка порядка | извлекающий |
| Числовой | вопрос, значение, допуск | отклонение | извлекающий |
| Подпись изображения | картинка, метки[], подписи/зоны | сверка координат/подписи | извлекающий |
| Free recall | вопрос, эталон | нечёткая сверка | извлекающий |
| Дивергентный (опрос/облако) | вопрос | эталона нет | дивергентный |

Список расширяется по мере добавления форматов (см. [Смысловое ядро](../vision/Смысловое%20ядро.md)).

**Результат проверки** = `{исход: верно/неверно/частично, опц. сигнал сложности}`. Это контракт между слоями: единственное, что Слой 2 читает у Слоя 1.

### Слой 2. SRS (надстройка)

SRS не знает внутренностей форматов. Работает только с Результатом проверки.

| Сущность | Описание | Связи |
|----------|----------|-------|
| SRS-запись | SRS-состояние: интервал, дата следующего показа, сложность. Ссылается на то, что реально планируется: Элемент, направление карточки или отдельный пропуск. Создаётся только для извлекающих элементов | ссылается на Элемент/направление/пропуск; принадлежит Пользователю |
| Сессия | Прогон режима (заучивание/тест/игра): результаты, время. Может затронуть несколько элементов (сопоставление, тест с дистракторами) — Результат каждого кормит его SRS-запись | Пользователь, Набор, много Элементов |

По умолчанию мастерство **раздельное**: у карточки и теста об одном факте свои SRS-записи. Общее мастерство остаётся опциональной боковой связью на потом (§7), не foundational.

Дивергентные элементы Результата с исходом не дают → SRS-запись для них не создаётся, в SRS не участвуют. Дистракторы для теста/сопоставления берутся из других извлекающих элементов набора.

### Мультиплеер

| Сущность | Описание | Связи |
|----------|----------|-------|
| Матч | Realtime или асинхронная сессия на нескольких игроков | над Набором |
| Игрок | Участник матча (может быть гостем без аккаунта) | в Матче, опц. Пользователь |
| Команда | Группировка игроков в матче | Игрок × Команда |

### Геймификация

| Сущность | Описание | Связи |
|----------|----------|-------|
| Достижение | Разблокируемая цель | Пользователь × Достижение |
| Награда / стрик | Ежедневные награды, серии | принадлежит Пользователю |

|--------|------|-------|
| `MVP` | мес 1–2 | фундамент: аккаунт, карточки, создание, шаринг |

## 4. Архитектурные ставки

Решения фиксируются позже в ADR; здесь только направление.

1. **Контент самодостаточен, SRS отдельный слой.** Элемент набора предъявляет, принимает ответ и проверяет его, возвращая Результат проверки, ничего не зная о расписании. Набор проходится и без SRS. SRS-слой читает только Результат и планирует SRS-запись. Зависимость идёт в одну сторону: SRS знает про контент, контент про SRS не знает. Так можно строить и использовать форматы раньше SRS и менять расписание, не трогая контент.
2. **Формат как контракт, класс формата решает участие в SRS.** Элемент определяет: что показать (вопрос), что сделать пользователю (вспомнить/вписать/выбрать), как проверить ответ. Класс формата (извлекающий / дивергентный) решает, создаётся ли SRS-запись. Режим оценки (авто-сверка / самооценка / нечёткая) задаёт, как получен сигнал сложности в Результате. Новые форматы добавляются по этому контракту.
3. **Realtime для мультиплеера отдельный слой.** Матчи (live-соревнования) требуют realtime-сервера; одиночное обучение от него не зависит. Самообучение не должно деградировать без сети.
4. **Гость без аккаунта.** Вход в матч гостем: низкий порог (ответ Kahoot). Аккаунт обязателен только для владения контентом и накопления прогресса.
5. **Web-first, адаптив.** Веб адаптирован под десктоп/планшет/телефон (как у обоих конкурентов). Отдельные мобильные приложения в off-scope.
6. **Оценка ответов на вводе.** Для форматов со свободным вводом проверка по эталону; нейросетевая оценка «правильно/неправильно» остаётся кандидатом (Проект), но не на старте.
7. **Служебное приложение (back-office) отдельно от публичного.** Модерацию и администрирование выносим в отдельное приложение со своим контуром доступа; привилегия — флаг на обычном аккаунте Пользователя. Публичный продукт не несёт привилегированного кода. Предусмотреть при проектировании, детали в ADR «Служебное приложение». Распределение прав: [Роли и доступ](Роли%20и%20доступ.md).

## 5. Приоритизация и роадмап

Горизонт 8 месяцев. Фазы ниже соответствуют статусам из §3. Число фич, недельные слоты и зависимости в [Бэклоге](Бэклог.md).

### MVP (мес 1–2): фундамент

Аккаунт, карточки (классический режим), ввод ответа, ручное создание набора, импорт текстом, папки/группы, шаринг по ссылке. Цель: пользователь создаёт набор и учит его. Проверка базовой гипотезы: люди создают и проходят наборы.

### core (мес 3–5): научное ядро

SRS-планировщик, заучивание с SRS, чередование, многоформатная проверка, тест/пропуски/сопоставление, верно/неверно, числовой ответ, публичная библиотека и поиск. Цель: включить главный дифференциатор, удержание на научной базе.

### social (мес 6–8): геймификация и мультиплеер

Достижения, награды/стрики, викторины, последовательность, учебные группы, realtime-матч с гостевым входом, статистика матча. Цель: социальная геймификация поверх ядра.

### ext: добивка внутри горизонта

Автоподсказки определений, сохранить чужой набор, экспорт, подпись изображения, дублировать чужой набор, прогрессирующее восстановление. Берутся при наличии ёмкости.

### off-scope: вне 8 месяцев

Free recall, TTS, ИИ-генерация, мини-игры, «объясни и угадай», учительский слой (курсы, задания, отчёты), мобильные приложения, нейросетевая оценка ответов.

Порядок внутри фаз ориентировочный, уточняется по User Stories и Decision Records.

## 6. Нефункциональные требования

| Требование | Суть | Почему |
|-----------|------|--------|
| Устойчивость мультиплеера | Матч переживает слабую сеть и массовый одновременный вход классом | жалобы на подключение у Kahoot |
| Производительность realtime | Низкая задержка на матчах | формат-соревнование чувствителен к лагу |
| Доступность ядра офлайн/при сбоях | Одиночное обучение не зависит от realtime-слоя | §4.3 |
| Прозрачность биллинга | Явная отмена, никаких скрытых списаний | повторные списания и спорный триал — частые жалобы у обоих конкурентов |
| Локализация | Русский интерфейс, рубли | целевой рынок |
| Адаптивность | Десктоп/планшет/телефон из веба | §4.5 |
| Приватность | Контроль видимости профиля и наборов | норма сегмента |

## 7. Открытые вопросы

1. Какой алгоритм SRS: готовый (SM-2 / FSRS) или свой? Решается в ADR.
2. Экономика «бесплатное ядро + платное удобство»: какие функции реально платные, где порог лимитов? Проверяется рано (Стратегия §6, §9).
3. Нейросетевая оценка свободных ответов: качество, стоимость, когда включать.
4. Как смягчать холодный старт библиотеки против сетевого эффекта Quizlet (импорт, ИИ, фокус на удержании)?
5. Нужна ли учебная группа отдельно от будущих курсов учителя, или это один примитив с ролями? (У Quizlet разделены.)
6. Форматы для «объясни и угадай» и эстафетной механики: отдельный тип сессии, проработать в User Stories.
7. Общее мастерство для элементов об одном факте (карточка и тест → одна SRS-запись). По умолчанию раздельно; боковая связь «элементы об одном знании» добавляется позже, не foundational.
